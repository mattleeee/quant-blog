幂等部署设计：可重复执行的更新脚本

2026-10-27 工程实践

部署脚本最怕的场景不是失败，而是“失败了一半”。远程打补丁时，网络抖动、SSH 超时、磁盘写满、进程被 kill，任何一步都可能让脚本停在中间状态。此时运维的第一反应是重跑脚本——如果脚本不可重入，重跑轻则报错误判，重则把已完成的步骤再执行一遍，造成配置重复、数据覆盖甚至服务不可用。

幂等（idempotent）部署的核心目标只有一个：同一份脚本，执行一次和执行 N 次，系统最终状态一致。下面从判断模式、反模式、远程补丁 checklist 三个层面拆解具体做法。

一、幂等检查的四种模式

1. 内容标记（Content Marker）

最可靠的判断方式：不看“第几步执行到哪”，只看“目标状态是否已经存在”。判断依据是目标文件或资源的内容特征，而不是计数器或时间戳。

import hashlib
import os

MARKER = "# managed-by: deploy-script-v3"

def patch_applied(target_file: str, marker: str = MARKER) -> bool:
    """检查目标文件是否已包含部署标记"""
    if not os.path.exists(target_file):
        return False
    with open(target_file, "r", encoding="utf-8") as f:
        content = f.read()
    return marker in content

def apply_patch(target_file: str, patch_block: str, marker: str = MARKER) -> bool:
    """幂等地追加补丁块；已应用则跳过"""
    if patch_applied(target_file, marker):
        print(f"[skip] {target_file} already patched")
        return False
    with open(target_file, "a", encoding="utf-8") as f:
        f.write(f"\n{patch_block}\n{marker}\n")
        f.flush()
        os.fsync(f.fileno())   # 立即写盘，防止断电丢内容
    print(f"[apply] {target_file} patched")
    return True

用内容标记的好处：即使脚本在“写完补丁但还没写状态文件”时崩溃，重跑时 patch_applied 依然能识别出补丁已存在，不会重复追加。状态文件可以丢，内容不会骗人。

2. 目标状态比对（Desired State Diff）

对配置文件类补丁，更稳妥的做法是先算出“期望内容”，再和现状比对，只做差异部分。

import re

def ensure_config_line(config_path: str, key: str, value: str) -> bool:
    """确保配置文件中 key=value 存在且唯一，幂等"""
    pattern = re.compile(rf"^{re.escape(key)}\s*=.*$", re.MULTILINE)
    new_line = f"{key}={value}"

    if not os.path.exists(config_path):
        with open(config_path, "w", encoding="utf-8") as f:
            f.write(new_line + "\n")
        return True

    with open(config_path, "r", encoding="utf-8") as f:
        content = f.read()

    matches = pattern.findall(content)
    if len(matches) == 1 and matches[0].strip() == new_line:
        return False                      # 已是目标状态
    if matches:
        content = pattern.sub(new_line, content, count=1)
        # 清理可能存在的重复行
        content = pattern.sub("", content)
    else:
        content = content.rstrip("\n") + "\n" + new_line + "\n"

    with open(config_path, "w", encoding="utf-8") as f:
        f.write(content)
        f.flush()
        os.fsync(f.fileno())
    return True

3. 资源存在性探测

对“创建类”操作（建目录、建用户、建 systemd unit），直接探测资源是否已存在，而不是靠“上次是否成功”的布尔值。

import subprocess

def ensure_user(username: str) -> bool:
    result = subprocess.run(
        ["id", "-u", username], capture_output=True, text=True
    )
    if result.returncode == 0:
        return False
    subprocess.run(["useradd", "-r", "-s", "/usr/sbin/nologin", username], check=True)
    return True

4. 版本号/指纹标记

对二进制或整包更新，用版本指纹判断，比时间戳可靠得多。

def current_version(binary: str) -> str:
    out = subprocess.run([binary, "--version"], capture_output=True, text=True)
    return out.stdout.strip()

def ensure_version(binary: str, expected: str) -> bool:
    if current_version(binary) == expected:
        return False

二、常见反模式

反模式一：先删后建

# 错误示范
shutil.rmtree("/opt/app/conf")
shutil.copytree("/tmp/new_conf", "/opt/app/conf")

如果 copytree 中途失败，/opt/app/conf 就没了，重跑脚本也救不回来——因为源可能已经清理。正确做法是先写临时目录，校验通过后原子替换：

import tempfile

def atomic_replace_dir(src: str, dst: str):
    parent = os.path.dirname(dst)
    tmp = tempfile.mkdtemp(dir=parent, prefix=".deploy-")
    try:
        shutil.copytree(src, os.path.join(tmp, "payload"))
        payload = os.path.join(tmp, "payload")
        backup = dst + ".bak"
        if os.path.exists(dst):
            os.rename(dst, backup)
        os.rename(payload, dst)
        if os.path.exists(backup):
            shutil.rmtree(backup)
    finally:
        shutil.rmtree(tmp, ignore_errors=True)

反模式二：计数式判断

# 错误示范
STATE_FILE = "/var/lib/deploy/step.txt"

def get_step() -> int:
    return int(open(STATE_FILE).read()) if os.path.exists(STATE_FILE) else 0

def run():
    step = get_step()
    if step < 1:
        do_step1()
        open(STATE_FILE, "w").write("1")
    if step < 2:
        do_step2()
        open(STATE_FILE, "w").write("2")

问题在于：do_step2() 执行成功但写状态文件前崩溃，重跑时 step 仍是 1，do_step2 会被再执行一次。计数式判断把“执行”和“记录”拆成两个非原子操作，天然存在窗口。用目标状态判断，别用执行进度判断。

反模式三：无条件覆盖

# 错误示范：每次都覆盖，配置里手工改过的项全丢
with open("/etc/app/config.yml", "w") as f:
    f.write(DEFAULT_CONFIG)

覆盖式写入在“重跑”场景下会把运维手工调过的参数冲掉。应改为“只补缺失项”或“按 key 合并”。

反模式四：依赖外部副作用判断

用 curl 探测服务是否起来决定要不要重启，看似合理，但服务可能因其他原因已运行，导致补丁永远不会被应用。判断依据必须和补丁本身强相关。

三、每步成功立即写盘的实现

幂等判断解决“要不要做”，立即写盘解决“做到一半崩了怎么办”。原则：每个原子步骤完成后，立即把该步骤的结果持久化，且持久化动作本身要幂等。

import json

class DeployLog:
    def __init__(self, path: str):
        self.path = path
        self.data = {}
        if os.path.exists(path):
            with open(path) as f:
                self.data = json.load(f)

    def mark(self, step: str, payload: dict):
        self.data[step] = payload
        tmp = self.path + ".tmp"
        with open(tmp, "w") as f:
            json.dump(self.data, f)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, self.path)   # 原子替换

    def done(self, step: str) -> bool:
        return step in self.data

配合内容标记使用：DeployLog 只是加速跳过，真正的正确性由内容标记兜底。即使日志文件丢失，重跑也不会重复打补丁。

四、远程打补丁完整 checklist

一个可重入的远程补丁脚本，按以下顺序组织：

  1. 前置检查：SSH 连通性、磁盘空间、目标路径存在性、依赖命令（systemctl/docker）可用。检查失败直接退出，不产生任何副作用。
  2. 备份：对将被修改的文件做带时间戳备份（cp -a），备份本身幂等——已存在同名备份则跳过。
  3. 逐项应用补丁：每项补丁独立函数，内部先做内容标记检查，未应用才执行，执行后 fsync。
  4. 配置校验：nginx -t、systemd-analyze verify、python -m py_compile 等，校验失败回滚本次变更，不影响已完成的项。
  5. 服务重载：只在配置确实变化时 reload，用 systemctl is-active + 配置哈希判断。
  6. 健康检查：curl 本地端点或 nc -z 端口，失败则告警但不自动回滚（回滚本身也需幂等）。
  7. 日志落盘：每步结果写入 DeployLog，供下次运行跳过。
  8. 退出码语义化：0 全部成功或全部已应用；1 前置检查失败；2 部分应用需人工介入。

对应的执行骨架：

STEPS = [
    ("backup",    do_backup),
    ("patch_ssh", lambda: apply_patch("/etc/ssh/sshd_config", SSHD_BLOCK)),
    ("patch_nginx", lambda: ensure_config_line("/etc/nginx/nginx.conf", "worker_rlimit_nofile", "65535")),
    ("reload",    reload_if_changed),
]

def run_deploy(log: DeployLog):
    for name, fn in STEPS:
        if log.done(name):
            print(f"[skip] {name}")
            continue
        try:
            changed = fn()
            log.mark(name, {"changed": bool(changed)})
        except Exception as e:
            print(f"[fail] {name}: {e}")
            return 2
    return 0

注意 fn() 的返回值表示“是否真的做了变更”，供后续步骤（如 reload）判断。这样即使某步因已应用而跳过，reload 逻辑也不会被误触发。

五、小结

幂等部署不是加个 if exists 就完事，它要求每个步骤都满足三个性质：判断依据与目标状态强相关、执行与记录原子化、失败可安全重入。内容标记做判断、原子替换做写入、每步立即落盘、checklist 覆盖前置与后置校验——这套组合在远程补丁场景下能把“重跑”从高风险操作变成常规操作。

写完脚本后最有效的验证方式：在测试机上故意在每步之间 kill -9，然后重跑，检查最终状态是否与一次跑完完全一致。跑不通的，就是还有非幂等的角落。
