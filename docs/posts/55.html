Gate.io API的分页陷阱：from+to+limit不能共存

2026-10-25 API实战

拉历史K线这件事，看起来是最简单的活。一个循环，翻页，拼起来，完事。但Gate.io期货行情API在这件事上埋了个坑：from、to、limit 三个参数只要同时出现，接口直接甩你一个400，而且错误信息里一个字都不提参数冲突，只告诉你请求有问题。你盯着文档看半天，参数名没错、格式没错，就是不通。

这篇文章把这个坑拆开讲清楚：怎么复现、正确的分页姿势是什么、撞到10000点上限怎么绕、以及遇到类似问题时怎么用最小参数组合快速定位。

一、问题背景

Gate.io期货（合约）的K线接口大致长这样：

GET /api/v4/futures/{settle}/candlesticks

常用参数：

  • contract：合约名
  • interval：K线周期，如 1m、5m、1h、1d
  • from：起始时间戳（秒）
  • to：结束时间戳（秒）
  • limit：返回条数上限

文档里对 from / to / limit 的描述是分开写的，各自都"能用"。直觉上你会认为：我给定时间区间 [from, to]，再用 limit 控制每次返回多少条，服务端在区间内分页返回——这是绝大多数交易所API的通用语义。

Gate.io不是。它的实际行为是：这三个参数互斥性极强，同时传会直接报错。

二、错误复现

先写一段最"理所当然"的代码：

import requests
import time

BASE = "https://api.gateio.ws/api/v4"

def fetch_candles_naive(contract, interval, start_ts, end_ts, limit=1000):
    url = f"{BASE}/futures/usdt/candlesticks"
    params = {
        "contract": contract,
        "interval": interval,
        "from": start_ts,
        "to": end_ts,
        "limit": limit,
    }
    resp = requests.get(url, params=params, timeout=10)
    print("status:", resp.status_code)
    print("body:", resp.text[:300])
    return resp

if __name__ == "__main__":
    now = int(time.time())
    fetch_candles_naive(
        contract="BTC_USDT",
        interval="1h",
        start_ts=now - 7 * 24 * 3600,
        end_ts=now,
        limit=1000,
    )

返回：

status: 400
body: {"label":"INVALID_PARAM_VALUE","message":"invalid argument"}

invalid argument——哪个argument？不说。你改 limit 大小、改时间戳、换合约，全是同一个错误。这就是最恶心的地方：错误信息不指向冲突本身，你只能靠猜。

把参数一个个删掉试：

参数组合 结果
from + to 200
from + limit 200
to + limit 200
from + to + limit 400

到这里结论就出来了：三者不能共存。from + to 能跑，但它返回的是区间内全部数据，没有分页能力，数据量大时一样会撞上别的限制（后面讲）。

三、正确的分页姿势：from + limit 单向翻页

Gate.io实际支持的分页语义是：给 from 和 limit，服务端从 from 开始向后取 limit 条。翻页靠推进 from，而不是靠 to 划区间。

关键细节：下一页的起点不是"上一页最后一条的时间戳"，而是最后一条时间戳 + 周期秒数（也就是 +1 根K线）。如果直接用最后一条的时间戳当新的 from，你会把上一页最后一根K线重复拉一次，拼接后出现重复数据。

import requests
import time

BASE = "https://api.gateio.ws/api/v4"

INTERVAL_SECONDS = {
    "10s": 10, "1m": 60, "5m": 300, "15m": 900,
    "30m": 1800, "1h": 3600, "4h": 14400,
    "8h": 28800, "1d": 86400,
}

def fetch_candles_paged(contract, interval, start_ts, end_ts,
                        limit=1000, settle="usdt"):
    """
    用 from + limit 单向翻页拉取 [start_ts, end_ts] 区间的K线。
    返回按时间升序排列的K线列表，元素为 dict。
    """
    url = f"{BASE}/futures/{settle}/candlesticks"
    step = INTERVAL_SECONDS[interval]
    cursor = start_ts
    all_candles = []

    while cursor < end_ts:
        params = {
            "contract": contract,
            "interval": interval,
            "from": cursor,
            "limit": limit,
        }
        resp = requests.get(url, params=params, timeout=10)
        resp.raise_for_status()
        batch = resp.json()

        if not batch:
            break

        # Gate.io 返回的 t 是字符串时间戳（秒）
        for c in batch:
            ts = int(c["t"])
            if start_ts <= ts <= end_ts:
                all_candles.append(c)

        last_ts = int(batch[-1]["t"])
        # 关键：+step，而不是直接用 last_ts
        cursor = last_ts + step

        # 拉到的最后一条已经越过 end_ts，收工
        if last_ts >= end_ts:
            break

        # 防止服务端返回条数不足导致死循环
        if len(batch) < limit:
            break

        time.sleep(0.2)  # 简单限速，避免触发频率限制

    # 去重 + 排序，双保险
    dedup = {int(c["t"]): c for c in all_candles}
    return [dedup[k] for k in sorted(dedup)]


if __name__ == "__main__":
    now = int(time.time())
    data = fetch_candles_paged(
        contract="BTC_USDT",
        interval="1h",
        start_ts=now - 30 * 24 * 3600,
        end_ts=now,
        limit=1000,
    )
    print("count:", len(data))
    print("first:", data[0]["t"], "last:", data[-1]["t"])

几个必须注意的点：

  1. cursor = last_ts + step，不是 last_ts。少加这一步，每页交界处会多一根重复K线，做回测时这种重复数据会污染指标计算，而且很难发现。
  2. len(batch) < limit 时 break。服务端有时返回不满一页，如果不判断，cursor 推进后可能原地打转。
  3. 去重兜底。用时间戳做 key 建字典，即使逻辑有疏漏也不至于把脏数据带进下游。
  4. raise_for_status()。400错误在翻页循环里如果不抛，resp.json() 会解析出错误体，后面 batch[-1]["t"] 直接 KeyError，报错位置离真正原因十万八千里。

四、10000点上限与多区间拼接

翻页逻辑写对了，还有第二个限制：单个查询窗口最多只能取最近10000个数据点。也就是说，不管你 from 设得多早，服务端只认最近10000根K线范围内的数据；更早的历史，from 怎么往前推都拿不到。

这个限制的应对方式是区间切分：把目标时间范围切成若干个子区间，每个子区间内的数据量控制在10000点以内，逐段拉取后拼接。

def fetch_candles_chunked(contract, interval, start_ts, end_ts,
                          limit=1000, max_points=10000, settle="usdt"):
    """
    按 max_points 切分时间区间，逐段调用 fetch_candles_paged，
    规避单窗口10000点上限。
    """
    step = INTERVAL_SECONDS[interval]
    chunk_span = max_points * step  # 每个子区间覆盖的秒数

    result = []
    seg_start = start_ts
    while seg_start < end_ts:
        seg_end = min(seg_start + chunk_span - step, end_ts)
        part = fetch_candles_paged(
            contract, interval, seg_start, seg_end,
            limit=limit, settle=settle,
        )
        result.extend(part)
        seg_start = seg_end + step

    dedup = {int(c["t"]): c for c in result}
    return [dedup[k] for k in sorted(dedup)]

切分时有两个细节：

  • chunk_span = max_points * step，子区间长度按"点数 × 周期秒数"算，保证每段理论点数不超过上限。
  • 段与段之间留 step 的间隔（seg_start = seg_end + step），避免相邻段在边界上重叠。即使重叠了，最后的去重也能兜住，但少一次重叠就少一次无谓的请求。

如果目标区间跨度极大（比如拉几年的一分钟线），max_points=10000 意味着每段只有约7天（1m周期下 10000 分钟 ≈ 6.9 天），段数会很多。这时候要配合限速和重试：

def fetch_with_retry(contract, interval, start_ts, end_ts,
                     retries=3, backoff=1.0, **kwargs):
    for i in range(retries):
        try:
            return fetch_candles_chunked(
                contract, interval, start_ts, end_ts, **kwargs
            )
        except requests.HTTPError as e:
            if e.response is not None and e.response.status_code == 429:
                time.sleep(backoff * (2 ** i))
                continue
            raise
    raise RuntimeError("retries exhausted")

五、调试方法：最小参数组合二分排查

这次踩坑暴露出的通用调试思路值得记下来：遇到"参数看起来都对但接口报错"时，不要读文档猜，用最小参数组合做二分。

具体做法：

  1. 先只传必填参数（contract + interval），确认接口通。
  2. 每次加一个参数，观察状态码变化。
  3. 一旦某次加参数后从200变400，那个参数就是嫌疑对象。
  4. 再在嫌疑参数之间做两两组合，定位到具体冲突对。

写成一个可复用的小工具：

import itertools

def probe_params(url, base_params, optional_params, timeout=10):
    """
    逐个、两两组合探测可选参数，找出导致报错的组合。
    """
    def call(extra):
        p = {**base_params, **extra}
        r = requests.get(url, params=p, timeout=timeout)
        return r.status_code

    print("baseline:", call({}))

    keys = list(optional_params.keys())
    for k in keys:
        code = call({k: optional_params[k]})
        print(f"+{k}: {code}")

    for a, b in itertools.combinations(keys, 2):
        code = call({a: optional_params[a], b: optional_params[b]})
        print(f"+{a}+{b}: {code}")


if __name__ == "__main__":
    now = int(time.time())
    probe_params(
        url=f"{BASE}/futures/usdt/candlesticks",
        base_params={"contract": "BTC_USDT", "interval": "1h"},
        optional_params={
            "from": now - 3600 * 24,
            "to": now,
            "limit": 100,
        },
    )

输出会直接把 +from+to+limit: 400 这一行打出来，冲突组合一目了然。这个方法对所有"文档描述模糊、错误信息笼统"的交易所API都适用，比反复读文档快得多。

另外补充两个排查习惯：

  • 打印完整请求URL。requests 的 params 会被编码，肉眼看不出来时把 resp.request.url 打出来，确认没有多余的空格或类型错误（时间戳传成字符串有时也会触发400）。
  • 看响应体的 label 字段。Gate.io的错误体里有 label，虽然这次是笼统的 INVALID_PARAM_VALUE，但其他场景（如签名、频率限制）会给出更具体的label，值得先看一眼再动手。

六、小结

把这次的坑归纳成几条可以直接抄进项目里的规则：

  • Gate.io期货K线接口，from、to、limit 不要同时传，分页只用 from + limit。
  • 翻页推进用 上一页最后时间戳 + 周期秒数，不要用时间戳本身。
  • 单次查询窗口上限 10000 点，超了就用区间切分 + 拼接 + 去重。
  • 循环里必须处理"返回不满一页"和"重复数据"两种情况，否则不是死循环就是脏数据。
  • 遇到参数冲突类问题，用最小参数组合二分探测，别靠读文档猜。

分页这种基础设施代码，写一次就要写对，因为它会出现在每一个数据拉取脚本里，错了就是全盘错。把上面的 fetch_candles_chunked 封装成公共模块，后面所有策略回测、数据入库都复用它，比每次现写现调省事得多。
