模拟盘几个月不开仓的排查：35%信号达标率下的零开仓悖论

2026-11-17 量化策略

一个做空的模拟盘连续几个月零开仓。第一反应和大多数人一样：最近没行情，或者信号条件太严。

但直觉不靠谱。用历史数据离线复现信号扫描器之后，结论完全相反——硬条件满足率高达35%，平均每天都能出一个合格做空信号。信号根本不缺。

问题出在信号产生之后的链路。这篇文章把整个排查过程拆开讲，重点不是"这个bug怎么修"，而是怎么系统性地定位一个"信号明明有、订单就是不出"的问题。

一、先别猜，把"信号供给"量化出来

排查零开仓，最常见的错误是从执行层往上猜：是不是API挂了？是不是风控拦了？是不是下单参数错了？这些都要查，但顺序错了。

正确的第一步是回答一个问题：这个策略在给定时间段内，理论上应该产生多少个信号？

如果答案是"接近零"，那问题在信号逻辑本身；如果是"每天都该有"，那问题一定在信号之后的消费链路。这一步不做，后面全是拍脑袋。

离线复现信号扫描器

思路很简单：拿一批标的的历史K线，用和线上完全一致的硬条件去扫，统计满足率。这里用24个跌幅榜币种 × 4个月 × 720根4h K线。

import pandas as pd
import numpy as np

def compute_ema(series: pd.Series, span: int) -> pd.Series:
    return series.ewm(span=span, adjust=False).mean()

def hard_condition(df: pd.DataFrame) -> pd.Series:
    """
    做空硬条件：EMA8 < EMA21 且 收盘价 < EMA200
    df 需包含 close 列，按时间升序
    """
    ema8 = compute_ema(df["close"], 8)
    ema21 = compute_ema(df["close"], 21)
    ema200 = compute_ema(df["close"], 200)
    cond = (ema8 < ema21) & (df["close"] < ema200)
    return cond

def signal_density_report(kline_map: dict, period_per_day: int = 6):
    """
    kline_map: {symbol: DataFrame(4h K线)}
    period_per_day: 4h K线一天6根
    返回信号密度统计
    """
    total_bars = 0
    total_hits = 0
    per_symbol = []

    for sym, df in kline_map.items():
        if len(df) < 200:
            continue
        cond = hard_condition(df)
        # 去掉EMA200预热期，避免前200根全是False拉低统计
        valid = cond.iloc[200:]
        hits = int(valid.sum())
        bars = len(valid)
        total_bars += bars
        total_hits += hits
        per_symbol.append({
            "symbol": sym,
            "bars": bars,
            "hits": hits,
            "hit_rate": hits / bars if bars else 0.0,
        })

    report = pd.DataFrame(per_symbol).sort_values("hit_rate", ascending=False)
    overall = total_hits / total_bars if total_bars else 0.0
    print(f"总K线数: {total_bars}, 命中数: {total_hits}, 整体满足率: {overall:.2%}")
    print(f"按每天{period_per_day}根4h K线折算，平均每日信号数: "
          f"{overall * period_per_day:.2f}")
    return report, overall

跑出来的结果：整体满足率 35%。折算下来，平均每天出一个合格做空信号。

24个标的、4个月、720根4h K线，这个样本量不算小，35%的满足率说明硬条件一点都不苛刻。所谓"最近没行情"，不成立。

那零开仓只可能来自一个地方：信号产生之后，到真正下单之前，中间某个环节把信号吃掉了。

二、把消费链路拆成环节，逐段统计过滤率

信号从产生到下单，中间通常有一串过滤器：复验、超卖过滤、风控、仓位检查、下单前校验。零开仓意味着整条链路的通过率是0，但0是结果，不是原因。要把每一段的过滤率单独打出来。

我当时的链路大致是这样：

  1. 4h周期扫描产生信号
  2. 延迟2小时后做一次复验
  3. RSI超卖过滤
  4. 风控与仓位检查
  5. 下单

先排除"看起来最像主因"的环节

直觉上，做空信号最容易卡在超卖过滤上——价格已经跌了很多，RSI很低，再去做空就是追空，很多策略会拦掉。

但统计结果打脸：RSI < 35 的超卖过滤只拦掉了 10.5%。剩下89.5%的信号都通过了这一关。这个环节不是主因，可以直接排除。

这就是为什么要逐段统计，而不是盯着一个可疑环节反复看。10.5%的过滤率解释不了100%的零开仓。

def stage_filter_stats(df: pd.DataFrame) -> dict:
    """
    统计各环节过滤率。假设 df 已带好各环节的布尔标记列。
    """
    stages = ["signal", "recheck_pass", "rsi_pass", "risk_pass"]
    stats = {}
    base = df[df["signal"]].copy()
    n_signal = len(base)
    stats["signal_count"] = n_signal

    for col in stages[1:]:
        passed = int(base[col].sum())
        stats[f"{col}_pass"] = passed
        stats[f"{col}_filter_rate"] = 1 - passed / n_signal if n_signal else 0.0

    return stats

真正的问题一：周期错配

链路里最隐蔽的一环是复验。

信号是在 4h 周期上产生的，但延迟2小时后的复验，用的是 15m 周期的 EMA8/EMA21。

这是典型的周期错配。4h 的 EMA8 反映的是约32小时的趋势，而 15m 的 EMA8 只反映2小时的价格波动。15m 均线在2小时的窗口里极其不稳定，一个正常的回抽就能让 EMA8 短暂上穿 EMA21，复验直接判不通过。

换句话说：信号在4h尺度上是成立的，但复验用15m尺度去确认，等于用放大镜看噪声。 复验大概率不通过，信号在第二关就被大量拦截。

修复很直接：复验周期必须与信号周期统一，都用4h。同一个尺度的确认才有意义。

真正的问题二：None 被当成 False 静默丢弃

第二个问题更致命，因为它不留痕迹。

复验函数在网络异常时返回 None（表示"无法确认"），但调用方是这样处理的：

# 错误写法：None 和 False 一起被当作"不成立"
def recheck_signal(symbol: str) -> bool | None:
    try:
        df = fetch_kline(symbol, period="4h", limit=300)
        if df is None or df.empty:
            return None
        ema8 = compute_ema(df["close"], 8).iloc[-1]
        ema21 = compute_ema(df["close"], 21).iloc[-1]
        return bool(ema8 < ema21)
    except Exception:
        return None  # 网络/数据异常，无法确认

def process_signal(symbol: str):
    ok = recheck_signal(symbol)
    if not ok:          # None 和 False 都进这里
        return          # 静默丢弃，无日志
    place_order(symbol)

not None 是 True，所以网络一抖动、数据一缺失，信号就被当成"复验不通过"直接丢掉，而且一行日志都没有。几个月零开仓，日志里干干净净，因为根本没有记录。

这里要区分两种语义：

  • False：明确确认不成立，应该拦截
  • None：无法确认（网络、数据、超时），不应该当作不成立，应该记录并重试或告警

修复后的写法：

import logging

logger = logging.getLogger("signal_chain")

def process_signal_fixed(symbol: str):
    ok = recheck_signal(symbol)

    if ok is None:
        # 无法确认：不拦截，记录并进入重试/告警
        logger.warning("recheck_unconfirmed symbol=%s action=retry", symbol)
        enqueue_retry(symbol)
        return

    if ok is False:
        # 明确不成立：拦截，但要留日志
        logger.info("recheck_rejected symbol=%s", symbol)
        return

    # 明确成立：继续后续链路
    logger.info("recheck_passed symbol=%s", symbol)
    place_order(symbol)

两个修复合起来：复验周期统一为4h，None 不再静默丢弃、只拦截 False。改完之后，信号开始正常走到下单环节。

三、这次排查沉淀下来的方法论

回头看，这个问题本身不难修，难的是定位。把方法固化下来，比修一个bug更有价值。

1. 先量化"信号供给"，再查"消费链路"

零开仓有两种可能：没有信号，或有信号但被吃掉。用离线数据先算出理论信号密度，直接把问题范围砍掉一半。35%的满足率一出来，方向就锁死在链路上了。

2. 每个环节的过滤率都要单独统计

不要盯着一个可疑环节反复看。RSI超卖过滤看起来最像主因，实际只拦10.5%。把链路每一段的过滤率打成一张表，主因自然浮出来——周期错配和None丢弃，都是靠这张表才被看见的。

3. 静默丢弃是排查的天敌

任何"拦截"动作都必须留日志，并且要区分"明确拦截"和"无法确认"。前者是策略行为，后者是故障信号。把两者混在一起处理，故障就被伪装成了策略的正常拒绝。

4. 周期一致性是硬约束

信号在哪个周期产生，确认就应该在哪个周期做。跨周期复验不是不可以，但必须是有意设计，而不是随手写了个15m的均线。

这次排查的核心不是某个函数写错了，而是没有把信号链路当成一个可观测的系统来对待。信号供给、各环节过滤率、None的语义，这三样只要有一样是可观测的，几个月的零开仓都不会发生。

把信号密度统计和链路过滤率统计做成常规监控，比事后排查划算得多。
