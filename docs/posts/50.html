从零搭建量化交易系统：50篇文章的总结与回顾

2026-10-20 系统运维

50篇文章写下来，这套量化交易系统从一行pip install开始，到现在跑在实盘环境里稳定运行了几个月。这一篇做个系统性回顾，把架构全貌、模块设计、踩过的坑和后续方向一次讲清楚。代码细节前面都展开过，这里只提炼方法论。

一、系统架构全貌

整套系统最终收敛成六个核心层，层与层之间通过明确的数据契约解耦：

┌─────────────────────────────────────────────┐
│  策略层 (Strategy)                            │
│  - 信号生成 / 仓位决策 / 风控钩子              │
├─────────────────────────────────────────────┤
│  组合层 (Portfolio)                           │
│  - 持仓管理 / 资金分配 / 再平衡                │
├─────────────────────────────────────────────┤
│  执行层 (Execution)                           │
│  - 订单路由 / 撮合对接 / 成交回报              │
├─────────────────────────────────────────────┤
│  风控层 (Risk)                                │
│  - 事前校验 / 事中监控 / 事后归因              │
├─────────────────────────────────────────────┤
│  数据层 (Data)                                │
│  - 行情采集 / 清洗 / 存储 / 复权               │
├─────────────────────────────────────────────┤
│  运维层 (Ops)                                 │
│  - 调度 / 日志 / 告警 / 状态持久化             │
└─────────────────────────────────────────────┘

关键设计原则只有一条：任何一层挂掉，其他层要能感知并安全降级。数据层断了，策略层收到的是"数据陈旧"信号而不是脏数据；执行层超时，风控层要能强制平掉异常敞口。

用配置驱动整个系统，是所有模块能拼起来的前提：

from dataclasses import dataclass, field
from typing import Dict, List

@dataclass
class SystemConfig:
    data: Dict = field(default_factory=lambda: {
        "source": "local",
        "bar_interval": "1m",
        "stale_threshold_sec": 120,
        "adjust": "qfq",
    })
    risk: Dict = field(default_factory=lambda: {
        "max_position_pct": 0.2,
        "max_drawdown_pct": 0.15,
        "max_order_notional": 1_000_000,
        "daily_loss_limit": 0.03,
    })
    execution: Dict = field(default_factory=lambda: {
        "order_timeout_sec": 5,
        "retry": 2,
        "mode": "paper",  # paper / live
    })
    ops: Dict = field(default_factory=lambda: {
        "log_level": "INFO",
        "alert_channel": "webhook",
        "state_backend": "sqlite",
    })

    def validate(self) -> List[str]:
        errors = []
        if self.risk["max_position_pct"] <= 0 or self.risk["max_position_pct"] > 1:
            errors.append("max_position_pct 必须在 (0, 1] 区间")
        if self.execution["mode"] not in ("paper", "live"):
            errors.append("execution.mode 非法")
        return errors

配置校验放在启动阶段，比运行到一半才发现参数越界要省事得多。

二、各模块关键设计总结

数据层：把"数据质量"当成一等公民

回测和实盘最大的差异往往不在策略，而在数据。数据层最终沉淀出三条铁律：

  1. 所有行情落库前先做完整性校验（时间戳单调、无重复、缺口标记），而不是在使用时临时判断；
  2. 复权因子单独存储，行情原始数据永远不动，复权在读取时计算；
  3. 数据陈旧检测前置到策略入口，超过阈值直接拒绝信号，而不是让策略拿着旧数据做决策。

策略层：策略只做一件事——产出目标仓位

早期版本里策略直接调下单接口，后来全部改成策略只输出"目标仓位向量"，由组合层统一算差额、拆订单。这个改动让回测和实盘共用同一套信号逻辑，也让风控有了统一的介入点。

from abc import ABC, abstractmethod
import pandas as pd

class BaseStrategy(ABC):
    @abstractmethod
    def generate_targets(self, bars: pd.DataFrame) -> pd.Series:
        """返回 index=symbol, value=目标权重，范围 [-1, 1]"""
        ...

class MovingAverageCross(BaseStrategy):
    def __init__(self, fast: int = 10, slow: int = 30):
        self.fast, self.slow = fast, slow

    def generate_targets(self, bars: pd.DataFrame) -> pd.Series:
        # bars: 多标的收盘价，columns=symbol
        fast_ma = bars.rolling(self.fast).mean()
        slow_ma = bars.rolling(self.slow).mean()
        signal = (fast_ma > slow_ma).astype(float)
        # 等权分配到有信号的标的
        counts = signal.sum(axis=1).replace(0, 1)
        return signal.div(counts, axis=0).iloc[-1]

执行层：幂等是第一要求

订单是整条链路里最容易出问题的地方——网络重试、接口超时、进程重启，都可能造成重复下单。执行层最终采用"客户端订单 ID + 状态机"的方案：每笔订单生成唯一 client_order_id，本地状态机记录 PENDING → SUBMITTED → PARTIAL → FILLED / CANCELLED / REJECTED，任何重试都先查状态再决定动作。

风控层：三层拦截

  • 事前：下单前校验名义金额、仓位上限、单日亏损；
  • 事中：定时扫描持仓，发现敞口超限或回撤触线直接生成减仓指令；
  • 事后：每日收盘归因，把盈亏拆到策略/标的/交易成本上。

运维层：状态必须可恢复

系统重启后要能"接着跑"，靠的是把持仓、挂单、当日已实现盈亏全部持久化。用 SQLite 足够，关键是每次状态变更和对应操作在同一事务语义内，避免出现"订单发了但状态没记"的幽灵单。

三、踩过的坑汇总

按杀伤力排序，这几个坑值得每个自己搭系统的人提前看：

  1. 回测前视偏差：用当日收盘价算信号又用当日收盘价成交，回测曲线漂亮得离谱。修正方式是信号基于 t 收盘生成，成交按 t+1 开盘价。
  2. 复权方式混用：数据层用后复权，回测代码里又手动乘了一次复权因子，收益直接翻倍。教训是复权只在一个地方做。
  3. 浮点仓位误差：0.1 + 0.2 != 0.3 导致持仓校验频繁误报。所有仓位比较统一用 abs(a - b) < 1e-8。
  4. 时间戳时区：行情源有的给 UTC 有的给本地时间，跨时区标的直接错位。全系统统一存 UTC，展示层再转。
  5. 重试风暴：接口超时后无退避地重试，把上游打挂。改为指数退避 + 熔断。
  6. 日志里泄露敏感信息：早期把完整请求体打进日志，包含密钥。日志脱敏要做在写入前。
  7. 进程无守护：半夜进程挂了没人知道。加心跳上报 + 告警是必须的，不能靠"每天早上看一眼"。

四、后续优化方向

系统能跑不代表跑得好，接下来几个方向按优先级排：

  • 执行质量评估：目前只记录成交价，缺少和 VWAP/TWAP 基准的对比，无法量化滑点成本；
  • 策略组合层：现在多策略是简单资金切分，缺少相关性约束和动态权重；
  • 回测引擎性能：向量化回测在标的数量上千后变慢，考虑引入事件驱动 + 增量计算；
  • 配置热更新：风控阈值目前改配置要重启，改成运行时可调；
  • 可观测性：加 Prometheus 指标，把延迟、成交率、拒单率做成看板。

五、给新手的建议

  • 先跑通最小闭环，再谈优化：一条数据 → 一个信号 → 一笔纸面成交 → 一条日志，这个闭环通了，系统骨架就立住了。
  • 回测和实盘共用代码路径，差异只允许出现在执行层的适配器里。两套代码是 bug 的温床。
  • 把日志和状态持久化放在第一天做，不是"以后再补"。排查问题时你会感谢当时的自己。
  • 风控先写，策略后写。没有风控的策略系统，实盘第一天就可能教你做人。
  • 别迷信回测曲线，重点看交易成本敏感性、参数稳定性、极端行情下的表现。
  • 小资金实盘验证，纸面交易和真金白银之间隔着流动性、滑点和心理，早发现早修。

50 篇下来，最大的体会是：量化系统 80% 的工作量在数据和运维，策略本身反而是相对轻的部分。把工程底座打牢，策略迭代才有意义。
