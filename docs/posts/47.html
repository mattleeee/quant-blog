JSON配置文件管理：原子读写与异常恢复

2026-10-17 系统运维

量化系统里，配置文件承载着策略参数、账户映射、风控阈值这类关键数据。一个写坏的 JSON 文件，轻则让程序启动失败，重则让策略用错误的参数跑一整天。这篇文章分享一套我在实盘项目里用了两年多的配置管理方案，核心解决四件事：原子写入、异常恢复、版本管理、热加载。

为什么直接 json.dump 会出问题

先看一段几乎所有人一开始都会写的代码：

import json

def save_config(path, config):
    with open(path, "w", encoding="utf-8") as f:
        json.dump(config, f, ensure_ascii=False, indent=2)

这段代码在 99% 的情况下没问题，问题出在剩下的 1%：

  1. 写入过程中进程被杀。open(path, "w") 会立刻把原文件截断为 0 字节，如果此时进程崩溃、机器断电、或者被 kill -9，你手里就只剩一个空文件或者半截 JSON。
  2. 并发写入。多个进程同时写同一个文件，内容会互相覆盖，最终落盘的可能是两个 JSON 交错的结果，解析必然失败。
  3. 磁盘满。写到一半 ENOSPC，文件同样是残缺的。

配置文件丢失的代价，在量化系统里往往不是"重写一遍"这么简单——如果你的持仓状态、参数快照存在里面，丢一次可能就要人工对账。

原子写入：tempfile + os.replace

解决思路是"先写临时文件，写完再原子替换"。os.replace 在 POSIX 系统上对应 rename(2)，是原子操作；在 Windows 上底层用 MoveFileEx，同样保证目标文件要么是旧的、要么是新的，不会出现中间态。

import json
import os
import tempfile
from pathlib import Path


def atomic_write_json(path, data, *, indent=2, fsync=True):
    """原子写入 JSON 文件。

    1. 在目标目录创建临时文件（同目录保证同一文件系统，rename 才是原子的）
    2. 写入并 flush + fsync，确保数据真正落盘
    3. os.replace 原子替换目标文件
    """
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)

    # 临时文件必须和目标文件在同一目录，否则跨文件系统的 rename 会退化为 copy
    fd, tmp_path = tempfile.mkstemp(
        dir=str(path.parent),
        prefix=f".{path.name}.",
        suffix=".tmp",
    )
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as f:
            json.dump(data, f, ensure_ascii=False, indent=indent)
            f.flush()
            if fsync:
                os.fsync(f.fileno())
        os.replace(tmp_path, path)
        if fsync:
            # 目录项本身也需要 fsync，否则极端断电场景下 rename 可能丢失
            dir_fd = os.open(str(path.parent), os.O_DIRECTORY)
            try:
                os.fsync(dir_fd)
            finally:
                os.close(dir_fd)
    except Exception:
        # 失败时清理临时文件，避免目录里堆积垃圾
        try:
            os.unlink(tmp_path)
        except FileNotFoundError:
            pass
        raise

几个容易踩的坑：

  • 临时文件必须放在目标目录。tempfile.mkstemp() 默认用 /tmp，如果 /tmp 和配置目录不在同一个文件系统，os.replace 会抛 OSError: [Errno 18] Invalid cross-device link。
  • fsync 不能省。flush() 只把数据从 Python 缓冲区推到内核页缓存，断电后仍会丢。fsync 才真正落盘。代价是慢，一次几毫秒，配置文件写入频率低，完全值得。
  • 目录也要 fsync。rename 修改的是目录项，某些文件系统（ext4 的 data=writeback 模式）下不 fsync 目录，断电后可能看到旧文件。

读取异常恢复：默认配置兜底

写完要防丢，读的时候要防坏。JSON 文件可能因为磁盘错误、外部程序误改、编码问题而损坏。读取时应该做到"坏文件不阻塞启动，但也不能静默吞掉"。

import logging
import shutil
from datetime import datetime

logger = logging.getLogger(__name__)


def load_json_safe(path, default=None, *, backup_broken=True):
    """安全读取 JSON，异常时返回 default。

    - 文件不存在：返回 default
    - JSON 解析失败：备份损坏文件，返回 default
    - 编码错误：同上
    """
    path = Path(path)
    if not path.exists():
        logger.info("配置文件 %s 不存在，使用默认配置", path)
        return default

    try:
        with path.open("r", encoding="utf-8") as f:
            return json.load(f)
    except (json.JSONDecodeError, UnicodeDecodeError) as e:
        logger.error("配置文件 %s 解析失败: %s", path, e)
        if backup_broken:
            ts = datetime.now().strftime("%Y%m%d_%H%M%S")
            broken = path.with_suffix(f"{path.suffix}.broken.{ts}")
            try:
                shutil.move(str(path), str(broken))
                logger.warning("损坏文件已备份至 %s", broken)
            except OSError as move_err:
                logger.error("备份损坏文件失败: %s", move_err)
        return default
    except OSError as e:
        logger.error("读取配置文件 %s 失败: %s", path, e)
        return default

这里有两个设计决策值得说明：

为什么备份而不是直接删？ 损坏的配置里可能还残留着部分有效信息，比如手工改坏了一个括号，但里面的参数是你调了很久的。备份出来人工看一眼，比直接覆盖强。

为什么返回 default 而不是抛异常？ 量化系统通常 7×24 运行，一个配置文件坏掉不应该让整个进程起不来。用默认配置启动、打一条 ERROR 日志、让监控告警，比直接 crash 更符合运维预期。当然，如果你的场景是"配置缺失必须人工介入"，那就在调用方判断 default is None 时主动抛异常。

版本管理：让配置可追溯

配置文件被改坏了，最常见的问题是"不知道改之前长什么样"。加一个轻量的版本字段和自动备份，能让回滚变成一行命令的事。

CONFIG_VERSION = 3


class ConfigManager:
    def __init__(self, path, defaults=None, *, max_backups=10):
        self.path = Path(path)
        self.defaults = defaults or {}
        self.max_backups = max_backups
        self._cache = None

    def _migrate(self, cfg):
        """把旧版本配置升级到当前版本。"""
        version = cfg.get("_version", 0)
        if version == CONFIG_VERSION:
            return cfg

        if version < 1:
            cfg.setdefault("risk", {})
        if version < 2:
            cfg["risk"].setdefault("max_position", 0.2)
        if version < 3:
            cfg.setdefault("log_level", "INFO")

        cfg["_version"] = CONFIG_VERSION
        logger.info("配置从 v%s 迁移到 v%s", version, CONFIG_VERSION)
        return cfg

    def load(self):
        raw = load_json_safe(self.path, default=None)
        if raw is None:
            raw = dict(self.defaults)
            raw["_version"] = CONFIG_VERSION
        cfg = self._migrate(raw)
        self._cache = cfg
        return cfg

    def save(self, cfg):
        self._backup()
        atomic_write_json(self.path, cfg)
        self._cache = cfg

    def _backup(self):
        if not self.path.exists():
            return
        ts = datetime.now().strftime("%Y%m%d_%H%M%S")
        backup = self.path.with_suffix(f"{self.path.suffix}.{ts}.bak")
        try:
            shutil.copy2(self.path, backup)
        except OSError as e:
            logger.warning("备份失败: %s", e)
            return
        self._prune_backups()

    def _prune_backups(self):
        pattern = f"{self.path.name}.*.bak"
        backups = sorted(self.path.parent.glob(pattern))
        for old in backups[:-self.max_backups]:
            try:
                old.unlink()
            except OSError:
                pass

版本管理的核心是 _version 字段加迁移函数。每次结构变更，递增 CONFIG_VERSION，在 _migrate 里补一段升级逻辑。这样老配置文件也能平滑升级，不需要人工改。

备份策略用"每次保存前 copy 一份 + 保留最近 N 份"，简单够用。别用 git 管理配置——配置文件里可能有敏感信息（API key、账户），塞进 git 容易出事故。

热加载：不重启更新配置

策略跑着跑着要调参数，重启进程代价太大。热加载的方案是：后台线程定期检查文件 mtime，发现变化就重新加载。

import threading
import time


class ConfigWatcher:
    def __init__(self, manager, interval=2.0, on_reload=None):
        self.manager = manager
        self.interval = interval
        self.on_reload = on_reload
        self._stop = threading.Event()
        self._thread = None
        self._last_mtime = 0.0

    def start(self):
        self._last_mtime = self._get_mtime()
        self._thread = threading.Thread(target=self._run, daemon=True)
        self._thread.start()

    def stop(self):
        self._stop.set()
        if self._thread:
            self._thread.join(timeout=self.interval + 1)

    def _get_mtime(self):
        try:
            return self.manager.path.stat().st_mtime
        except OSError:
            return 0.0

    def _run(self):
        while not self._stop.wait(self.interval):
            mtime = self._get_mtime()
            if mtime == self._last_mtime:
                continue
            self._last_mtime = mtime
            try:
                cfg = self.manager.load()
                logger.info("配置已热加载")
                if self.on_reload:
                    self.on_reload(cfg)
            except Exception as e:
                logger.exception("热加载失败，保留旧配置: %s", e)

几个注意点：

  • 用 mtime 判断变化，别用文件内容 hash。hash 每次都要读全文件，配置小无所谓，但如果配置里挂了大数据就不划算。mtime 的精度在大多数文件系统上足够。
  • 热加载失败要保留旧配置。load() 内部已经做了异常兜底，但 on_reload 回调里如果抛异常，不能污染当前状态。上面用 try/except 包住了。
  • 回调里不要做重活。热加载线程是守护线程，回调里如果做数据库迁移、重连之类的操作，会阻塞后续检测。重活丢到队列里异步处理。
  • 多进程场景要注意。上面的方案只适用于单进程。多进程要么用文件锁 + 版本号，要么直接上 etcd/consul 这类配置中心。单机量化系统用文件 + watcher 就够了。

串起来用

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)

    mgr = ConfigManager(
        "config/strategy.json",
        defaults={"risk": {"max_position": 0.2}, "log_level": "INFO"},
    )
    cfg = mgr.load()
    print("当前配置:", cfg)

    watcher = ConfigWatcher(mgr, interval=1.0,
                            on_reload=lambda c: print("重载:", c))
    watcher.start()

    try:
        time.sleep(30)
    finally:
        watcher.stop()

跑起来之后，手动改一下 config/strategy.json，一秒内就能看到重载日志。

小结

这套方案的核心就四点：

  1. 原子写入：tempfile.mkstemp 同目录建临时文件 → 写入 → fsync → os.replace → fsync 目录。
  2. 异常恢复：读取失败返回默认值，损坏文件自动备份，不阻塞启动。
  3. 版本管理：_version 字段 + 迁移函数 + 保存前备份 + 保留最近 N 份。
  4. 热加载：后台线程轮询 mtime，回调里做重活，失败保留旧配置。

代码量不大，但能省掉很多半夜起来修配置的麻烦。配置文件这种基础设施，值得多花半小时把它做扎实。
