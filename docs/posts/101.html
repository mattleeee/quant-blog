一个前视偏差bug，让我的回测从+1702%变成-50.7%

2026-11-14 量化回测

先说结论：我的EMA均线交叉双向策略回测跑出来 +1702.1%、DSR=1.000、p=0.0000，看起来是一个可以直接上实盘的"圣杯"。修复一个时序bug之后，同一份代码、同一个参数、同一个币池，变成 -50.7%、DSR=0.000、t=-2.93。

这不是参数过拟合，不是手续费没算，也不是滑点问题。是一个前视偏差（lookahead bias），藏在我自己写的回测引擎里，逐行看代码的时候每一行都"对"。

这篇文章把这个bug拆开讲：它长什么样、为什么难发现、什么测试能把它逼出来、以及我现在的防御清单。

一、策略和回测引擎的基本结构

策略很简单：EMA8 与 EMA21 的金叉/死叉，双向持仓。

  • 金叉（EMA8 从下方向上穿越 EMA21）→ 做多
  • 死叉（EMA8 从上方向下穿越 EMA21）→ 做空

K线周期 4 小时。回测引擎是逐K线循环的，核心结构大致是这样：

import pandas as pd
import numpy as np

def ema_cross_signals(df, fast=8, slow=21):
    df = df.copy()
    df["ema_fast"] = df["close"].ewm(span=fast, adjust=False).mean()
    df["ema_slow"] = df["close"].ewm(span=slow, adjust=False).mean()
    # 1 = 金叉做多, -1 = 死叉做空, 0 = 无新信号
    cross_up = (df["ema_fast"] > df["ema_slow"]) & \
               (df["ema_fast"].shift(1) <= df["ema_slow"].shift(1))
    cross_dn = (df["ema_fast"] < df["ema_slow"]) & \
               (df["ema_fast"].shift(1) >= df["ema_slow"].shift(1))
    df["signal"] = 0
    df.loc[cross_up, "signal"] = 1
    df.loc[cross_dn, "signal"] = -1
    return df

信号本身没问题。问题出在循环里怎么"消费"这个信号。

二、bug的具体形态

2.1 错误版本

我最初的逐K线循环是这样的（简化后保留关键逻辑）：

def backtest_buggy(df, fee=0.0005):
    df = ema_cross_signals(df)
    position = 0          # 当前持仓方向
    entry_price = 0.0
    equity = 1.0
    equity_curve = []

    for i in range(len(df)):
        row = df.iloc[i]

        # 有信号就按"当前这根K线"的开盘价成交
        if row["signal"] != 0 and row["signal"] != position:
            # 先平旧仓（按本根开盘价）
            if position != 0:
                ret = position * (row["open"] / entry_price - 1)
                equity *= (1 + ret - fee)
            # 再开新仓（按本根开盘价）
            position = row["signal"]
            entry_price = row["open"]

        equity_curve.append(equity)

    return pd.Series(equity_curve, index=df.index)

看起来完全合理：第 i 根K线出现信号，就用第 i 根K线的开盘价成交。逐行读，没有任何一行是错的。

但 row["signal"] 是怎么算出来的？它来自 cross_up，而 cross_up 比较的是 第 i 根的收盘价算出的 EMA 和 第 i-1 根的收盘价算出的 EMA。

也就是说：信号的判定依赖第 i 根K线的收盘价，成交却发生在第 i 根K线的开盘价。

2.2 时间线错位

把时间线画出来就清楚了。一根 4 小时K线，从 t_open 到 t_close：

t_open ────────────── 4小时 ────────────── t_close
   |                                          |
  成交发生在这里                          信号判定用这里的收盘价
  （第i根开盘）                          （第i根收盘算EMA）

成交时刻比信号判定时刻早了整整 4 小时。回测在 t_open 就"知道"了 t_close 才会产生的金叉结果。

而EMA金叉有一个统计特征：它经常发生在大阳线上——因为大阳线才能把快线快速推过慢线。于是"开盘到收盘"这段涨幅，在回测里被白送给了策略：开盘买入，收盘时这根大阳线已经涨完了，而回测的净值已经把这部分吃掉了。

2.3 正确版本

修复方式只有一句话：信号在第 i-1 根收盘确认，第 i 根开盘成交。

def backtest_fixed(df, fee=0.0005):
    df = ema_cross_signals(df)
    position = 0
    entry_price = 0.0
    equity = 1.0
    equity_curve = []

    for i in range(len(df)):
        row = df.iloc[i]

        # 用上一根K线已经确认的信号，在本根开盘执行
        prev_signal = df["signal"].iloc[i - 1] if i > 0 else 0

        if prev_signal != 0 and prev_signal != position:
            if position != 0:
                ret = position * (row["open"] / entry_price - 1)
                equity *= (1 + ret - fee)
            position = prev_signal
            entry_price = row["open"]

        # 净值按本根收盘价 mark-to-market
        if position != 0:
            unrealized = position * (row["close"] / entry_price - 1)
            equity_curve.append(equity * (1 + unrealized))
        else:
            equity_curve.append(equity)

    return pd.Series(equity_curve, index=df.index)

两段代码的区别只有一行：row["signal"] 换成了 df["signal"].iloc[i-1]。

结果：

版本 总收益 DSR p值 / t值
错误版（信号与成交同根） +1702.1% 1.000 p=0.0000
修复版（信号前移一根） -50.7% 0.000 t=-2.93

同一策略、同一参数、同一币池。1702% 和 -50.7% 之间，只隔了一根K线的时间差。

三、为什么这个bug极难被发现

3.1 每一行代码都"对"

回测引擎逐行审阅时，你会看到：

  • ema_cross_signals 用 shift(1) 做穿越判定，标准写法，没问题；
  • 循环里 signal != position 判断换仓，没问题；
  • 成交价用 row["open"]，这是"当根开盘价"，看起来是最保守、最不可能前视的写法；
  • 手续费扣了，滑点可以再加。

问题不在任何单行，而在两行之间的时间关系：信号的计算时点和成交时点不在同一根K线的同一端。这种错误只能靠"把时间轴摊平"才能看出来，靠读代码看不出来。

3.2 "用开盘价成交"反而制造了安全感

很多人以为前视偏差就是"用了未来价格"，所以只要成交价用开盘价、不用收盘价，就安全了。恰恰相反：成交价用当根开盘价 + 信号用当根收盘价，是前视偏差最经典的组合。开盘价比收盘价"更早"，两者放在同一根K线里，天然就是错的。

真正的判据不是"用了哪个价格"，而是成交时点必须晚于或等于信号判定时点。用当根开盘价成交是合法的，前提是信号在上一根收盘就已确认。

3.3 回测指标全部"配合"这个bug

错误版本给出的 DSR=1.000、p=0.0000，是统计上"太完美"的典型征兆。但人在看到 +1702% 的时候，第一反应是"策略有效"，而不是"数据泄漏"。DSR 和 p 值在这里不是验证工具，反而成了放大器——它们只告诉你"这个收益序列很显著"，不会告诉你"这个收益序列是怎么来的"。

四、什么测试能把它逼出来：实盘语义回放

真正让我定位到这个bug的，不是代码审查，是一个实盘语义回放测试。

思路很简单：写一个"如果我真的在实盘跑这个策略，每一根K线收盘时我会做什么决策"的模拟器，和回测引擎并行跑同一段历史数据，比较两者的成交记录。

def live_semantics_replay(df, fee=0.0005):
    """
    模拟实盘语义：每根K线收盘时才能看到该K线的收盘价，
    因此信号只能在收盘后确认，成交只能在下一根K线开盘执行。
    """
    df = ema_cross_signals(df)
    position = 0
    entry_price = 0.0
    equity = 1.0
    equity_curve = []
    pending_signal = 0   # 收盘后挂起、下一根开盘执行的信号

    for i in range(len(df)):
        row = df.iloc[i]

        # 开盘：执行上一根收盘时挂起的信号
        if pending_signal != 0 and pending_signal != position:
            if position != 0:
                ret = position * (row["open"] / entry_price - 1)
                equity *= (1 + ret - fee)
            position = pending_signal
            entry_price = row["open"]
        pending_signal = 0

        # 收盘：此时才看得到本根收盘价，产生信号，挂起到下一根
        if row["signal"] != 0 and row["signal"] != position:
            pending_signal = row["signal"]

        if position != 0:
            unrealized = position * (row["close"] / entry_price - 1)
            equity_curve.append(equity * (1 + unrealized))
        else:
            equity_curve.append(equity)

    return pd.Series(equity_curve, index=df.index)

把回测引擎和回放引擎的成交记录逐笔对比，矛盾立刻暴露：

  • 回放引擎（实盘语义）：只有微亏；
  • 原回测引擎：暴赚 +1702%。

同一个策略、同一段数据，两个引擎的净值曲线天差地别。当"实盘语义回放"和"回测"严重不一致时，几乎一定是回测里有前视偏差，而不是回放写错了——因为回放引擎的约束更严（信号必须等收盘），它没有能力"作弊"。

这个测试的价值在于：它不依赖你审查代码时能否想到时序问题，它直接用"实盘上物理上可能发生什么"来约束回测。凡是回测里做了实盘做不到的事，两条曲线就会分叉。

五、防御清单

我现在每个回测引擎上线前，都会过一遍这几条：

  1. 成交时点永远不能早于信号判定时点。 这是唯一一条硬规则。信号若用到第 i 根收盘价，成交最早只能是第 i+1 根开盘价（或第 i 根收盘价，如果引擎支持收盘成交）。用当根开盘价成交，信号必须来自第 i-1 根及更早。

  2. 把"信号列"和"成交列"在时间轴上对齐打印。 对任意一笔交易，打印 signal_bar_time 和 fill_bar_time，断言 fill_bar_time >= signal_bar_time。这一条断言能拦住绝大多数同类bug。

  3. 必跑实盘语义回放。 独立实现一个"收盘决策、下一根开盘执行"的模拟器，与回测引擎逐笔对比成交。两条净值曲线分叉即报警。

  4. 警惕"太完美"的统计量。 DSR=1.000、p=0.0000、夏普高得离谱，第一反应应该是查数据泄漏，而不是庆祝。先怀疑，再相信。

  5. 指标类信号统一走"确认后一根"约定。 EMA、RSI、MACD 这类由收盘价序列计算的指标，信号天然在收盘时点才成立。在引擎层面统一加一根延迟，比在每个策略里手动 shift 更不容易出错。

  6. 成交价用 open 不等于安全。 安全性来自时序关系，不来自价格字段的选择。这条我踩过，写在这里提醒自己。

写在最后

+1702% 到 -50.7%，差的不是策略，是一根K线的时间差。前视偏差最阴险的地方在于：它不会让代码报错，不会让指标异常，反而会让回测结果变得"更好看"。你越是想找到一个能跑的策略，越容易在"逐行都对"的代码里放过那个时序错位。

修复之后，这个EMA8/21双向策略的 t=-2.93 是一个显著的负期望——它不是一个能用的策略，但它是一个诚实的回测结果。对我来说，后者比前者值钱得多。
