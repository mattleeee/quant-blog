微信推送绑定失败排查：SQLite数据库清理方案

2026-10-11 系统运维

问题现象

上周给量化系统加了一个微信推送模块，用于把每日的实盘信号、持仓变动、风控告警推送到微信。方案用的是企业微信应用消息 + 自建绑定服务，整体架构不复杂：

  • im-service：负责微信扫码绑定、token 管理、消息转发
  • push-worker：从 Redis 队列消费消息，调用 im-service 的 HTTP 接口
  • SQLite：存储绑定关系、access_token、扫码会话状态

上线跑了几天都正常，直到某天早上收到告警：微信推送全部失败。登录服务器手动测试，发现扫码绑定时页面直接提示“连接失败，请稍后重试”。

这个报错很模糊，既不是“token 失效”，也不是“用户未绑定”，说明问题出在绑定流程本身，而不是消息通道。

排查过程

第一步：确认服务存活

先看进程和端口：

ps aux | grep im-service
ss -lntp | grep 8300

进程在，端口也监听正常。curl 本地健康检查接口返回 200：

curl -s http://127.0.0.1:8300/healthz
# {"status":"ok"}

服务没挂，问题在业务逻辑层。

第二步：看日志定位失败点

im-service 用的是 loguru，日志按天切割。直接 grep 关键字：

grep -i "bind" /var/log/im-service/app.log | tail -50

关键几行：

ERROR  bind_session_create failed: database is locked
ERROR  qrcode generate error: sqlite3.OperationalError: database is locked

database is locked——SQLite 的经典问题。说明有连接没有释放，或者有长事务卡住了写锁。

第三步：检查 SQLite 状态

先看数据库文件：

ls -lh /data/im-service/*.db*

输出：

-rw-r--r-- 1 root root 1.2G  im-service.db
-rw-r--r-- 1 root root  32K  im-service.db-shm
-rw-r--r-- 1 root root 4.1M  im-service.db-wal

im-service.db 已经 1.2G，而正常情况这个库应该只有几 MB。-wal 文件也有 4MB 没 checkpoint。基本可以确认：数据库被写爆了。

再看表大小：

sqlite3 /data/im-service/im-service.db "SELECT name, SUM(pgsize)/1024/1024 AS mb FROM dbstat GROUP BY name ORDER BY mb DESC LIMIT 10;"

结果：

bind_session|1080
access_token|45
bind_relation|3
...

bind_session 表占了 1GB。这张表本应只存临时的扫码会话，正常情况几秒到几分钟就过期删除。现在明显是清理逻辑失效了。

第四步：确认根因

查一下这张表的记录数和最早时间：

sqlite3 /data/im-service/im-service.db \
"SELECT COUNT(*), MIN(created_at), MAX(created_at) FROM bind_session;"

1284733|2024-11-03 09:12:33|2025-01-15 08:41:02

120 万条记录，从去年 11 月堆到现在。翻了代码，清理逻辑是这样的：

# 旧代码，有问题
def cleanup_expired_sessions():
    conn = sqlite3.connect(DB_PATH)
    conn.execute(
        "DELETE FROM bind_session WHERE expire_at < datetime('now')"
    )
    conn.commit()
    # 忘了 conn.close()

两个问题叠加：

  1. 连接未关闭：每次调用都泄漏一个连接，累积到一定数量后 SQLite 拿不到写锁
  2. 删除没有分批：120 万行一次性 DELETE，事务巨大，WAL 文件暴涨，进一步加剧锁竞争

扫码时创建新 session 需要写锁，拿不到就抛 database is locked，前端看到的就是“连接失败”。

解决方案

立即恢复：清理数据库文件

最直接的办法是把这几个文件移走，让服务重启后自动重建：

# 先停服务
systemctl stop im-service

# 备份而不是直接删，方便后续分析
mkdir -p /data/backup/$(date +%F)
mv /data/im-service/im-service.db     /data/backup/$(date +%F)/
mv /data/im-service/im-service.db-shm /data/backup/$(date +%F)/
mv /data/im-service/im-service.db-wal /data/backup/$(date +%F)/

# 重启，服务会自动建表
systemctl start im-service

注意：im-service.db 里除了 bind_session，还有 bind_relation（用户绑定关系）和 access_token。如果直接删，绑定关系会丢，所有用户需要重新扫码。

生产环境更稳妥的做法是只清 bind_session，保留另外两张表：

systemctl stop im-service

sqlite3 /data/im-service/im-service.db <<'SQL'
PRAGMA journal_mode=WAL;
DELETE FROM bind_session;
VACUUM;
SQL

systemctl start im-service

VACUUM 会重建整个数据库文件，把碎片空间真正释放回磁盘。1GB 的库执行完会缩回几 MB。执行期间会短暂锁库，所以必须先停服务。

修复清理逻辑

数据库清空只是止血，代码不改下次还会复发。重写清理函数：

import sqlite3
import logging
from contextlib import contextmanager

DB_PATH = "/data/im-service/im-service.db"
BATCH_SIZE = 5000

logger = logging.getLogger(__name__)


@contextmanager
def get_conn():
    """每次用完确保关闭，避免连接泄漏"""
    conn = sqlite3.connect(DB_PATH, timeout=10)
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA busy_timeout=5000")
    try:
        yield conn
    finally:
        conn.close()


def cleanup_expired_sessions() -> int:
    """分批删除过期 session，避免长事务"""
    total = 0
    while True:
        with get_conn() as conn:
            cur = conn.execute(
                """
                DELETE FROM bind_session
                WHERE rowid IN (
                    SELECT rowid FROM bind_session
                    WHERE expire_at < datetime('now', '-1 hour')
                    LIMIT ?
                )
                """,
                (BATCH_SIZE,),
            )
            conn.commit()
            deleted = cur.rowcount

        total += deleted
        if deleted < BATCH_SIZE:
            break

    logger.info("cleanup_expired_sessions done, deleted=%d", total)
    return total

关键改动：

  • contextmanager 保证连接一定关闭
  • busy_timeout 让写锁等待而不是立刻报错
  • 分批删除，每批 5000 行，事务短，WAL 不会暴涨
  • 保留 1 小时缓冲，避免边界情况误删正在使用的 session

加上定时任务

清理函数挂到 APScheduler 上，每 10 分钟跑一次：

from apscheduler.schedulers.background import BackgroundScheduler

scheduler = BackgroundScheduler(timezone="Asia/Shanghai")
scheduler.add_job(
    cleanup_expired_sessions,
    "interval",
    minutes=10,
    id="cleanup_bind_session",
    max_instances=1,      # 防止上一次没跑完又启动
    coalesce=True,        # 错过的任务合并成一次
)
scheduler.start()

max_instances=1 很重要。如果某次清理因为数据量大跑得慢，不加这个参数会并发启动多个清理任务，反而把锁搞死。

加监控

光靠日志不够，加两个 Prometheus 指标：

from prometheus_client import Gauge

db_size_mb = Gauge("im_db_size_mb", "SQLite file size in MB")
bind_session_rows = Gauge("im_bind_session_rows", "Rows in bind_session")


def report_metrics():
    import os
    size = os.path.getsize(DB_PATH) / 1024 / 1024
    db_size_mb.set(size)

    with get_conn() as conn:
        n = conn.execute("SELECT COUNT(*) FROM bind_session").fetchone()[0]
    bind_session_rows.set(n)

配上告警规则：im_db_size_mb > 200 或 im_bind_session_rows > 100000 就报警。这样在问题爆发前就能收到通知，而不是等用户反馈“连接失败”。

预防措施

这次踩的坑不复杂，但几个点值得记下来：

1. SQLite 适合小数据量，但要管好连接生命周期。 用 contextmanager 或连接池，绝不裸写 sqlite3.connect 然后忘记关闭。Python 的 sqlite3 不会自动回收连接，泄漏是静默的。

2. 所有 DELETE 都要考虑分批。 单表超过 10 万行就别一次性删了。LIMIT + 循环 是标准写法，代码多几行，稳定性差很多。

3. WAL 模式要配 busy_timeout。 默认 busy_timeout=0，拿不到锁立即报错。设成 5000ms 能让大部分瞬时竞争自动化解。

4. 临时表要有 TTL 机制。 bind_session 这种本质是缓存，写的时候就要想好怎么删。要么定时任务，要么写入时顺带清理，别指望“以后再说”。

5. 数据库文件大小纳入监控。 磁盘、连接数、QPS 都监控了，唯独忘了文件大小。对于 SQLite 这种单文件数据库，文件体积是最直观的健康指标。

6. 清理逻辑上线前先在生产数据上 dry-run。 用 SELECT COUNT(*) 跑一遍条件，看看会删多少行。这次如果提前跑一下，会发现 120 万行的删除量，自然会想到要分批。

修完之后跑了半个月，im-service.db 稳定在 5MB 左右，bind_session 表常年维持在几百行。扫码绑定再没出过问题。
