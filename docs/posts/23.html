Python请求频率控制：从sleep到令牌桶的演进

2026-09-22 Python自动化

做量化交易和自动化脚本，绕不开API请求频率控制。交易所接口有硬性限频，数据服务商按套餐限制QPS，爬虫目标站点更是随时可能封IP。控制不好频率，轻则请求失败，重则账号被封。

这篇文章梳理三种频率控制方案：sleep延迟、基于时间窗口的计数器、令牌桶算法。从最简单的开始，逐步演进到生产级方案。

方案一：time.sleep——最原始的做法

最直觉的做法是在每次请求后加一个固定延迟：

import time
import requests

def fetch_data(url):
    resp = requests.get(url)
    time.sleep(0.5)  # 每次请求后等0.5秒
    return resp.json()

# 循环调用
for i in range(10):
    data = fetch_data(f"https://api.example.com/ticker?page={i}")
    print(data)

这种方式简单粗暴，但问题很明显：

  • 效率低：如果API允许每秒5次请求，sleep(0.5)意味着你每秒只用了2次配额，浪费了60%的吞吐量
  • 不考虑实际耗时：如果请求本身耗时0.3秒，实际间隔是0.8秒，而不是0.5秒
  • 无法应对突发：所有请求被均匀拉平，无法在需要时快速连续请求

适用场景：单次脚本、请求量极小（几十次以内）、对时间不敏感的场景。超过这个范围就不合适了。

方案二：基于时间窗口的计数器

比sleep进一步，我们可以记录请求时间戳，动态计算需要等待多久：

import time
import requests
from collections import deque

class RateLimiter:
    """滑动窗口限流器：限制任意window秒内最多max_calls次请求"""

    def __init__(self, max_calls: int, window: float = 1.0):
        self.max_calls = max_calls
        self.window = window
        self.timestamps = deque()

    def acquire(self):
        now = time.monotonic()

        # 清除窗口外的记录
        while self.timestamps and now - self.timestamps[0] >= self.window:
            self.timestamps.popleft()

        # 如果窗口内已满，等待到最早那次请求过期
        if len(self.timestamps) >= self.max_calls:
            sleep_time = self.window - (now - self.timestamps[0])
            if sleep_time > 0:
                time.sleep(sleep_time)
            now = time.monotonic()
            # 再次清理
            while self.timestamps and now - self.timestamps[0] >= self.window:
                self.timestamps.popleft()

        self.timestamps.append(time.monotonic())

    def __enter__(self):
        self.acquire()
        return self

    def __exit__(self, *args):
        pass


# 使用示例：限制每秒最多3次请求
limiter = RateLimiter(max_calls=3, window=1.0)

for i in range(10):
    with limiter:
        resp = requests.get(f"https://api.example.com/data/{i}")
        print(f"Request {i}: {resp.status_code}")

这个方案比sleep好在哪里：

  1. 充分利用配额：允许在1秒内快速发3次，然后等待窗口滑动
  2. 精确控制：基于实际时间戳，不受请求耗时影响
  3. 滑动窗口：不是固定窗口（如每整秒重置），而是任意1秒内不超过N次

但仍然有问题：

  • 无法处理突发流量：如果业务需要短时间内发一批请求（比如批量下单），滑动窗口会强制排队
  • 线程安全问题：多线程环境下deque的操作需要加锁
  • 不够平滑：窗口边界处可能出现“前1秒末尾3次 + 后1秒开头3次 = 0.1秒内6次”的情况

适用场景：单线程脚本、对突发没有要求的定时任务、API限频规则是“N次/秒”的简单场景。

方案三：令牌桶算法

令牌桶（Token Bucket）是业界最常用的限流算法，Nginx、Guava RateLimiter、各种API网关都在用。

核心原理

想象一个桶，系统以固定速率往桶里放令牌（token）。每个请求需要从桶里取一个令牌才能执行。桶有容量上限，满了就丢弃新令牌。

关键特性：

  • 平均速率受控：令牌生成速率 = 长期平均请求速率
  • 允许突发：桶里积累的令牌可以一次性消耗，支持短时突发流量
  • 平滑限流：不会出现窗口算法的边界问题

参数： - rate：每秒生成多少令牌（即长期QPS上限） - capacity：桶容量（即允许的最大突发量）

Python实现

import time
import threading
import requests


class TokenBucket:
    """线程安全的令牌桶限流器"""

    def __init__(self, rate: float, capacity: int):
        """
        :param rate: 每秒生成的令牌数（QPS）
        :param capacity: 桶容量，允许的最大突发请求数
        """
        self.rate = rate
        self.capacity = capacity
        self.tokens = capacity  # 初始装满
        self.last_refill = time.monotonic()
        self._lock = threading.Lock()

    def _refill(self):
        """补充令牌"""
        now = time.monotonic()
        elapsed = now - self.last_refill
        new_tokens = elapsed * self.rate
        if new_tokens > 0:
            self.tokens = min(self.capacity, self.tokens + new_tokens)
            self.last_refill = now

    def acquire(self, tokens: int = 1, block: bool = True, timeout: float = None):
        """
        获取令牌
        :param tokens: 需要的令牌数
        :param block: 是否阻塞等待
        :param timeout: 最大等待时间（秒）
        :return: 是否成功获取
        """
        deadline = None if timeout is None else time.monotonic() + timeout

        while True:
            with self._lock:
                self._refill()
                if self.tokens >= tokens:
                    self.tokens -= tokens
                    return True

                if not block:
                    return False

                # 计算需要等待的时间
                deficit = tokens - self.tokens
                wait_time = deficit / self.rate

            if deadline is not None:
                remaining = deadline - time.monotonic()
                if remaining <= 0:
                    return False
                wait_time = min(wait_time, remaining)

            time.sleep(wait_time)

    def __enter__(self):
        self.acquire()
        return self

    def __exit__(self, *args):
        pass


# 使用示例
bucket = TokenBucket(rate=5, capacity=10)  # 平均5 QPS，允许突发10次

for i in range(20):
    with bucket:
        resp = requests.get(f"https://api.example.com/order/{i}")
        print(f"[{time.strftime('%H:%M:%S')}] Request {i}: {resp.status_code}")

实际效果

假设rate=5, capacity=10：

  • 空闲一段时间后，桶满（10个令牌），可以瞬间发10次请求
  • 之后令牌以每秒5个的速度补充，长期平均QPS稳定在5
  • 如果持续请求超过5 QPS，桶会逐渐见底，后续请求被限速

这正是量化交易中需要的：平时低频轮询，行情突变时可以短时间高频拉取数据。

支持不同权重的请求

有些API对不同接口有不同的频率权重（比如查询接口权重1，下单接口权重5）。令牌桶天然支持：

bucket = TokenBucket(rate=10, capacity=20)

# 普通查询，消耗1个令牌
bucket.acquire(tokens=1)

# 下单操作，消耗5个令牌
bucket.acquire(tokens=5)

非阻塞模式

在高频策略中，有时候宁可跳过也不等待：

bucket = TokenBucket(rate=3, capacity=5)

def try_fetch(url):
    if bucket.acquire(block=False):
        return requests.get(url).json()
    else:
        # 限流了，走降级逻辑
        return None

生产环境注意事项

1. 使用 monotonic 时钟

time.time()受系统时间调整影响（NTP同步、手动改时间），time.monotonic()单调递增，更适合做限流。上面的代码已经用了monotonic。

2. 多进程场景

令牌桶在单进程内有效。如果开了多个进程/容器，需要把状态放到Redis：

import redis
import time

class RedisTokenBucket:
    """基于Redis的分布式令牌桶，用Lua脚本保证原子性"""

    LUA_SCRIPT = """
    local key = KEYS[1]
    local rate = tonumber(ARGV[1])
    local capacity = tonumber(ARGV[2])
    local now = tonumber(ARGV[3])
    local requested = tonumber(ARGV[4])

    local bucket = redis.call('hmget', key, 'tokens', 'last_refill')
    local tokens = tonumber(bucket[1]) or capacity
    local last_refill = tonumber(bucket[2]) or now

    local elapsed = now - last_refill
    tokens = math.min(capacity, tokens + elapsed * rate)

    local allowed = 0
    if tokens >= requested then
        tokens = tokens - requested
        allowed = 1
    end

    redis.call('hmset', key, 'tokens', tokens, 'last_refill', now)
    redis.call('expire', key, math.ceil(capacity / rate) + 1)

    return allowed
    """

    def __init__(self, redis_client, key, rate, capacity):
        self.redis = redis_client
        self.key = key
        self.rate = rate
        self.capacity = capacity
        self.script = self.redis.register_script(self.LUA_SCRIPT)

    def acquire(self, tokens=1):
        now = time.time()
        result = self.script(
            keys=[self.key],
            args=[self.rate, self.capacity, now, tokens]
        )
        return bool(result)

3. 结合重试机制

限流器只负责控制发送速率，网络异常和API返回的错误码还需要重试逻辑配合：

import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

def create_session():
    session = requests.Session()
    retry = Retry(
        total=3,
        backoff_factor=0.5,
        status_forcelist=[429, 500, 502, 503],
        respect_retry_after_header=True,  # 尊重服务端的Retry-After
    )
    adapter = HTTPAdapter(max_retries=retry)
    session.mount("https://", adapter)
    return session

注意respect_retry_after_header=True，很多API在返回429时会带上Retry-After头告诉你等多久，这个信息比你自己猜要准确。

4. 动态调整速率

交易所的限频规则可能变化，或者你的账户VIP等级提升后配额增加。令牌桶的rate和capacity应该支持运行时调整：

class AdaptiveTokenBucket(TokenBucket):
    def update_rate(self, new_rate: float):
        with self._lock:
            self._refill()  # 先按旧速率结算
            self.rate = new_rate

选型建议

  • 写个一次性脚本抓几十条数据：time.sleep够了，别过度设计
  • 单线程定时任务，每分钟拉一次行情：滑动窗口计数器，简单可靠
  • 量化交易系统、多线程爬虫、需要处理突发的场景：令牌桶，这是标准答案
  • 分布式系统：Redis + Lua的令牌桶

令牌桶不是银弹，但它是目前工程实践中平衡了简单性、正确性和灵活性的最优解。理解它的原理，能帮你在面对具体限频需求时做出合理的参数选择。
