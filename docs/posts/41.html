Python项目网络环境应对：被墙API的替代方案与配置

2026-10-10 系统运维

做量化交易的朋友大概率遇到过这种情况：同一个脚本,访问某些交易所API一切正常,换一个就超时。最近我在一个多交易所套利项目里就碰到了——Gate.io直连毫无问题,但Binance和OKX的REST接口全部超时,WebSocket也连不上。

这篇文章记录一下完整的排查和应对过程,包括连通性检测、替代方案选型、直连配置和长期稳定性监控。代码都是实际项目里跑过的,可以直接拿去改。

一、先做网络连通性检测

遇到API超时,第一步不是急着挂代理,而是确认到底是DNS问题、TCP不通还是TLS握手失败。不同层的故障对应不同的解决方案。

1.1 分层检测脚本

import socket
import ssl
import time
import requests
from urllib.parse import urlparse

def check_dns(host: str) -> dict:
    """检测DNS解析"""
    try:
        start = time.time()
        infos = socket.getaddrinfo(host, 443, proto=socket.IPPROTO_TCP)
        ips = list({info[4][0] for info in infos})
        return {
            "ok": True,
            "ips": ips,
            "elapsed_ms": round((time.time() - start) * 1000, 2)
        }
    except Exception as e:
        return {"ok": False, "error": str(e)}


def check_tcp(host: str, port: int = 443, timeout: float = 5.0) -> dict:
    """检测TCP连接"""
    try:
        start = time.time()
        with socket.create_connection((host, port), timeout=timeout):
            return {
                "ok": True,
                "elapsed_ms": round((time.time() - start) * 1000, 2)
            }
    except Exception as e:
        return {"ok": False, "error": str(e)}


def check_tls(host: str, port: int = 443, timeout: float = 5.0) -> dict:
    """检测TLS握手"""
    ctx = ssl.create_default_context()
    try:
        start = time.time()
        with socket.create_connection((host, port), timeout=timeout) as sock:
            with ctx.wrap_socket(sock, server_hostname=host) as ssock:
                return {
                    "ok": True,
                    "tls_version": ssock.version(),
                    "elapsed_ms": round((time.time() - start) * 1000, 2)
                }
    except Exception as e:
        return {"ok": False, "error": str(e)}


def check_http(url: str, timeout: float = 8.0) -> dict:
    """检测完整HTTP请求"""
    try:
        start = time.time()
        r = requests.get(url, timeout=timeout)
        return {
            "ok": True,
            "status": r.status_code,
            "elapsed_ms": round((time.time() - start) * 1000, 2)
        }
    except Exception as e:
        return {"ok": False, "error": str(e)}


if __name__ == "__main__":
    targets = {
        "Gate.io":  "https://api.gateio.ws/api/v4/spot/time",
        "Binance":  "https://api.binance.com/api/v3/time",
        "OKX":      "https://www.okx.com/api/v5/public/time",
    }
    for name, url in targets.items():
        host = urlparse(url).hostname
        print(f"\n=== {name} ({host}) ===")
        print("DNS :", check_dns(host))
        print("TCP :", check_tcp(host))
        print("TLS :", check_tls(host))
        print("HTTP:", check_http(url))

跑一遍就能定位问题层级。我本地实测的结果:

交易所 DNS TCP TLS HTTP
Gate.io ✅ ✅ ✅ ✅ 200
Binance ✅ ❌ timeout - ❌
OKX ✅ ❌ timeout - ❌

DNS能解析出IP,但TCP连不上,这是典型的IP层被阻断。这种情况下改hosts、换DNS都没用,必须走代理或者找替代域名。

1.2 判断是否被墙的辅助信号

  • DNS返回的是真实IP(不是0.0.0.0或污染IP),但TCP握手超时 → 大概率IP封锁
  • TCP通但TLS握手被重置(ConnectionResetError) → SNI阻断
  • 只有HTTP层超时 → 可能是WAF或接口本身限流

二、API替代方案选择

确认被墙之后,有几条路可以走,按成本和稳定性排序:

2.1 方案对比

方案 成本 稳定性 适用场景
交易所备用域名 免费 中 临时应急
自建代理(VPS) 低 高 长期项目
商业代理服务 中 高 多地区需求
第三方数据聚合API 中高 中 只读行情
切换到直连可用的交易所 免费 高 策略允许时

2.2 备用域名

Binance和OKX都有一些面向不同地区的域名,比如 api1.binance.com、api-gcp.binance.com,OKX的 aws.okx.com。这些域名走的IP池不同,有时能绕过部分封锁,但不稳定,不能作为长期方案。

BINANCE_ENDPOINTS = [
    "https://api.binance.com",
    "https://api1.binance.com",
    "https://api2.binance.com",
    "https://api3.binance.com",
    "https://api-gcp.binance.com",
]

def pick_alive_endpoint(endpoints, path="/api/v3/time", timeout=3.0):
    for base in endpoints:
        try:
            r = requests.get(base + path, timeout=timeout)
            if r.status_code == 200:
                return base
        except Exception:
            continue
    return None

2.3 自建代理(推荐)

长期跑的策略,最省心的还是自建。一台海外VPS + 一个轻量HTTP/SOCKS5代理,成本每月几美元,稳定性远超公共代理。

如果只是HTTP API,直接在requests里指定代理即可:

PROXIES = {
    "http":  "http://user:pass@your-vps-ip:port",
    "https": "http://user:pass@your-vps-ip:port",
}

r = requests.get("https://api.binance.com/api/v3/time",
                 proxies=PROXIES, timeout=5)

WebSocket的话,websockets 库从8.0开始支持通过环境变量走代理:

export HTTPS_PROXY=http://user:pass@your-vps-ip:port
export HTTP_PROXY=http://user:pass@your-vps-ip:port

或者用 python-socks 显式配置:

import asyncio
import websockets
from python_socks.async_.asyncio import Proxy

async def connect_ws(url: str, proxy_url: str):
    proxy = Proxy.from_url(proxy_url)
    sock = await proxy.connect(dest_host="stream.binance.com", dest_port=443)
    return await websockets.connect(url, sock=sock)

async def main():
    ws = await connect_ws(
        "wss://stream.binance.com:9443/ws/btcusdt@trade",
        "socks5://user:pass@your-vps-ip:port"
    )
    async for msg in ws:
        print(msg[:100])

asyncio.run(main())

2.4 切换到直连可用的交易所

如果策略本身不依赖特定交易所,最干净的做法是直接用直连可用的。比如Gate.io在国内大部分网络环境下可以直连,这时候可以把行情源和下单通道都切过去,代理只作为灾备。

三、直连配置方法

即使主链路走代理,也建议保留一条直连通道作为fallback。下面是一个多通道自动切换的配置方案。

3.1 统一客户端封装

import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

class ExchangeClient:
    def __init__(self, name, base_urls, proxies=None, timeout=5.0):
        self.name = name
        self.base_urls = base_urls          # 多个候选域名
        self.proxies = proxies              # 可为None
        self.timeout = timeout
        self.active_base = None
        self.session = self._build_session()

    def _build_session(self):
        s = requests.Session()
        retry = Retry(
            total=2, backoff_factor=0.3,
            status_forcelist=[429, 500, 502, 503, 504],
            allowed_methods=["GET", "POST"],
        )
        adapter = HTTPAdapter(max_retries=retry, pool_connections=10, pool_maxsize=20)
        s.mount("https://", adapter)
        s.mount("http://", adapter)
        return s

    def _try_request(self, base, path, method="GET", **kwargs):
        url = base + path
        kwargs.setdefault("timeout", self.timeout)
        if self.proxies:
            kwargs["proxies"] = self.proxies
        return self.session.request(method, url, **kwargs)

    def request(self, path, method="GET", **kwargs):
        # 优先用上次成功的base
        candidates = []
        if self.active_base:
            candidates.append(self.active_base)
        candidates += [b for b in self.base_urls if b != self.active_base]

        last_err = None
        for base in candidates:
            try:
                r = self._try_request(base, path, method, **kwargs)
                if r.status_code < 500:
                    self.active_base = base
                    return r
            except Exception as e:
                last_err = e
                continue
        raise RuntimeError(f"{self.name} all endpoints failed: {last_err}")

3.2 使用示例

gate = ExchangeClient(
    "Gate.io",
    base_urls=["https://api.gateio.ws"],
    proxies=None,  # 直连
)

binance = ExchangeClient(
    "Binance",
    base_urls=[
        "https://api.binance.com",
        "https://api1.binance.com",
        "https://api-gcp.binance.com",
    ],
    proxies={"https": "http://user:pass@vps:port"},
)

r = gate.request("/api/v4/spot/time")
print("Gate:", r.json())

r = binance.request("/api/v3/time")
print("Binance:", r.json())

这个封装的核心思路是:每个交易所维护一组候选域名 + 一个可选代理,请求时按顺序尝试,成功后记住活跃域名。这样即便某条线路临时挂掉,也能自动漂移到可用的通道。

3.3 环境变量集中管理

不要把代理地址硬编码在代码里,用环境变量或配置文件:

import os

PROXY = os.getenv("EXCHANGE_PROXY")  # http://user:pass@host:port
PROXIES = {"http": PROXY, "https": PROXY} if PROXY else None

配合 .env 文件:

EXCHANGE_PROXY=http://user:pass@your-vps:port

四、稳定性监控

代理链路和直连链路都需要持续监控,不然某天半夜断了,策略直接停摆。

4.1 周期性探测

import time
import logging
from datetime import datetime

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s"
)

def probe(client: ExchangeClient, path: str, interval: int = 30):
    while True:
        start = time.time()
        try:
            r = client.request(path)
            latency = round((time.time() - start) * 1000, 2)
            logging.info(
                f"{client.name} OK | base={client.active_base} "
                f"| status={r.status_code} | {latency}ms"
            )
        except Exception as e:
            logging.error(f"{client.name} FAIL | {e}")
        time.sleep(interval)

4.2 失败率统计与告警

光打日志不够,得量化。用一个滑动窗口统计最近N次请求的成功率,低于阈值就告警:

from collections import deque

class HealthTracker:
    def __init__(self, window=20, fail_threshold=0.3):
        self.window = deque(maxlen=window)
        self.fail_threshold = fail_threshold

    def record(self, ok: bool):
        self.window.append(1 if ok else 0)

    @property
    def fail_rate(self) -> float:
        if not self.window:
            return 0.0
        return 1 - sum(self.window) / len(self.window)

    def should_alert(self) -> bool:
        return len(self.window) == self.window.maxlen and \
               self.fail_rate >= self.fail_threshold

配合告警通道(企业微信/Telegram/邮件)接入即可。我一般用Telegram Bot,几行代码搞定:

def send_alert(token, chat_id, text):
    url = f"https://api.telegram.org/bot{token}/sendMessage"
    requests.post(url, json={"chat_id": chat_id, "text": text}, timeout=5)

4.3 探测与业务分离

监控线程和交易主逻辑要分开跑,避免探测阻塞下单。用 threading 或 asyncio 都可以:

import threading

def start_monitor(clients):
    for name, (client, path) in clients.items():
        t = threading.Thread(
            target=probe, args=(client, path),
            daemon=True, name=f"probe-{name}"
        )
        t.start()

守护线程随主进程退出,不会影响正常关闭。

五、几个实践中的坑

  1. 代理超时设置要短。代理本身挂了的话,默认超时会拖很久,建议 timeout=(3, 5) 分别控制连接和读取超时。

  2. WebSocket重连要带退避。被墙环境下WS断线频繁,指数退避(1s、2s、4s、8s,上限60s)比固定间隔靠谱。

  3. 不要在请求里混用代理和直连。有些库会读环境变量 HTTP_PROXY,导致你代码里传了 proxies=None 也没用。必要时用 session.trust_env = False 关掉。

  4. 时钟同步。走代理后延迟增加,签名接口对时间戳敏感,记得定期NTP同步,或者用服务器返回的时间校正本地时间偏移。

  5. 备用域名定期更新。交易所域名策略会变,把候选列表做成可配置项,别写死。

小结

应对被墙API的核心思路是:分层检测定位问题 → 多通道冗余 → 自动切换 → 持续监控。代码层面,一个统一的客户端封装 + 健康追踪器就能覆盖大部分场景。不要指望单一方案永远有效,把切换逻辑做进代码里,才是长期稳定的关键。
