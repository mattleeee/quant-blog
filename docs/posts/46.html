推送优先级设计：为什么MA信号推送要提前执行

2026-10-16 系统运维

问题背景

我们的量化交易系统每天盘后需要跑一批定时任务：行情数据同步、持仓更新、MA信号计算、风险检查、报表生成、消息推送。最初的实现很"自然"——按业务逻辑顺序串行执行，最后统一推送所有通知。

这个设计在大多数时候没问题。但当某个模块超时的时候，问题就暴露了。

一次真实的延迟事故

某天收盘后，数据同步模块因为上游接口响应慢，卡了将近 8 分钟。等它跑完，后面的 MA 信号计算、推送全部顺延。等用户收到 MA 金叉信号推送时，已经过去了 12 分钟。

对于日线级别的策略来说，12 分钟不算致命。但问题在于：MA 信号的计算本身只花了 0.3 秒，它被延迟完全是因为排在了慢模块后面。

这就是典型的"优先级倒置"——快且重要的任务，被慢且不紧急的任务阻塞了。

优化前的执行流程

先看原始代码结构：

import time
import logging
from datetime import datetime

logger = logging.getLogger(__name__)


def sync_market_data():
    """同步行情数据，可能因上游接口慢而超时"""
    time.sleep(2)  # 模拟耗时
    logger.info("行情数据同步完成")
    return {"000001": {"close": 10.5}}


def update_positions():
    """更新持仓信息"""
    time.sleep(0.5)
    logger.info("持仓更新完成")
    return {"000001": 1000}


def calc_ma_signal(market_data):
    """计算MA信号，本身很快"""
    time.sleep(0.3)
    signal = {"code": "000001", "type": "MA_GOLDEN_CROSS", "period": "MA5/MA20"}
    logger.info(f"MA信号计算完成: {signal}")
    return signal


def risk_check():
    """风险检查，可能耗时较长"""
    time.sleep(3)
    logger.info("风险检查完成")
    return True


def generate_report():
    """生成报表"""
    time.sleep(1.5)
    logger.info("报表生成完成")
    return "report.xlsx"


def push_all_notifications(signal, report):
    """统一推送"""
    time.sleep(0.2)
    logger.info(f"推送MA信号: {signal}")
    logger.info(f"推送报表: {report}")


def run_daily_task_v1():
    """优化前的串行流程"""
    start = time.time()
    logger.info("=== 开始每日任务 v1 ===")

    market_data = sync_market_data()          # 2s
    positions = update_positions()             # 0.5s
    signal = calc_ma_signal(market_data)       # 0.3s —— 信号在这里就算好了
    risk_check()                               # 3s
    report = generate_report()                 # 1.5s
    push_all_notifications(signal, report)     # 0.2s —— 但推送要等到最后

    elapsed = time.time() - start
    logger.info(f"=== 任务完成，总耗时 {elapsed:.2f}s ===")
    return elapsed


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO, format="%(asctime)s %(message)s")
    run_daily_task_v1()

MA 信号在 2.8 秒时就算好了，但推送发生在 7.3 秒。中间 4.5 秒全是等待。如果 risk_check 或 generate_report 超时，延迟会被进一步放大。

优化思路：按优先级重排执行顺序

核心原则只有一条：高优先级、低耗时的任务，尽早执行并立即推送，不要和其他任务捆绑。

具体到我们的场景：

任务 耗时 时效性要求 优先级
MA信号计算+推送 低 高 P0
持仓更新 低 中 P1
行情同步 中 中 P1
风险检查 高 低 P2
报表生成 高 低 P2

MA 信号是用户最关心的、时效性最强的通知，而且计算成本极低。它应该走"快速通道"——算完就推，不等其他模块。

优化后的执行流程

def push_ma_signal(signal):
    """独立的MA信号推送通道"""
    time.sleep(0.1)
    logger.info(f"[P0推送] MA信号: {signal}")


def run_daily_task_v2():
    """优化后的流程：P0任务优先执行并立即推送"""
    start = time.time()
    logger.info("=== 开始每日任务 v2 ===")

    # --- P0: 快速通道，算完立即推送 ---
    market_data = sync_market_data()          # 2s
    positions = update_positions()             # 0.5s
    signal = calc_ma_signal(market_data)       # 0.3s
    push_ma_signal(signal)                     # 0.1s —— 立即推送，不等后续模块

    # --- P2: 慢任务，即使超时也不影响P0 ---
    risk_check()                               # 3s
    report = generate_report()                 # 1.5s
    push_report(report)                        # 0.1s

    elapsed = time.time() - start
    logger.info(f"=== 任务完成，总耗时 {elapsed:.2f}s ===")
    return elapsed


def push_report(report):
    time.sleep(0.1)
    logger.info(f"[P2推送] 报表: {report}")

持仓更新完成
MA信号计算完成: {'code': '000001', 'type': 'MA_GOLDEN_CROSS', 'period': 'MA5/MA20'}
[P0推送] MA信号: {'code': '000001', 'type': 'MA_GOLDEN_CROSS', 'period': 'MA5/MA20'}

报表生成完成
[P2推送] 报表: report.xlsx

总耗时没变，但 MA 信号推送从第 7.3 秒提前到了第 2.9 秒。用户提前 4.4 秒收到关键通知。

更重要的是容错性：如果 risk_check 超时 30 秒，v1 的推送会延迟 30 秒，v2 的 MA 推送完全不受影响。

进一步：用超时隔离保护 P0

上面的方案解决了"顺序"问题，但如果 P0 之前的模块（行情同步、持仓更新）本身超时呢？需要给它们加上超时控制。

import concurrent.futures


def run_with_timeout(func, timeout_sec, *args, **kwargs):
    """带超时保护的执行器"""
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
        future = executor.submit(func, *args, **kwargs)
        try:
            return future.result(timeout=timeout_sec)
        except concurrent.futures.TimeoutError:
            logger.warning(f"{func.__name__} 超时({timeout_sec}s)，跳过")
            return None


def run_daily_task_v3():
    """v3: 增加超时隔离"""
    start = time.time()
    logger.info("=== 开始每日任务 v3 ===")

    # P0 前置依赖，带超时保护
    market_data = run_with_timeout(sync_market_data, 5)
    if market_data is None:
        logger.error("行情数据获取失败，MA信号跳过")
        return

    positions = run_with_timeout(update_positions, 3)

    # P0: 计算并立即推送
    signal = calc_ma_signal(market_data)
    if signal:
        push_ma_signal(signal)

    # P2: 慢任务独立执行
    run_with_timeout(risk_check, 10)
    report = run_with_timeout(generate_report, 15)
    if report:
        push_report(report)

    elapsed = time.time() - start
    logger.info(f"=== 任务完成，总耗时 {elapsed:.2f}s ===")

优先级设计原则总结

从这次优化中提炼出几条可复用的原则：

1. 按"时效性 × 耗时"排序，而非按业务逻辑

业务逻辑上的顺序（先同步→再计算→再检查→最后推送）不等于执行顺序。执行顺序应该按优先级排：时效性高 + 耗时低的任务排最前，且算完立即推送。

2. 推送与计算绑定，不要集中推送

统一推送是个反模式。它把不同优先级的通知耦合在一起，任何一个模块慢都会拖累所有推送。正确做法是：谁产生信号，谁负责推送，算完就推。

3. 用超时隔离切断故障传播

P0 任务的前置依赖必须加超时。上游慢不能成为下游延迟的理由——超时后走降级逻辑（跳过、用缓存数据、发告警），而不是无限等待。

4. 监控推送延迟，而不只是任务总耗时

总耗时 7.5 秒在 v1 和 v2 里是一样的，但用户体验完全不同。需要单独埋点监控 "信号产生时间 → 推送到达时间" 这个指标，它才是真正反映推送时效的 KPI。

def push_with_latency_tracking(signal, signal_time):
    """记录推送延迟"""
    push_ma_signal(signal)
    latency = time.time() - signal_time
    logger.info(f"推送延迟: {latency:.3f}s")
    # 这里可以接入监控系统，超过阈值告警
    if latency > 2.0:
        logger.warning(f"推送延迟过高: {latency:.3f}s")

小结

推送优先级设计的本质是解耦：把高时效性的通知从低时效性的批处理流程中剥离出来，让它们独立、尽早、带超时保护地执行。

改动量很小——无非是调整了几行代码的顺序，加了一个独立的推送函数。但收益是实打实的：关键信号推送时间从 7.3 秒降到 2.9 秒，且在后续模块超时时依然稳定。

如果你也在做类似的定时任务系统，建议检查一下：你最关心的那个通知，是不是被排在了最后？
