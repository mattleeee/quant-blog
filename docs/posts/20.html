深信服安全软件拦截子进程的排查与解决方案

2026-08-22 Python自动化

在量化交易和自动化运维中，subprocess 调用是家常便饭——启动一个数据同步脚本、调用外部行情接口、或者拉起一个辅助进程。但最近在部署一套定时任务时，遇到了一个极其隐蔽的问题：Python 脚本中的 subprocess 调用被深信服（Sangfor）安全软件静默拦截，导致子进程无响应，主进程卡死。

这篇文章记录完整的排查过程、根因分析以及可落地的解决方案，希望能给同样被企业安全软件“折磨”的自动化工程师一些参考。

问题现象

环境背景：

  • Windows Server 2019
  • Python 3.9（64位）
  • 深信服 aTrust VPN 客户端 + Sangfor EDR 终端安全软件
  • 脚本通过 Windows 计划任务定时运行

现象描述：

  1. 主脚本运行正常，日志输出到 subprocess.Popen 调用处后停止。
  2. 子进程（例如 ping、curl、或另一个 Python 脚本）没有任何输出，也没有报错。
  3. 主进程挂起，直到超时或手动 kill。
  4. 手动在命令行执行同样的子进程命令，一切正常。
  5. 在无深信服软件的环境下测试，脚本运行完全正常。

初步排查

1. 确认 subprocess 调用方式

先看一段典型的触发问题的代码：

import subprocess
import sys

def run_command(cmd, timeout=30):
    """
    运行外部命令并捕获输出
    """
    try:
        proc = subprocess.Popen(
            cmd,
            shell=True,
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            text=True,
            encoding='utf-8',
            errors='replace'
        )
        stdout, stderr = proc.communicate(timeout=timeout)
        return proc.returncode, stdout, stderr
    except subprocess.TimeoutExpired as e:
        proc.kill()
        raise RuntimeError(f"命令执行超时: {cmd}") from e
    except Exception as e:
        raise RuntimeError(f"命令执行失败: {cmd}, error: {e}") from e

if __name__ == "__main__":
    # 测试命令
    code, out, err = run_command("ping 127.0.0.1 -n 3")
    print(f"Return code: {code}")
    print(f"STDOUT: {out}")
    print(f"STDERR: {err}")

这段代码在标准环境下运行没有任何问题，但在安装了深信服安全软件的机器上，运行到 proc.communicate() 时直接卡死，直到超时。

2. 检查进程状态

使用 tasklist 和 wmic 查看进程状态：

tasklist | findstr "ping"
wmic process where "name='ping.exe'" get ProcessId,ParentProcessId,CommandLine

发现子进程 ping.exe 确实被创建了，但状态一直处于“挂起”，CPU 和内存占用极低，像是被“冻结”了。

3. 尝试不同调用方式

为了排除 Python 代码本身的问题，我测试了多种调用方式：

# 方式1: shell=False
proc = subprocess.Popen(["ping", "127.0.0.1", "-n", "3"], 
                        stdout=subprocess.PIPE, stderr=subprocess.PIPE)

# 方式2: 使用 subprocess.run
result = subprocess.run(["ping", "127.0.0.1", "-n", "3"], 
                        capture_output=True, timeout=30)

# 方式3: 使用 os.system
os.system("ping 127.0.0.1 -n 3")

结果：全部卡死。说明问题不在 subprocess 的具体调用方式，而是系统层面的拦截。

4. 检查深信服软件日志

打开深信服 EDR 控制台，查看终端日志。在“行为检测”或“安全事件”中发现了关键线索：

  • 事件类型：进程创建拦截
  • 目标进程：ping.exe
  • 父进程：python.exe
  • 拦截原因：命中“敏感操作防护”策略

原来，深信服安全软件默认启用了“进程创建防护”功能，对某些系统命令（如 ping、cmd、powershell 等）的调用进行监控，当检测到 Python 脚本尝试创建子进程时，会先挂起子进程，等待用户或策略确认——但在无人值守的自动化场景下，这个“等待”永远不会结束。

根因分析

深信服安全软件（特别是 EDR 和 aTrust 联动时）的“主机安全防护”模块，会拦截以下几类行为：

  1. 敏感系统命令调用：ping、net、tasklist、reg 等。
  2. 脚本解释器调用：cmd.exe、powershell.exe、wscript.exe 等。
  3. 非白名单程序的子进程创建：特别是由 python.exe 或 java.exe 等解释器发起的。

这种拦截在交互式命令行中不会触发（因为用户在场，可以弹窗确认），但在计划任务、服务、或无人值守脚本中，弹窗无法显示，导致子进程永久挂起。

解决方案

方案一：临时绕过（测试用）

在深信服 EDR 控制台或客户端中，将 Python 解释器（python.exe）和常用命令加入“信任列表”或“白名单”。这是最快的临时方案，但需要管理员权限。

# 如果无法修改安全策略，可以在代码层面做一些规避
# 注意：这种方法不推荐用于生产环境，仅用于应急测试

import subprocess
import os

# 通过 cmd /c 调用，部分情况下可以绕过（但可能被更严格的策略拦截）
result = subprocess.run(
    ["cmd.exe", "/c", "ping 127.0.0.1 -n 3"],
    capture_output=True,
    timeout=30
)

方案二：使用 shell=False 并避免敏感命令

如果业务允许，尽量使用 shell=False，并避免直接调用 ping、cmd 等敏感命令。例如，用 Python 原生的 socket 模块替代 ping：

import socket

def check_host(host, port=80, timeout=3):
    """
    使用 socket 检测主机连通性，替代 ping 命令
    """
    try:
        sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        sock.settimeout(timeout)
        result = sock.connect_ex((host, port))
        sock.close()
        return result == 0
    except Exception as e:
        print(f"连接失败: {e}")
        return False

if __name__ == "__main__":
    print(f"百度连通性: {check_host('www.baidu.com', 80)}")

方案三：与 IT 部门沟通（推荐）

最根本的解决方案是让 IT 部门调整安全策略。以下是我整理的一份沟通模板，可以直接发给 IT 管理员：

**申请内容**：为 Python 自动化脚本添加进程白名单

**背景**：公司量化交易系统需要在 Windows 服务器上运行 Python 脚本，
需要调用外部命令（如 ping、curl、git 等）完成数据同步和健康检查。

**当前问题**：深信服 EDR 安全策略拦截了 Python 发起的子进程调用，
导致脚本在无人值守场景下挂起，影响生产任务。

**申请白名单**：
- 进程路径：C:\Python39\python.exe
- 允许行为：创建子进程（ping.exe, curl.exe, git.exe 等）
- 适用范围：仅限指定服务器（IP: 192.168.x.x）

**业务影响**：若无法调整，将导致每日行情数据无法同步，影响量化策略运行。

方案四：使用 Windows 计划任务的替代方案

如果安全策略无法调整，可以考虑绕过 subprocess，改用 Windows 计划任务来运行外部命令：

import subprocess

def run_scheduled_task(task_name, command):
    """
    创建并运行 Windows 计划任务
    """
    # 创建计划任务
    create_cmd = (
        f'schtasks /Create /TN "{task_name}" /TR "{command}" '
        f'/SC ONCE /ST 00:00 /F'
    )
    subprocess.run(create_cmd, shell=True, timeout=10)

    # 运行计划任务
    run_cmd = f'schtasks /Run /TN "{task_name}"'
    result = subprocess.run(run_cmd, shell=True, timeout=10)
    return result.returncode

# 示例：通过计划任务运行 ping
run_scheduled_task("PingTask", "ping 127.0.0.1 -n 3")

这种方法将子进程的执行权交给 Windows 计划任务服务，而不是由 Python 直接创建，可以在一定程度上规避安全软件的拦截。

最终方案与经验总结

经过与 IT 部门的多轮沟通，最终采用了以下组合方案：

  1. 短期：将 Python 解释器和常用工具加入信任列表。
  2. 长期：修改业务代码，使用 Python 原生库替代系统命令（如 socket 替代 ping，requests 替代 curl）。
  3. 架构调整：将高频外部调用封装为独立的 Windows 服务，由服务管理器统一调度。

经验总结：

  • 在部署自动化脚本到生产环境前，先在目标机器上做一次完整的 smoke test，特别是涉及 subprocess 的调用。
  • 企业安全软件（深信服、奇安信、360 等）的“进程防护”功能在无人值守场景下极易引发问题，务必提前排查。
  • 写代码时尽量减少对系统命令的依赖，能用 Python 原生库解决的就不要调用外部程序。
  • 与 IT 部门沟通时，明确给出业务影响和替代方案，而不是单纯抱怨，这样更容易获得支持。
