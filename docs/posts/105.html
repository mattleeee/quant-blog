死叉事件漏检死锁：为什么满仓之后就再也不开新仓了

2026-11-18 量化风控

先描述一个真实踩过的坑。趋势跟随模拟盘，平仓逻辑写得很直白：

检测到 EMA 死叉交叉事件，当根 K 线就平多。

回测跑得漂漂亮亮，实盘挂上去头几天也正常。然后某一天开始,系统不再开任何新仓。查日志,没有报错,没有异常,持仓检查、信号计算、下单流程全部显示"正常"。账户里就静静躺着 3 个仓位——正好是仓位上限——然后永远不再动。

这就是典型的事件驱动死锁。下面拆开讲。

根因：事件会漏，状态不会

交叉是一个瞬时事件

EMA 死叉不是一种"状态"，而是两条线在某一根 K 线上发生的穿越动作。用代码表达通常是这样的判定：

def is_dead_cross(ema_fast_prev, ema_slow_prev, ema_fast_now, ema_slow_now):
    # 上一根快线还在慢线上方，这一根跌到下方 —— 穿越发生
    return ema_fast_prev >= ema_slow_prev and ema_fast_now < ema_slow_now

注意这个判定依赖相邻两根的 EMA 相对位置。它只在穿越发生的那一根 K 线上为 True，之后所有 K 线上，只要快线一直待在慢线下方，这个函数永远返回 False——因为"上一根快线在慢线上方"这个前提再也不会成立。

漏检是怎么发生的

K 线接口偶发失败在实盘里太常见了。这个系统的容错设计是：连续 3 次失败才判定行情下线并强平。问题在于——间歇性失败会把失败计数清零。

于是出现了这样的时间线：

  1. 死叉在 T 根 K 线发生。
  2. T 根这一轮任务,行情接口恰好失败,任务没拿到这根 K 线,平仓检查没跑成。
  3. 下一轮任务成功,失败计数清零,但 T 根已经过去了。
  4. T+1 根开始,EMA 已经稳定空头排列,is_dead_cross 永远返回 False。
  5. 持仓永久卡死。

失败计数清零这个设计本身没错（它防的是"偶发失败误强平"），但它和"事件驱动平仓"组合在一起，就制造了一个事件窗口被跳过的漏洞。

死锁的闭环

单个仓位卡死还不够致命。真正让它变成"系统停摆"的是仓位上限：

  • 仓位上限 = 3。
  • 3 个仓位依次因为漏检死叉而卡死。
  • 新开仓前检查 len(positions) < max_positions，返回 False。
  • 系统不再开新仓。
  • 而且没有任何报错——因为从代码视角看，一切逻辑都按设计执行了：没有死叉事件，所以不平仓；仓位满了，所以不开仓。日志"一切正常"。

这就是死锁：每个模块单独看都对，组合起来系统进入一个无法自行退出的状态。

事件 vs 状态：两种平仓判定

把两种写法并排放在一起，问题一目了然。

事件驱动（有缺陷）

class EventDrivenExit:
    """只在交叉发生的那一根 K 线触发平仓"""

    def __init__(self):
        self.prev_fast = None
        self.prev_slow = None

    def should_exit(self, ema_fast: float, ema_slow: float) -> bool:
        triggered = False
        if self.prev_fast is not None:
            # 上一根快线 >= 慢线, 这一根快线 < 慢线 => 死叉
            if self.prev_fast >= self.prev_slow and ema_fast < ema_slow:
                triggered = True
        self.prev_fast = ema_fast
        self.prev_slow = ema_slow
        return triggered

缺陷：triggered 只在这一根为 True。一旦这根被跳过（接口失败、任务未执行、进程重启丢了 prev_fast），就永久错过。

状态兜底（鲁棒）

class StateBasedExit:
    """持仓检查时直接判断当前 EMA 状态"""

    def should_exit(self, ema_fast: float, ema_slow: float) -> bool:
        # 快线在慢线下方 => 当前处于空头排列 => 应平多
        return ema_fast < ema_slow

交叉事件只是最早的触发点，而"快线在慢线下方"是一个持续成立的状态。只要当前状态满足平仓条件，无论之前漏检了多少根，下一次持仓检查都能兜住。

两者在逐根回测中的等价性

关键结论：在逐根回测中，状态兜底与事件检测结果完全一致。原因很简单——回测逐根推进，每根 K 线都会执行一次检查。事件检测在死叉那一根返回 True 并平仓；状态兜底在死叉那一根也返回 True（因为快线已经跌到慢线下方）并平仓。两者平仓点相同，回测曲线一模一样。

差异只出现在实盘：实盘会漏根，状态兜底能在漏根之后补上，事件检测不能。

这也解释了为什么这个 bug 在回测里发现不了——回测的"逐根不漏"假设掩盖了事件的脆弱性。回测等价性不是缺陷，恰恰是修复的安全保证：改成状态兜底不会改变历史回测结果，只提高实盘鲁棒性。

修复方案

方案一：直接改成状态判定（推荐）

对于"死叉平多"这种单向、单调的平仓条件，最干净的修复就是直接用状态判定，删掉事件逻辑：

class PositionManager:
    def __init__(self, max_positions: int = 3):
        self.positions = []
        self.max_positions = max_positions

    def check_exit(self, pos, ema_fast: float, ema_slow: float) -> bool:
        # 状态兜底: 多头持仓, 快线在慢线下方即平
        if pos.side == "long" and ema_fast < ema_slow:
            return True
        return False

    def can_open(self) -> bool:
        return len(self.positions) < self.max_positions

每一轮持仓检查都重新评估当前状态，漏检多少根都能补上。

方案二：事件 + 状态双保险

如果业务上确实需要保留"事件触发"的语义（比如事件触发时要做额外动作，或者平仓条件不是单调的），可以保留事件检测作为最快触发，同时加状态兜底作为保底：

class HybridExit:
    def __init__(self):
        self.prev_fast = None
        self.prev_slow = None

    def should_exit(self, ema_fast: float, ema_slow: float) -> bool:
        # 1) 事件触发(最快, 但当根漏检就没了)
        event_hit = False
        if self.prev_fast is not None:
            if self.prev_fast >= self.prev_slow and ema_fast < ema_slow:
                event_hit = True
        self.prev_fast = ema_fast
        self.prev_slow = ema_slow

        # 2) 状态兜底(漏检也能补)
        state_hit = ema_fast < ema_slow

        return event_hit or state_hit

注意：当平仓条件是单调的（一旦进入空头排列就不再回头），event_hit or state_hit 里的 event_hit 其实是冗余的——state_hit 已经覆盖。保留它更多是为了日志可读性，能区分"是事件触发还是状态兜底触发"。

方案三：加死锁监控

修复逻辑之外，建议加一个独立于交易逻辑的健康检查，专门盯这种"静默死锁"：

def health_check(pm: PositionManager, ema_fast: float, ema_slow: float):
    """独立巡检: 发现应平未平、仓位满且无新信号, 主动告警"""
    stuck = []
    for pos in pm.positions:
        if pos.side == "long" and ema_fast < ema_slow:
            stuck.append(pos)
    if stuck:
        # 这里应打 ERROR 日志 / 发告警, 而不是静默
        raise RuntimeError(
            f"检测到 {len(stuck)} 个应平未平仓位, 疑似事件漏检死锁"
        )

这个巡检的价值在于：它不依赖交易主流程的"正常"判断，而是独立用状态重新核对一遍。主流程说"没死叉事件所以不平仓"，巡检说"当前明明是空头排列，为什么还拿着多单"——两个视角一对照，死锁立刻暴露。

测试方法

改完之后怎么验证？三个层次的测试。

1. 逐根等价性测试

证明状态兜底不改变回测结果：

def test_equivalence():
    """同一段行情, 事件检测与状态兜底的平仓点必须一致"""
    import random
    random.seed(42)

    # 构造一段有多次交叉的 EMA 序列
    fast, slow = 100.0, 100.0
    series = []
    for _ in range(500):
        fast += random.uniform(-1.5, 1.5)
        slow += random.uniform(-1.0, 1.0)
        series.append((fast, slow))

    event_exit = EventDrivenExit()
    exits_event = []
    for i, (f, s) in enumerate(series):
        if event_exit.should_exit(f, s):
            exits_event.append(i)

    state_exit = StateBasedExit()
    exits_state = []
    for i, (f, s) in enumerate(series):
        if state_exit.should_exit(f, s):
            exits_state.append(i)

    # 逐根回测里, 两者应给出相同的首次平仓点
    assert exits_event[0] == exits_state[0], "首次平仓点不一致"

2. 漏检注入测试

模拟接口失败跳过若干根，验证状态兜底能补上：

def test_missed_bar_recovery():
    """注入漏检: 事件检测会卡死, 状态兜底能补平"""
    # 死叉发生在第 10 根
    series = [(100.0, 100.0)] * 9 + [(99.0, 100.5)] + [(98.0, 101.0)] * 10

    # 场景A: 事件检测, 第10根被跳过
    ev = EventDrivenExit()
    event_exited = False
    for i, (f, s) in enumerate(series):
        if i == 10:          # 模拟漏检
            continue
        if ev.should_exit(f, s):
            event_exited = True
    assert not event_exited, "事件检测在漏检后应卡死(复现bug)"

    # 场景B: 状态兜底, 第10根被跳过
    st = StateBasedExit()
    state_exited = False
    for i, (f, s) in enumerate(series):
        if i == 10:
            continue
        if st.should_exit(f, s):
            state_exited = True
            break
    assert state_exited, "状态兜底应在漏检后仍能平仓"

3. 死锁回归测试

验证"仓位满 + 应平未平"能被巡检捕获：

def test_deadlock_detected():
    pm = PositionManager(max_positions=3)
    pm.positions = [
        type("P", (), {"side": "long"})() for _ in range(3)
    ]
    # 空头排列: 快线 < 慢线
    try:
        health_check(pm, ema_fast=98.0, ema_slow=101.0)
        assert False, "应抛异常"
    except RuntimeError as e:
        assert "应平未平" in str(e)

经验总结

  1. 事件可以被错过，状态不会。 凡是"穿越/触发/首次"这类瞬时语义，都要问一句：漏了怎么办？如果答案是"永远补不回来"，就该加状态兜底。
  2. 死锁往往是静默的。 每个模块单独看都"正常"，组合起来系统停摆，日志还一片祥和。健康巡检要用独立视角重新核对状态。
  3. 回测等价性是修复的安全网。 逐根回测里状态兜底与事件检测等价，说明这个修复不改历史结果，只是让实盘更抗漏。改之前先写等价性测试，改完心里有底。
  4. 容错设计要防组合漏洞。 失败计数清零单独看是合理的，但和事件驱动平仓组合就制造了窗口跳过。设计容错时要把"漏检"和"依赖漏检结果的逻辑"放在一起审视。

事件驱动不是不能用，但要用在对漏检不敏感的地方。平仓这种"必须发生"的动作，交给状态判定更稳。
