一次API拉全市场行情：批量持仓估值的工程优化

2026-10-29 API实战

给几十个持仓算实时浮亏，最直观的写法是循环遍历持仓，每个 symbol 调一次行情接口：

for pos in positions:
    price = get_price(pos.symbol)   # 一次HTTP请求
    pnl = (price - pos.entry) * pos.size * pos.direction

逻辑没问题，但工程上很糟。几十个持仓就是几十次 HTTP 请求，串行跑下来几百毫秒到几秒不等，而且每个请求都是一次独立的限频计数。仓位再多一点，或者估值频率提高到每秒一次，很快就会被交易所按在限频墙上。

这篇文章记录一个把「N 次请求」压成「1 次请求」的改造过程：用全市场 tickers 接口一次拉回所有合约现价，本地建字典查价，批量算浮亏。顺带处理单币缺失、超时、重试这些绕不开的工程细节。

问题拆解：慢在哪，限频限在哪

先把成本算清楚。假设 50 个持仓，单次行情请求平均耗时 80ms（含网络 RTT 和交易所处理），串行就是 4 秒。如果估值循环跑在策略主循环里，4 秒的阻塞足以让信号延迟到没法用。

限频方面，主流交易所的现货/合约行情端点通常按 IP 或 API Key 计权重，单 symbol 查询的权重虽低，但 50 次/轮的频率叠加多策略并发，很容易撞到每分钟请求数上限。一旦触发限频，返回 429 或直接封禁一段时间，整个估值链路一起挂掉。

关键观察是：我们需要的不是「每个 symbol 的最新价」，而是「全市场最新价里我们关心的那几十个」。这两个需求在数据量上差了几个数量级，但交易所恰好提供了后者——一次返回全市场所有合约 ticker 的端点。

以 Gate.io 的合约行情为例，/api/v4/futures/usdt/tickers 一次返回全部 USDT 永续合约的最新成交价、标记价、买一卖一等字段。一次请求，几百个合约的价格全在手里。

方案：全市场快照 + 本地字典

整体思路三步：

  1. 一次请求拉全市场 tickers；
  2. 构建 pair -> price 的字典；
  3. 遍历持仓，从字典 O(1) 查价，批量算浮亏。

先看拉取和建字典的部分：

import time
import requests
from typing import Dict, List, Optional

GATE_FUTURES_TICKERS = "https://api.gateio.ws/api/v4/futures/usdt/tickers"

def fetch_all_prices(timeout: float = 5.0, retries: int = 3) -> Dict[str, float]:
    """一次拉取全市场合约最新价，返回 {contract: price} 字典。"""
    last_err: Optional[Exception] = None
    for attempt in range(retries):
        try:
            resp = requests.get(GATE_FUTURES_TICKERS, timeout=timeout)
            resp.raise_for_status()
            data = resp.json()
            prices: Dict[str, float] = {}
            for item in data:
                contract = item.get("contract")
                last = item.get("last")
                if not contract or last is None:
                    continue
                try:
                    prices[contract] = float(last)
                except (TypeError, ValueError):
                    continue
            if not prices:
                raise ValueError("empty tickers payload")
            return prices
        except Exception as e:
            last_err = e
            time.sleep(0.5 * (2 ** attempt))  # 指数退避
    raise RuntimeError(f"fetch_all_prices failed after {retries} retries") from last_err

注意几个细节：

  • raise_for_status() 把 4xx/5xx 转成异常，交给重试逻辑统一处理；
  • 单条记录解析失败（last 为 None 或不是数字）直接 continue，不让一条脏数据毁掉整批；
  • 指数退避 0.5 * 2**attempt，避免限频时连续重试加重惩罚；
  • 返回空字典视为失败，触发重试——全市场接口返回空基本只能是异常。

拿到价格字典后，批量估值就是纯本地计算：

from dataclasses import dataclass

@dataclass
class Position:
    contract: str      # 例如 "BTC_USDT"
    entry: float
    size: float        # 正数为多，负数为空
    # 合约面值等乘数按实际品种自行处理，这里简化

def batch_valuation(positions: List[Position],
                    prices: Dict[str, float]) -> List[dict]:
    results = []
    for pos in positions:
        price = prices.get(pos.contract)
        if price is None:
            # 单币缺失：跳过并标记，不中断整批
            results.append({
                "contract": pos.contract,
                "price": None,
                "pnl": None,
                "status": "missing_price",
            })
            continue
        pnl = (price - pos.entry) * pos.size
        results.append({
            "contract": pos.contract,
            "price": price,
            "pnl": pnl,
            "status": "ok",
        })
    return results

这里的关键设计是单币缺失只影响自己。全市场快照里理论上应该包含所有在交易的合约，但新上市、临时停牌、字段异常都可能让某个 contract 查不到价。如果直接 prices[pos.contract] 抛 KeyError，整批估值全废；用 .get() 加状态标记，缺失的持仓单独标出来，其余照常算完。上层可以对这些 missing_price 的仓位做告警或沿用上一轮价格。

性能对比：N 次 vs 1 次

写个简单基准，对比两种方式在 50 个持仓下的耗时：

import statistics

def bench_single_requests(contracts: List[str], rounds: int = 5) -> float:
    """逐 symbol 请求，返回平均耗时（秒）。"""
    times = []
    for _ in range(rounds):
        t0 = time.perf_counter()
        for c in contracts:
            requests.get(
                f"https://api.gateio.ws/api/v4/futures/usdt/tickers?contract={c}",
                timeout=5,
            )
        times.append(time.perf_counter() - t0)
    return statistics.mean(times)

def bench_batch(rounds: int = 5) -> float:
    times = []
    for _ in range(rounds):
        t0 = time.perf_counter()
        fetch_all_prices()
        times.append(time.perf_counter() - t0)
    return statistics.mean(times)

在本地网络环境下实测（不同网络差异较大，仅看数量级）：

方式 请求数 平均耗时 限频权重消耗
逐 symbol 请求（50 持仓） 50 ~3.5–5 s 50 次/轮
全市场快照 1 ~0.1–0.2 s 1 次/轮

耗时差一个数量级以上，限频权重消耗差 50 倍。更重要的是，全市场快照的耗时基本与持仓数量无关——50 个持仓和 500 个持仓，拉取成本一样，只有本地字典遍历的差异，而那是微秒级的。这让估值频率可以放心提高，比如从每分钟一次提到每 5 秒一次，限频压力反而比原来更低。

内存上，几百个合约的字典也就几十 KB，完全不是瓶颈。

异常处理：让估值链路不因单点失败而崩

批量估值最容易出问题的地方不是计算，是数据链路。分三层处理：

单币缺失：跳过而非中断

前面 batch_valuation 已经用 .get() + 状态标记解决了。补充一个实践：对 missing_price 的持仓，可以维护一份「上一轮有效价格」缓存，缺失时用缓存兜底，同时打日志告警。这样估值结果不会因为一次快照缺字段就出现空洞。

class PriceCache:
    def __init__(self):
        self._last: Dict[str, float] = {}

    def update(self, prices: Dict[str, float]):
        self._last.update(prices)

    def get(self, contract: str) -> Optional[float]:
        return self._last.get(contract)

超时与重试：分开处理可重试与不可重试

requests 的 timeout 参数建议传元组 (connect_timeout, read_timeout)，把连接超时和读取超时区分开。连接超时通常设短（1–2s），读取超时按接口实际响应时间留余量（3–5s）。

重试要区分错误类型：网络超时、连接错误、5xx 值得重试；4xx（尤其 401/403 鉴权失败、400 参数错误）重试没有意义，直接抛。上面的 fetch_all_prices 用 raise_for_status() 统一转异常后无差别重试，更严谨的版本应该判断状态码：

def _should_retry(resp_or_exc) -> bool:
    if isinstance(resp_or_exc, requests.HTTPError):
        code = resp_or_exc.response.status_code
        return code == 429 or 500 <= code < 600
    return isinstance(resp_or_exc, (requests.Timeout, requests.ConnectionError))

429 单独处理：读 Retry-After 响应头，按它给的秒数等待，比盲目指数退避更符合交易所预期。

快照新鲜度：别让旧数据冒充实时

全市场快照有个隐含风险：接口返回成功，但某些合约的 last 字段可能是很久以前的成交价（流动性差的品种）。如果直接用，算出来的浮亏是失真的。可以在解析时检查 ticker 里的时间戳字段（Gate.io 的 tickers 返回 create_time 等），超过阈值（比如 60 秒）的标记为 stale，走和缺失一样的兜底逻辑。

def is_stale(item: dict, max_age: float = 60.0) -> bool:
    ts = item.get("create_time")
    if ts is None:
        return False
    try:
        return time.time() - float(ts) > max_age
    except (TypeError, ValueError):
        return True

落地建议

几个从这次改造里总结的点：

估值循环和行情拉取解耦。 用一个后台线程或定时任务按固定频率刷新价格字典，估值函数只读字典、不做网络 IO。这样估值调用是纯内存操作，主策略循环不会被网络抖动阻塞。字典更新用整体替换而非逐 key 更新，避免读到半更新状态（Python 的 dict 赋值是原子的，但整体替换语义更清晰）。

频率对齐限频预算。 全市场快照虽然便宜，也不是免费的。先查清楚该端点的权重和每分钟上限，再决定刷新频率。单策略 5 秒一次、多策略共享一个刷新线程，是常见做法。

监控缺失率和延迟。 每次估值记录 missing_price 数量和快照年龄，这两个指标异常往往先于估值错误暴露问题。缺失率突然上升，可能是合约改名或接口字段变更；快照年龄变大，可能是拉取线程卡死。

别在估值路径里做重试。 重试放在拉取层，估值层拿到什么用什么，缺失就走兜底。估值函数应该是确定性的、无副作用的，方便测试和复用。

这套改造的核心其实就一句话：把「按需逐个取」换成「批量快照 + 本地索引」。同样的思路可以用在任何「需要全市场某个字段」的场景——批量查余额、批量查订单状态、批量算保证金占用，都是先拉全量再本地匹配，比逐个请求快一个数量级，限频压力也小得多。
