Exit Code 267009: Debugging CMD Encoding Corruption

2026-10-04 Windows Automation

Exit code 267009 looks like noise until you decode it. On a Windows scheduled task I maintain, a .bat launcher that worked fine when double-clicked started failing under Task Scheduler with that exact code. The task had no output, no log, nothing in Event Viewer beyond the failure. The launcher itself was three lines long. The problem was not the logic — it was the bytes.

What 267009 actually is

Windows exit codes are unsigned 32-bit integers. 267009 in hex is 0x41301. If you have spent time around the Task Scheduler API, that number should look familiar: SCHED_S_TASK_RUNNING is 0x00041301. It means the task is still running — or, more precisely, the Task Scheduler is reporting that the task's process has not terminated.

That is why the code is confusing. It is not an error from your script at all. It is the scheduler's own status code leaking into whatever tool you used to read the result. A .bat that exits cleanly with 0 will still surface as 267009 if the scheduler sampled the state before the process finished, or if the process never finished because it died in a way the scheduler could not classify.

So the first lesson: exit code 267009 is a scheduler status, not a script error. It tells you the task did not reach a clean terminal state. In my case, cmd.exe was stuck parsing the batch file.

Decoding obscure exit codes in general

Before chasing the script, decode the number. A small Python helper saves a lot of guessing:

def explain_exit_code(code: int) -> str:
    unsigned = code & 0xFFFFFFFF
    known = {
        0x00000000: "success",
        0x00000001: "generic failure / incorrect function",
        0x00000002: "file not found",
        0x00000005: "access denied",
        0x00000102: "timeout",
        0x00000413: "SCHED_S_TASK_READY",
        0x000004130: "SCHED_S_TASK_RUNNING",  # 267009
        0x000004131: "SCHED_S_TASK_NOT_SCHEDULED",
        0x80070420: "service already running",
        0xC000013A: "STATUS_CONTROL_C_EXIT (Ctrl+C)",
    }
    return known.get(unsigned, f"unknown: 0x{unsigned:08X} ({unsigned})")

for c in (267009, 1, 0xC000013A):
    print(c, "->", explain_exit_code(c))

Run that and 267009 -> SCHED_S_TASK_RUNNING falls out immediately. That single lookup reframed the whole investigation: I was not debugging a script that returned a bad code, I was debugging a script that never returned.

Reproducing the failure

The launcher was a batch file with Chinese comments and a path containing Chinese characters:

@echo off
rem 启动数据同步任务
cd /d "D:\数据\sync"
python sync.py --mode incremental

Saved as UTF-8 without BOM. The system codepage was GBK (code page 936). When cmd.exe reads a batch file, it interprets bytes according to the active console code page, not the file's declared encoding. UTF-8 Chinese text is multi-byte sequences that GBK reads as different characters. In the worst case, a byte sequence decodes to a character that cmd.exe treats as a command separator or a redirection operator. The parser then either runs garbage or blocks waiting for input.

You can reproduce this deterministically:

@echo off
rem 这是中文注释
echo done

Save as UTF-8, run from a GBK console:

C:\> test.bat
'锟斤拷' is not recognized as an internal or external command,
operable program or batch file.

The mojibake command name is the tell. Under Task Scheduler the same script may hang instead of erroring, because the corrupted token can consume the rest of the line and leave cmd.exe waiting on a pipe that never closes. The process stays alive, the scheduler reports 267009, and the task never completes.

Why it works interactively but fails in a task

When you double-click the file, cmd.exe inherits your interactive console code page, which may already be 65001 (UTF-8) or have the right font and locale. Task Scheduler launches with a different environment: no interactive console, a system default code page, and often a different user profile. The same bytes are interpreted differently. This is the single most common reason a .bat "works on my machine" but fails as a scheduled task.

The three fixes that worked

1. Keep .bat files pure ASCII

This is the most robust fix. Batch files are a legacy format; do not put non-ASCII text in them. Move comments out of the launcher and into the Python script or a separate README. If you must keep a comment, write it in ASCII:

@echo off
rem start data sync task
cd /d "D:\data\sync"
python sync.py --mode incremental

If the path itself contains Chinese characters, do not embed it as UTF-8 in the batch file. Two options: encode the whole file as GBK, or avoid the literal path entirely.

2. Encode as GBK, or better, avoid the issue

If you cannot remove non-ASCII content, write the file in the codepage the target machine uses. For a GBK system:

content = '@echo off\nrem 启动数据同步任务\ncd /d "D:\\数据\\sync"\npython sync.py\n'
with open("launcher.bat", "wb") as f:
    f.write(content.encode("gbk"))

This works, but it is fragile. Copy the file to a machine with a different codepage and it breaks again. That is exactly the "survives being copied between machines" problem. Prefer ASCII plus a path that does not need non-ASCII bytes.

3. Use the 8.3 short path for non-ASCII paths

Windows maintains an 8.3 short name for every long path, including paths with Chinese characters. D:\数据\sync might have a short form like D:\5F3A~1\SYNC. You can retrieve it programmatically and put the ASCII short path in the batch file:

import ctypes
from ctypes import wintypes

def short_path(long_path: str) -> str:
    GetShortPathNameW = ctypes.windll.kernel32.GetShortPathNameW
    GetShortPathNameW.argtypes = [wintypes.LPCWSTR, wintypes.LPWSTR, wintypes.DWORD]
    GetShortPathNameW.restype = wintypes.DWORD
    size = GetShortPathNameW(long_path, None, 0)
    if size == 0:
        raise OSError(f"cannot resolve short path for {long_path}")
    buf = ctypes.create_unicode_buffer(size)
    GetShortPathNameW(long_path, buf, size)
    return buf.value

print(short_path(r"D:\数据\sync"))
# -> D:\5F3A~1\SYNC

Then the launcher stays pure ASCII:

@echo off
cd /d "D:\5F3A~1\SYNC"
python sync.py --mode incremental

One caveat: 8.3 name generation can be disabled on a volume (fsutil 8dot3name query D:). If it is disabled and the path already exists without a short name, GetShortPathNameW returns the original long path. Check this before relying on it.

CRLF line endings matter

Batch files require CRLF (\r\n). A file saved with LF-only line endings can behave inconsistently — cmd.exe may treat the whole file as one line, or misparse labels and goto targets. This is another failure mode that appears when a file is copied through a tool that normalizes line endings (Git with core.autocrlf=false, or a text editor on Linux/macOS).

content = '@echo off\r\nrem start sync\r\ncd /d "D:\\data\\sync"\r\npython sync.py\r\n'
with open("launcher.bat", "wb") as f:
    f.write(content.encode("ascii"))

Write bytes, not text, and be explicit about both encoding and line endings. Never let an editor or version control decide for you.

A checklist for batch files that travel

Before a .bat file goes into a scheduled task or gets copied to another machine, verify:

  • Encoding is ASCII or the target codepage. file launcher.bat should not report UTF-8 if the target is GBK.
  • Line endings are CRLF. Check with python -c "print(open('launcher.bat','rb').read()[:200])" and look for \r\n.
  • No non-ASCII in comments, echoes, or paths. If a path needs non-ASCII, use the 8.3 short form.
  • No BOM. A UTF-8 BOM at the start of a .bat file causes cmd.exe to fail on the first line with an unrecognized command. Write with encoding="ascii" or encoding="gbk", never utf-8-sig.
  • Absolute paths, not relative. The task's working directory is not what you think it is.
  • Explicit cd /d to the target directory before running anything.
  • Exit codes are explicit. End the script with exit /b %ERRORLEVEL% so the scheduler sees a real code.

A validation helper that catches most of these before deployment:

from pathlib import Path

def validate_bat(path: Path, expected_encoding: str = "ascii") -> list[str]:
    issues = []
    raw = path.read_bytes()
    if raw.startswith(b"\xef\xbb\xbf"):
        issues.append("UTF-8 BOM present")
    if b"\r\n" not in raw:
        issues.append("no CRLF line endings found")
    if b"\n" in raw.replace(b"\r\n", b""):
        issues.append("bare LF line endings present")
    try:
        raw.decode(expected_encoding)
    except UnicodeDecodeError as e:
        issues.append(f"not decodable as {expected_encoding}: {e}")
    for i, line in enumerate(raw.split(b"\r\n"), 1):
        if any(b > 127 for b in line):
            issues.append(f"non-ASCII bytes on line {i}")
    return issues

for problem in validate_bat(Path("launcher.bat")):
    print("ISSUE:", problem)

Run this in your build or deployment step and the encoding class of bugs stops reaching production.

Why the exit code misleads

The trap with 267009 is that it points at the scheduler, not the script. If you only look at the exit code, you will spend time reading Task Scheduler documentation when the real fault is a byte on line 2 of a batch file. The debugging sequence that worked was:

  1. Decode the exit code. 267009 is SCHED_S_TASK_RUNNING, not a script error.
  2. Check whether the process is actually alive. If it is, the script is blocked, not failing.
  3. Inspect the batch file as bytes, not as text. file, xxd, or the validator above.
  4. Reproduce interactively with the same code page the task uses.
  5. Fix the encoding, line endings, and path representation.

The general principle extends past this one bug: when a scheduled task fails with a code you do not recognize, decode it first, then ask what state the process is actually in. The answer is often that it never finished — and the reason it never finished is usually in the bytes of the launcher, not in the logic of the program.
