Cross-Posting Automation: One Article, Three Platforms

2026-10-20 API Integration

Publishing the same article to three places sounds trivial until you actually build it. The canonical copy lives on a self-hosted static site built from Markdown and pushed to GitHub Pages. Juejin accepts a bearer token and has an editor-friendly draft API. CSDN doesn't really offer a supported write API, so you drive it with cookies and the same internal endpoints the web editor uses. Three different auth models, three different content rules, three different ways to fail.

The design principle that makes this manageable: the canonical copy is the source of truth, and every secondary platform is best-effort. If Juejin is down, that is a Juejin problem, not an article problem. The run should still succeed.

The pipeline shape

A publish run has four phases:

  1. Render and verify — build the site locally, check the Markdown converts cleanly, confirm required front matter exists.
  2. Publish canonical — commit and push to GitHub. This is the only step allowed to fail the run.
  3. Fan out — attempt each secondary platform independently. Each returns a structured result, never raises.
  4. Summarize — push one notification with per-platform status.

The key word in phase 3 is independently. No shared try/except around the loop, no early exit on first failure. Each platform adapter gets its own attempt and its own timeout.

from dataclasses import dataclass, field
from enum import Enum

class Status(str, Enum):
    OK = "ok"
    SKIPPED = "skipped"
    AUTH_EXPIRED = "auth_expired"
    FAILED = "failed"
    TIMEOUT = "timeout"

@dataclass
class PublishResult:
    platform: str
    status: Status
    url: str | None = None
    detail: str = ""

    @property
    def needs_attention(self) -> bool:
        return self.status in (Status.AUTH_EXPIRED, Status.FAILED, Status.TIMEOUT)

Adapters never raise past their boundary. They translate exceptions into a Status. That single rule removes most of the orchestration complexity downstream.

Canonical publish first, and only it can fail the run

The static site build is deterministic and cheap to verify. Render the article, check that the output HTML contains the expected title and at least one code block, then push.

import subprocess
from pathlib import Path

def publish_canonical(article: Path) -> PublishResult:
    build = subprocess.run(
        ["python", "-m", "build_site", "--strict", str(article)],
        capture_output=True, text=True, timeout=120,
    )
    if build.returncode != 0:
        return PublishResult("github-pages", Status.FAILED,
                             detail=build.stderr[-2000:])

    commit = subprocess.run(
        ["git", "add", "-A"], capture_output=True, text=True,
    )
    commit = subprocess.run(
        ["git", "commit", "-m", f"publish: {article.stem}"],
        capture_output=True, text=True,
    )
    if commit.returncode != 0 and "nothing to commit" not in commit.stdout:
        return PublishResult("github-pages", Status.FAILED,
                             detail=commit.stdout + commit.stderr)

    push = subprocess.run(
        ["git", "push"], capture_output=True, text=True, timeout=120,
    )
    if push.returncode != 0:
        return PublishResult("github-pages", Status.FAILED,
                             detail=push.stderr[-2000:])

    return PublishResult("github-pages", Status.OK,
                         url=f"https://example.dev/posts/{article.stem}/")

If this returns FAILED, the orchestrator stops and exits non-zero. Nothing gets posted anywhere else, because posting a secondary copy of an article that isn't live on your own site is backwards. Once canonical succeeds, the run is considered successful regardless of what happens next.

Cookie hygiene for CSDN

The CSDN adapter needs a session cookie. The tempting shortcut is to paste the cookie string into a CI variable or a shell script. Don't. Cookie strings are long, contain characters that break shell quoting, rotate silently, and end up in logs. Keep them in a JSON file that is gitignored and injected at runtime.

{
  "cookies": [
    {"name": "UserName", "value": "..."},
    {"name": "UserToken", "value": "..."},
    {"name": "SESSION", "value": "..."}
  ],
  "saved_at": "2025-01-14T09:30:00Z"
}

Load it with a small helper that validates shape before use:

import json
from pathlib import Path

COOKIE_FILE = Path.home() / ".config" / "crosspost" / "csdn.json"

def load_cookies(path: Path = COOKIE_FILE) -> list[dict]:
    if not path.exists():
        raise FileNotFoundError(f"cookie file missing: {path}")
    data = json.loads(path.read_text(encoding="utf-8"))
    cookies = data.get("cookies")
    if not isinstance(cookies, list) or not cookies:
        raise ValueError("cookie file has no usable cookies")
    for c in cookies:
        if not {"name", "value"} <= c.keys():
            raise ValueError(f"malformed cookie entry: {c.get('name')!r}")
    return cookies

Two rules that save pain later:

  • Never log cookie values. Log names and count only. When you debug, you need to know which cookie is missing, not its value.
  • Keep the file out of git and out of shell history. One file, one path, one loader. If you refresh cookies, you overwrite the file, and nothing else changes.

Detect expiry before you publish

The worst failure mode is a half-published article: the draft gets created, then the publish call fails because the session expired, leaving a broken draft behind. Check auth first with a cheap read call.

For CSDN, hit an endpoint that requires the session and returns the current user. For Juejin, call the token-validated "me" endpoint. Both are cheap and both fail fast.

import httpx

def check_csdn_session(cookies: list[dict]) -> Status:
    jar = {c["name"]: c["value"] for c in cookies}
    try:
        r = httpx.get(
            "https://bizapi.csdn.net/blog-console-api/v1/user/info",
            cookies=jar,
            headers={"Referer": "https://mp.csdn.net/"},
            timeout=15,
        )
    except httpx.TimeoutException:
        return Status.TIMEOUT

    if r.status_code in (401, 403):
        return Status.AUTH_EXPIRED
    if r.status_code != 200:
        return Status.FAILED
    body = r.json()
    if body.get("code") != 200:
        return Status.AUTH_EXPIRED
    return Status.OK

When the check returns AUTH_EXPIRED, the adapter returns that status immediately and does not touch the article. The summary then tells you to refresh that one cookie file, and you don't have to clean up a stray draft.

Content rules differ, so normalize once

Juejin and CSDN both accept Markdown, but not the same Markdown. Differences that bite in practice:

  • Images. Juejin requires images to be hosted on its own CDN; external URLs render inconsistently. CSDN tolerates external images but strips some attributes. The safe move is to upload images once to each platform and rewrite URLs per target.
  • Code fences. Both handle fenced code, but CSDN's editor sometimes mangles nested fences. Flatten any triple-backtick-inside-triple-backtick before sending.
  • Front matter. Neither platform wants your YAML front matter. Strip it before the body leaves your pipeline.
  • Length and title limits. Both truncate long titles silently. Validate title length before the call, not after.

Do the normalization in one place, keyed by platform, so the adapters stay dumb:

import re

FRONT_MATTER = re.compile(r"\A---\n.*?\n---\n", re.DOTALL)
NESTED_FENCE = re.compile(r"````.*?````", re.DOTALL)

def normalize(markdown: str, platform: str) -> str:
    body = FRONT_MATTER.sub("", markdown, count=1)
    body = NESTED_FENCE.sub(lambda m: m.group(0).replace("````", "```"), body)
    if platform in ("juejin", "csdn"):
        body = rewrite_images(body, platform)
    return body.strip()

rewrite_images uploads each referenced image to the platform's image API and swaps the URL. Cache the mapping by content hash so a re-run doesn't re-upload the same image.

The orchestrator

With adapters that never raise, the fan-out is a short loop. The one thing worth adding is a per-platform timeout so a hanging CSDN request can't stall the run.

import concurrent.futures as cf

ADAPTERS = {
    "juejin": publish_juejin,
    "csdn": publish_csdn,
}

def fan_out(markdown: str, meta: dict) -> list[PublishResult]:
    results: list[PublishResult] = []
    with cf.ThreadPoolExecutor(max_workers=len(ADAPTERS)) as pool:
        futures = {
            pool.submit(safe_publish, name, fn, markdown, meta): name
            for name, fn in ADAPTERS.items()
        }
        for fut in cf.as_completed(futures, timeout=180):
            results.append(fut.result())
    return results

def safe_publish(name, fn, markdown, meta) -> PublishResult:
    try:
        return fn(markdown, meta)
    except Exception as exc:
        return PublishResult(name, Status.FAILED, detail=repr(exc)[:500])

safe_publish is the backstop. Adapters should already handle their own errors, but if one slips through, the run still finishes and the summary still reflects reality.

The summary push

This is the part people skip, and it's the part that makes the system usable. One notification, per-platform status, links where available.

def format_summary(results: list[PublishResult]) -> str:
    lines = []
    for r in sorted(results, key=lambda x: (not x.needs_attention, x.platform)):
        icon = {Status.OK: "OK", Status.SKIPPED: "--",
                Status.AUTH_EXPIRED: "AUTH", Status.FAILED: "FAIL",
                Status.TIMEOUT: "TIME"}[r.status]
        line = f"[{icon}] {r.platform}"
        if r.url:
            line += f" -> {r.url}"
        if r.detail:
            line += f" ({r.detail[:120]})"
        lines.append(line)
    return "\n".join(lines)

Sort attention-needed platforms to the top. If the first line says [AUTH] csdn, you know exactly what to do before reading anything else. The notification goes through whatever channel you already use — a webhook, a bot, an email — and the payload is just this string plus the canonical URL.

Exit code logic is one line:

canonical_ok = canonical.status == Status.OK
sys.exit(0 if canonical_ok else 1)

Secondary failures never affect the exit code. They affect the summary, which is where you want them.

What this buys you

The pipeline now has one hard dependency (your own site) and two soft ones. A Juejin outage costs you nothing. An expired CSDN cookie costs you one line in a notification and one file refresh. The article is never half-published, because auth is checked before any write, and the canonical copy is always live first.

The pattern generalizes: any time you fan out to external services with unequal reliability, make the reliable step gate the run, make the unreliable steps independent, and put the truth in one summary instead of scattered logs.
