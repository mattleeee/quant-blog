When GitHub Is Blocked but You Still Need to Push

2026-10-06 Network & Security

When a firewall blocks github.com:443 but leaves api.github.com and raw.githubusercontent.com open, git push dies while the REST API keeps working. Here is the exact path I used to keep deploying.

The symptom: push hangs, API responds

The failure mode is specific. git push hangs on connect and eventually times out:

fatal: unable to access 'https://github.com/user/repo.git/':
Failed to connect to github.com port 443 after 21000 ms

But the same machine can fetch https://api.github.com/rate_limit in under a second. That asymmetry is the whole opportunity. The firewall rule was written against the hostname github.com, not against GitHub's IP ranges or the API host. Git's smart HTTP transport and the Contents API happen to live on different hostnames, so one dies and the other survives.

Before rewriting any deployment logic, confirm which endpoints actually work. Do not assume — probe.

Probing with curl.exe on Windows

On Windows, curl is an alias for Invoke-WebRequest in older PowerShell, which has different flags and different error messages. Call curl.exe explicitly so you get real curl semantics.

# Connectivity and TLS handshake per endpoint
foreach ($h in @("github.com","api.github.com","raw.githubusercontent.com","codeload.github.com")) {
    Write-Host "--- $h ---"
    curl.exe -sS -o NUL -w "http=%{http_code} connect=%{time_connect}s total=%{time_total}s`n" `
        --max-time 8 "https://$h"
}

Three outcomes matter:

  • http=200 or http=301/404 — the endpoint is reachable. A 404 on the bare host is fine; you got a response.
  • curl: (7) Failed to connect — TCP is blocked or blackholed.
  • Exit code 28 with a long time_total — packets are being dropped silently. That is a firewall, not a DNS problem.

Check DNS separately, because a poisoned or filtered resolver produces confusing results:

Resolve-DnsName api.github.com -Type A

If DNS resolves but connect fails, the block is at the network layer. If DNS itself is filtered, you have a different problem and the API trick will not help.

Finally, verify that the API path works end to end with authentication, because unauthenticated requests are rate-limited to 60/hour and will not survive a deployment:

curl.exe -sS -H "Authorization: Bearer $env:GH_TOKEN" `
    -H "Accept: application/vnd.github+json" `
    "https://api.github.com/rate_limit"

Look at resources.core.remaining. If you see 4999 or 5000, you are authenticated and good to go.

The Contents API: read the SHA, write the blob

The Contents API is a plain REST resource. To update a file you need three things: the path, the new content, and the current blob SHA. The SHA is the optimistic-concurrency token — GitHub rejects the write if it does not match, which prevents two deployers from clobbering each other.

Step 1: GET the current file

import base64
import os
import time
import requests

API = "https://api.github.com"
OWNER = "your-org"
REPO = "your-repo"
BRANCH = "main"
TOKEN = os.environ["GH_TOKEN"]

HEADERS = {
    "Authorization": f"Bearer {TOKEN}",
    "Accept": "application/vnd.github+json",
    "X-GitHub-Api-Version": "2022-11-28",
}

def get_file_sha(path: str) -> str | None:
    url = f"{API}/repos/{OWNER}/{REPO}/contents/{path}"
    r = requests.get(url, headers=HEADERS, params={"ref": BRANCH}, timeout=15)
    if r.status_code == 404:
        return None          # file does not exist yet -> create
    r.raise_for_status()
    return r.json()["sha"]

A 404 is not an error here. It means you are creating the file, and the PUT omits the sha field.

Step 2: PUT the new content

def put_file(path: str, content: bytes, message: str, sha: str | None) -> dict:
    url = f"{API}/repos/{OWNER}/{REPO}/contents/{path}"
    payload = {
        "message": message,
        "content": base64.b64encode(content).decode("ascii"),
        "branch": BRANCH,
    }
    if sha:
        payload["sha"] = sha

    r = requests.put(url, headers=HEADERS, json=payload, timeout=30)

    # 409 = SHA mismatch, someone else committed. Re-read and retry once.
    if r.status_code == 409:
        fresh = get_file_sha(path)
        payload["sha"] = fresh
        r = requests.put(url, headers=HEADERS, json=payload, timeout=30)

    r.raise_for_status()
    return r.json()

Two details worth noting. First, content must be base64-encoded ASCII, not a Python string of the raw bytes. Second, the 409 retry matters in any pipeline with more than one writer — without it, a concurrent commit turns into a failed deploy.

Step 3: One commit per file, with a sleep

The Contents API commits one file per request. There is no multi-file atomic commit through this endpoint; the Git Data API (/git/blobs + /git/trees + /git/commits) can do that, but it is a lot more code and you rarely need atomicity for a deploy.

Rate limits are the constraint. Authenticated requests get 5000/hour against core. That is generous, but the secondary rate limit is the one that bites: GitHub throttles bursts of content-creating requests, and the documented guidance is to wait at least one second between mutating calls. I use 0.4s in practice for small batches and it has held up, but treat it as a floor, not a target.

def deploy(files: dict[str, bytes], commit_prefix: str) -> None:
    for i, (path, content) in enumerate(files.items(), 1):
        sha = get_file_sha(path)
        msg = f"{commit_prefix}: {path}"
        put_file(path, content, msg, sha)
        print(f"[{i}/{len(files)}] {path} -> {msg}")
        time.sleep(0.4)          # stay well under the secondary limit

If you have hundreds of files, raise the sleep. If you have thousands, switch to the Git Data API and make one commit — the per-request overhead will dominate otherwise.

Why this is also the right fallback when git itself is broken

The firewall story is the trigger, but the same HTTP-only path fixes a second class of problems: machines where git is unavailable or broken.

I have hit all of these on locked-down Windows hosts:

  • Git not installed and no admin rights to install it.
  • Git installed but the corporate proxy intercepts TLS and git refuses the certificate while Python's certifi bundle works fine.
  • Git's credential helper is misconfigured or points at a dead store.
  • A minimal CI container with no git binary at all.

In every case, requests plus a token does the job. The dependency surface shrinks to Python and network access to api.github.com. No SSH keys, no credential helper, no local repository state to get out of sync.

There is a side benefit for reproducibility: the deployment script is self-contained. Anyone can read it and see exactly what it does. There is no hidden .git state, no rebase, no stash. The file content and the commit message are the entire input.

Guarding against a bad deploy

Because the API path bypasses git's safety checks, add your own. A few lines of validation before the PUT saves a lot of pain:

def safe_deploy(files: dict[str, bytes], commit_prefix: str) -> None:
    if not files:
        raise ValueError("nothing to deploy")
    for path, content in files.items():
        if not path or path.startswith("/") or ".." in path:
            raise ValueError(f"unsafe path: {path!r}")
        if not isinstance(content, bytes):
            raise TypeError(f"{path}: content must be bytes")
    deploy(files, commit_prefix)

Also log the returned commit.sha from each PUT. When something goes wrong upstream, that SHA is how you find the exact commit to revert.

Operating notes

A few things that are not obvious until they bite you.

Token scope

Use a fine-grained personal access token scoped to the single repository with Contents: Read and write. Do not use a classic token with repo scope if you can avoid it. Store it in an environment variable or a secrets manager, never in the script.

Rate limit accounting

Each file update costs two requests: one GET for the SHA and one PUT. A 100-file deploy is 200 requests. At 5000/hour that is fine, but if you deploy on every push from multiple machines, watch the X-RateLimit-Remaining header and back off when it drops.

def remaining(r: requests.Response) -> int:
    return int(r.headers.get("X-RateLimit-Remaining", "0"))

Branch protection

If main is protected, the API write will be rejected with a 422 unless the token belongs to a user allowed to bypass, or you target a branch and open a pull request. The Contents API can create a branch by passing a branch that does not exist yet, and then you can open a PR through the Pulls API. That is more machinery than a deploy usually needs, but it is the correct path on a protected repo.

Verifying the write landed

Do not trust the 201 alone. Read the file back through raw.githubusercontent.com, which is a different hostname and therefore a genuinely independent check:

def verify(path: str, expected: bytes) -> bool:
    url = f"https://raw.githubusercontent.com/{OWNER}/{REPO}/{BRANCH}/{path}"
    r = requests.get(url, timeout=15)
    r.raise_for_status()
    return r.content == expected

If raw.githubusercontent.com is also blocked on your network, fall back to a GET on the Contents API and decode the base64. The point is to confirm the content, not to assume it.

Wrapping up

The firewall that blocks github.com but leaves the API open is more common than it sounds, and the fix is smaller than you would expect: probe the endpoints with curl.exe, authenticate against the API, GET the SHA, PUT the base64 content, sleep 0.4s, verify. The same code is the right answer when git is missing, broken, or fighting a TLS-intercepting proxy. The dependency is Python and one reachable hostname.
