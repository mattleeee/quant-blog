Fail-Fast Retry Design for Scheduled Scripts: Three Attempts with Backoff

2026-10-03 Windows Automation

Scheduled scripts fail for boring reasons. A vendor API returns 429 for thirty seconds. A DNS lookup times out once. A socket hangs and gets killed at the OS level. None of these are logic bugs, and none of them deserve a page at 3 a.m.

The fix is a retry wrapper with a narrow scope: three attempts, fixed linear backoff, every attempt logged with its reason. This post covers a decorator implementation, the exit-code conventions that let Task Scheduler (or cron, or a systemd timer) distinguish "failed after retries" from "nothing to do", and why retry state has to live on disk instead of in a module-level variable.

The failure modes you actually see

Before writing the wrapper, it helps to be precise about what you're retrying. In unattended Windows jobs, the recurring ones are:

  • Rate limits. HTTP 429, sometimes 503 with a Retry-After header. Transient by definition.
  • Network blips. ConnectionResetError, requests.exceptions.ConnectionError, transient DNS failures.
  • Timeouts. requests.exceptions.Timeout — connect timeout or read timeout. The request may or may not have been processed server-side, which matters for non-idempotent operations.
  • Upstream 5xx. Usually transient, occasionally not.

And the ones you must not retry:

  • KeyboardInterrupt and SystemExit. These derive from BaseException, not Exception. A bare except: or except Exception: in the wrong place swallows Ctrl-C and makes an interactive debugging session feel broken.
  • Programming errors. KeyError, TypeError, AttributeError on your own data structures. Retrying these three times just triples the log noise before the same crash.
  • 4xx client errors other than 429. A 401 or 400 will not fix itself in ten seconds.

The practical rule: catch requests.RequestException and nothing broader. That covers connection errors, timeouts, and HTTPError from raise_for_status(), and it deliberately excludes everything else.

A decorator that retries the right things

Here is the wrapper. It retries up to three attempts total, waits 10s, then 20s between them, and logs each failure with its reason.

import functools
import logging
import time

import requests

log = logging.getLogger(__name__)

RETRYABLE = (
    requests.exceptions.ConnectionError,
    requests.exceptions.Timeout,
    requests.exceptions.HTTPError,
)

BACKOFF_SECONDS = (10, 20)  # sleeps between attempt 1->2 and 2->3


def retry_request(max_attempts: int = 3, backoff: tuple[int, ...] = BACKOFF_SECONDS):
    """Retry a function on transient requests failures.

    Never catches BaseException, so KeyboardInterrupt and SystemExit
    propagate immediately.
    """
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(1, max_attempts + 1):
                try:
                    result = func(*args, **kwargs)
                    if attempt > 1:
                        log.info("%s succeeded on attempt %d", func.__name__, attempt)
                    return result
                except RETRYABLE as exc:
                    last_exc = exc
                    status = getattr(getattr(exc, "response", None), "status_code", None)
                    # Do not retry 4xx except 429.
                    if status is not None and 400 <= status < 500 and status != 429:
                        log.error("%s failed with non-retryable HTTP %s: %s",
                                  func.__name__, status, exc)
                        raise
                    if attempt == max_attempts:
                        log.error("%s failed after %d attempts: %s",
                                  func.__name__, max_attempts, exc)
                        raise
                    delay = backoff[attempt - 1]
                    log.warning("%s attempt %d/%d failed (%s); retrying in %ds",
                                func.__name__, attempt, max_attempts, exc, delay)
                    time.sleep(delay)
            raise last_exc  # unreachable, but keeps type checkers happy
        return wrapper
    return decorator

A few deliberate choices:

RETRYABLE is a tuple of specific exception classes. requests.RequestException is the parent of all of them, but HTTPError needs the status-code guard above, so listing the concrete classes makes the guard's intent readable. If you prefer one catch-all, catch requests.RequestException and keep the 4xx check.

Backoff is a tuple, not a computed formula. With three attempts you need exactly two sleeps. A tuple makes the schedule explicit and reviewable: 10s, 20s. If you later want jitter, you add it in one place.

KeyboardInterrupt is not caught. It's a BaseException subclass, so it sails through the except RETRYABLE clause and kills the process. Same for SystemExit. This is the entire reason to avoid bare except:.

The 4xx guard runs before the retry decision. A 401 from a rotated API key is not going to resolve itself, and burning 30 seconds of backoff on it delays the alert.

Usage is unremarkable:

@retry_request()
def fetch_positions(session: requests.Session, url: str) -> dict:
    resp = session.get(url, timeout=(5, 15))
    resp.raise_for_status()
    return resp.json()

Note the timeout=(connect, read) tuple. A request with no timeout is the single most common way a "simple" scheduled script hangs forever and blocks its own next run.

Exit codes the scheduler can act on

Task Scheduler and cron both care about one thing: the process exit code. A retry wrapper that always exits 0 hides failures; one that always exits 1 on any error makes "the market was closed" indistinguishable from "the API is down."

Define a small, stable set of codes and use them consistently:

import sys
from enum import IntEnum


class ExitCode(IntEnum):
    OK = 0            # did work, or nothing to do
    NOTHING_TO_DO = 0 # alias: same exit, different log line
    TRANSIENT_FAIL = 1  # failed after retries; safe to alert
    CONFIG_ERROR = 2    # bad credentials, missing file; do not retry
    LOCKED = 3          # another instance holds the run lock

The important distinction is between TRANSIENT_FAIL and NOTHING_TO_DO. Both are "the script ran," but only the first should page someone. A weekend run that finds no data to process should exit 0 with a clear log line, not 1.

The main function wires it together:

def main() -> int:
    try:
        result = run_job()
    except requests.RequestException as exc:
        log.error("job failed after retries: %s", exc)
        return ExitCode.TRANSIENT_FAIL
    except (FileNotFoundError, KeyError) as exc:
        log.error("configuration problem: %s", exc)
        return ExitCode.CONFIG_ERROR

    if result is None:
        log.info("nothing to do")
        return ExitCode.NOTHING_TO_DO
    log.info("processed %d items", result)
    return ExitCode.OK


if __name__ == "__main__":
    sys.exit(main())

Two conventions worth enforcing:

  1. sys.exit(main()), not main() followed by an implicit exit. The return value is the contract with the scheduler.
  2. Never sys.exit(1) inside the retry decorator. The decorator raises; the top-level handler decides the code. Retry logic and exit policy stay separate, so you can change one without touching the other.

If you're on Task Scheduler, map non-zero codes to a failure action (email, webhook) and leave 0 alone. If you're on a systemd timer, OnFailure= units give you the same thing. Either way, the scheduler layer never has to parse your logs to know whether to wake you up.

Why retry state must be re-read from disk

This is the part that bites people.

Suppose a job processes a batch of records and writes a progress marker. A naive implementation keeps the marker in memory:

# Don't do this.
state = {"last_id": 0}

@retry_request()
def process_batch():
    global state
    rows = fetch_since(state["last_id"])
    for row in rows:
        handle(row)
        state["last_id"] = row.id

Now the process is killed mid-batch — power event, Task Scheduler "Stop the task if it runs longer than," a kill -9 from a deploy. The in-memory state is gone. On the next run, last_id is 0 again, and you reprocess everything. If handle() isn't idempotent, you've just double-posted a day of records.

The fix is to treat disk as the source of truth and memory as a cache:

import json
from pathlib import Path

STATE_PATH = Path(r"C:\jobs\state\positions.json")


def load_state() -> dict:
    if not STATE_PATH.exists():
        return {"last_id": 0}
    return json.loads(STATE_PATH.read_text(encoding="utf-8"))


def save_state(state: dict) -> None:
    tmp = STATE_PATH.with_suffix(".tmp")
    tmp.write_text(json.dumps(state), encoding="utf-8")
    tmp.replace(STATE_PATH)  # atomic on Windows and POSIX


@retry_request()
def process_batch():
    state = load_state()          # re-read on every attempt
    rows = fetch_since(state["last_id"])
    for row in rows:
        handle(row)
        state["last_id"] = row.id
        save_state(state)         # persist after each row

Three properties fall out of this:

Retries are safe. If attempt 1 fails halfway through, attempt 2 starts from the last persisted last_id, not from the top. The retry decorator doesn't need to know anything about the job's internals.

Restarts are safe. A new process reads the same file and resumes. There's no warm-up phase where you have to reconstruct state from logs.

The write is atomic. Path.replace() is atomic on Windows (it maps to MoveFileEx with MOVEFILE_REPLACE_EXISTING) and on POSIX. A crash mid-write leaves either the old file or the new one, never a truncated one. Writing directly to STATE_PATH risks a zero-byte file that fails to parse on the next run.

The lock file, and why it's the same problem

The same reasoning applies to preventing overlapping runs. A module-level _running = True flag does nothing across processes. Use a lock file with a PID and timestamp:

import os
from datetime import datetime, timezone

LOCK_PATH = Path(r"C:\jobs\state\positions.lock")


def acquire_lock() -> bool:
    try:
        fd = os.open(LOCK_PATH, os.O_CREAT | os.O_EXCL | os.O_WRONLY)
    except FileExistsError:
        return False
    with os.fdopen(fd, "w") as f:
        f.write(f"{os.getpid()} {datetime.now(timezone.utc).isoformat()}\n")
    return True


def release_lock() -> None:
    LOCK_PATH.unlink(missing_ok=True)

O_CREAT | os.O_EXCL is the atomic test-and-set. The catch is stale locks: if the process dies without releasing, the lock persists. Either record the PID and check whether it's alive, or store a timestamp and treat locks older than the job's maximum runtime as stale. Whichever you pick, make it explicit — an unhandled stale lock silently stops the job forever, which is worse than the overlap you were guarding against.

What this design does not do

It doesn't handle exponential backoff with jitter, circuit breakers, or dead-letter queues. Those are worth adding when you have many jobs sharing one upstream and you need to avoid synchronized retry storms. For a single scheduled script talking to one API, three attempts with 10/20-second waits is the right amount of machinery.

It also doesn't retry non-idempotent writes without thought. If handle(row) sends an email or places an order, a timeout after the server processed the request means a retry duplicates the effect. The persisted last_id helps, but the real fix is an idempotency key on the write itself — a topic for another post.

The pattern to take away: catch narrowly, back off linearly, log every attempt, exit with codes the scheduler understands, and keep state on disk. That covers the boring failures without hiding the interesting ones.
