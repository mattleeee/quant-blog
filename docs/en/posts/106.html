Zombie Positions: When Event-Only Exits Lock a Portfolio Shut

2026-11-19 Quant Trading

A trend-following paper trader sat idle for six weeks. The logs were clean: every scheduled run completed, every position check returned "hold," no errors. The portfolio was full—three positions at the cap—and no new entries could open. The reason: all three positions were zombies. Each had been opened on a bullish EMA crossover and was supposed to close "on the bar where the death cross is detected." One scheduled run fetched candles and failed once. The death cross happened on that bar. The EMAs settled into a stable bearish alignment, and the death-cross event never fired again. The positions lived forever.

This is not a rare edge case. It is a structural bug in any strategy whose exits are defined purely as events. The general lesson is short: events can be missed; states cannot.

The Setup

The strategy is a plain EMA crossover trend follower. Entry: fast EMA crosses above slow EMA. Exit: fast EMA crosses below slow EMA, and you close the long on the bar where that crossover is detected. A three-position cap limits exposure. Position checks run on a schedule, each check fetching recent candles, recomputing indicators, and evaluating the exit condition.

The exit logic, stripped down, looks like this:

def should_exit_event_only(position, candles, fast_period=20, slow_period=50):
    """Exit only when a death cross is detected on the latest bars."""
    closes = [c.close for c in candles]
    fast = ema(closes, fast_period)
    slow = ema(closes, slow_period)

    # Compare the last two bars: a cross is fast going from >= slow to < slow
    prev_fast, prev_slow = fast[-2], slow[-2]
    curr_fast, curr_slow = fast[-1], slow[-1]

    crossed_down = prev_fast >= prev_slow and curr_fast < curr_slow
    return crossed_down

This is the code that looks correct in review. It is also the code that deadlocked the portfolio.

Why the Event Never Fires Again

A crossover is not a condition. It is a transition—a property of the boundary between two adjacent bars. The predicate prev_fast >= prev_slow and curr_fast < curr_slow is true on exactly one bar per crossing. Miss that bar, and the predicate is false on every subsequent bar, forever, because the EMAs are now stably ordered with fast below slow.

The failure mode has three ingredients, and all three are common:

  1. A one-shot trigger. The exit condition is true for a single bar. There is no persistence.
  2. A missed evaluation. A fetch failure, a restart, a timezone bug, a holiday gap, a scheduler hiccup—any of these can skip the bar where the trigger was live. In the incident above, one failed candle fetch was enough.
  3. No reconciliation. Nothing in the system compares the desired state (flat) against the actual state (long). The position check asks "did an exit event occur?" rather than "should this position still exist?"

Once the cross is behind you, the position is unreachable by the exit logic. It is a zombie: alive in the book, invisible to the strategy, and consuming one of three slots. Three zombies and the pool is locked. Entries are rejected by the cap, and every rejection is logged as routine. Nothing in the logs says "stuck"—because from the code's point of view, nothing is wrong.

The nastiest part is the silence. Event-only exits fail open: the absence of an event is indistinguishable from the absence of a reason to exit. A crash gets noticed. A zombie does not.

The Fix: Pair Every Event With a State Fallback

The exit rule should be restated in terms of state, with the event as an optimization:

Close the long when the fast EMA is below the slow EMA. The death-cross event is just the earliest bar on which that state becomes true.

That single reframing fixes the deadlock. The state "fast below slow" persists for as long as the bearish alignment holds, so it cannot be missed by a skipped evaluation. The event remains useful—it fires one bar earlier than a naive state check on the crossing bar—but it is no longer the only path out.

Here is the before/after for the exit block.

Before (event-only):

def should_exit_event_only(position, candles, fast_period=20, slow_period=50):
    closes = [c.close for c in candles]
    fast = ema(closes, fast_period)
    slow = ema(closes, slow_period)

    prev_fast, prev_slow = fast[-2], slow[-2]
    curr_fast, curr_slow = fast[-1], slow[-1]

    return prev_fast >= prev_slow and curr_fast < curr_slow

After (event + state fallback):

def should_exit(position, candles, fast_period=20, slow_period=50):
    """Exit on the death-cross event, or on the persistent bearish state.

    The event is the earliest trigger; the state check guarantees we
    cannot get stuck if the event bar was never evaluated.
    """
    closes = [c.close for c in candles]
    fast = ema(closes, fast_period)
    slow = ema(closes, slow_period)

    prev_fast, prev_slow = fast[-2], slow[-2]
    curr_fast, curr_slow = fast[-1], slow[-1]

    # Event: the earliest possible trigger, fires on the crossing bar.
    crossed_down = prev_fast >= prev_slow and curr_fast < curr_slow

    # State: persistent fallback. True on every bar of bearish alignment.
    bearish_state = curr_fast < curr_slow

    return crossed_down or bearish_state

The or bearish_state term is the whole fix. On the crossing bar, crossed_down is true and the position closes—identical to before. On any later bar where the alignment is still bearish, bearish_state is true and the position closes. On a bar where the fast EMA is above the slow EMA, both terms are false and the position is held. The exit is now a function of the current state, not of having witnessed a transition.

Note what the fallback does not do: it does not change when a correctly evaluated position exits. If every bar is evaluated, the event fires first, and the state term is redundant on that bar. The fallback only matters when a bar was missed—which is exactly the live-trading case it exists to cover.

Why This Doesn't Drift the Backtest

The obvious objection: adding a state condition changes the exit rule, so backtests will diverge from the old results. They won't, in bar-by-bar replay—and it's worth being precise about why.

In a bar-by-bar replay, every bar is evaluated in order. On the bar where the cross occurs, crossed_down is true, so the position closes on that bar. The bearish_state term is also true on that bar, but it changes nothing: the exit already happened. On the next bar, the position is already flat, so the state check is never consulted. The two versions produce identical trade sequences and identical PnL.

The state fallback is therefore backtest-neutral and live-positive. It adds robustness only in the regime where the backtest's assumption—that every bar is observed—breaks down. That is a rare and valuable property: you can deploy the fix without re-validating every historical result, because the historical results are unchanged by construction.

There is one caveat worth stating plainly: this equivalence holds only if your backtest is genuinely bar-by-bar and evaluates the exit on every bar. If your backtest skips bars (for example, it only samples at signal times, or it uses a coarser resampling for speed), then the backtest itself has the same blind spot as production, and you should fix the harness before trusting the equivalence. The property is "no drift under complete evaluation," not "no drift under any evaluation."

Generalizing the Pattern

The event/state pairing is not specific to EMA crossovers. It applies to any exit defined as a transition:

  • Indicator crosses (EMA, MACD, price vs. moving average): exit on the cross event, fall back to "indicator on the wrong side."
  • Threshold breaches (drawdown limits, volatility cutoffs): exit on the breach event, fall back to "threshold currently exceeded."
  • Time-based exits: exit on the scheduled bar, fall back to "holding time exceeds limit." A missed scheduler tick should not extend a position indefinitely.
  • Signal flips from an external model: exit on the flip event, fall back to "current signal disagrees with position direction."

The shape of the fix is always the same. Identify the state that the event is a transition into, and make that state an exit condition in its own right. The event becomes the fast path; the state becomes the guarantee.

A useful discipline is to write every exit rule in two forms and check that they agree:

def exit_rule(position, candles):
    event = exit_event_fired(candles)
    state = exit_state_holds(position, candles)
    # The event should imply the state on the bar it fires.
    assert not event or state, "event fired without state holding"
    return event or state

That assertion is cheap and catches the class of bug where an event is defined more narrowly than the state it is supposed to represent—which is precisely how event-only exits get written in the first place.

A Note on the Position Check

The deadlock also exposed a second gap: nothing reconciled the book against the strategy's intent. A periodic sweep that asks "for each open position, does the current state still justify it?" would have caught the zombies on the first run after the missed bar, regardless of the exit logic. The state fallback makes that sweep unnecessary for this particular rule, but the sweep is still worth having as a backstop for rules you haven't yet refactored. Defense in depth: fix the exit logic, and add a reconciliation check that would notice if the fix ever regresses.

The core lesson stands on its own, though. An exit that depends on witnessing a moment is an exit that can be skipped. An exit that depends on a state is one that cannot. When you write exit logic, ask: if this evaluation never runs on the bar where the condition first becomes true, does the position still close? If the answer is no, you have a zombie waiting to happen—and the fix is to make the state, not the event, the thing the code checks.
