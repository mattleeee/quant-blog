Generating Technical Blog Posts with the DeepSeek API

2026-10-19 API Integration

A daily pipeline that publishes one or two articles per day in two languages, with no human in the loop, has an uncomfortable property: the prompt is not a suggestion, it is the specification. If the prompt is vague, the output is vague, and it goes live. There is no editor to catch a missing code block, an H1 that duplicates the page template, or a 400-word stub that technically satisfies "write an article."

The setup I run is boring on purpose. A Python job assembles a prompt from three parts, calls the DeepSeek API, validates the result, derives an excerpt, and records the publication in a manifest. Everything below is about making each of those steps deterministic enough that "nobody reviews it" stops being a risk.

Anatomy of the Prompt

The prompt has three layers, and the boundaries between them matter.

Layer 1: The fixed persona

The persona is a constant string shared by every article. It sets voice and, more importantly, sets constraints the model can't negotiate away. "Practical engineer, code-first, no fluff" is short, but it's doing real work: it biases the model toward concrete examples and away from the "in today's fast-paced world" register that LLMs default to.

PERSONA = (
    "You are a professional software engineer writing for a technical blog. "
    "Your style is practical, concise, and code-first. You write real problems "
    "and real fixes, never marketing copy. You never pad with filler sentences."
)

Keep this in a module-level constant. If you edit it weekly, you can't attribute changes in output quality to anything.

Layer 2: Hard requirements, numbered

Numbered requirements are easier for the model to follow than prose paragraphs, and easier for you to diff when something goes wrong. Each one should be checkable by a script after the fact.

REQUIREMENTS = """\
1. Output pure Markdown. No HTML, no JSON wrapper, no preamble.
2. Do not use a top-level # heading; the page template renders the title.
3. Use ## and ### headings for structure.
4. Length: 1200-1800 words.
5. Include concrete Python code examples in ```python fenced blocks.
6. Explain methodology only. No disclaimers, no investment advice.
7. Do not recommend any specific trade, coin, or stock.
8. Start directly with the subject; no greetings.
9. Close with one short sentence.
"""

Requirement 2 exists because the model will otherwise start with # {title} roughly every time, and then your rendered page shows the title twice. Requirement 4 is a range, not a minimum, because "write at least 1200 words" invites padding. A range gives the model a ceiling too.

Layer 3: Topic background

This is the part that separates usable drafts from generic ones. If you prompt with only a title, the model writes from its prior — which means plausible-sounding, unspecific, and occasionally invented. A short paragraph of real context ("we run a pipeline that publishes daily in two languages with no reviewer; here's what broke and how we fixed it") anchors the article in evidence. The model stops inventing scenarios and starts explaining the one you handed it.

def build_prompt(title: str, category: str, keywords: list[str],
                 background: str) -> str:
    kw = ", ".join(keywords)
    return f"""{PERSONA}

Write one blog post.

Title: {title}
Category: {category}
Keywords: {kw}

Requirements:
{REQUIREMENTS}

Topic background (write from this; do not invent facts beyond it):
{background}
"""

The background paragraph is the highest-leverage input you control. Write two or three sentences of genuine specifics — what the system does, what failed, what the constraint was — and the draft will carry those specifics through. Leave it out and you get an article about "LLM integration" in general, which nobody needs.

Sampling Parameters

Two knobs matter here: temperature and max_tokens.

For this kind of structured, requirement-heavy output, temperature around 0.7 is the sweet spot. Lower (0.2–0.4) makes the model rigid; it follows the format but the prose flattens into a checklist. Higher (1.0+) starts drifting on the hard requirements — you'll see the H1 come back, or the word count overshoot. 0.7 keeps some variation between the two daily articles while staying compliant.

max_tokens needs headroom. 1200–1800 words is roughly 1600–2400 tokens for English; add the code blocks and you're looking at 3000+ tokens of output. Set max_tokens to 4096 and check the finish reason — if it's length, the article was truncated mid-sentence and must be retried, not published.

import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

def call_model(prompt: str) -> tuple[str, str]:
    resp = client.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.7,
        max_tokens=4096,
    )
    choice = resp.choices[0]
    return choice.message.content, choice.finish_reason

The DeepSeek API is OpenAI-compatible, so the standard client works with a base_url override. That also means the retry logic below is portable to any compatible endpoint.

Retries with Backoff

Timeouts and 5xx responses happen. What you cannot afford is a pipeline that either crashes the whole daily run or silently publishes a half-generated draft. The retry policy needs three properties: bounded attempts, exponential backoff with jitter, and a distinction between retryable and non-retryable failures.

import random
import time

RETRYABLE = (TimeoutError, ConnectionError)

def call_with_retry(prompt: str, attempts: int = 4) -> str:
    last_err = None
    for i in range(attempts):
        try:
            text, finish = call_model(prompt)
            if finish == "length":
                raise ValueError("truncated output")
            return text
        except Exception as e:
            last_err = e
            retryable = isinstance(e, RETRYABLE) or "rate" in str(e).lower()
            if not retryable or i == attempts - 1:
                raise
            delay = (2 ** i) + random.uniform(0, 0.5)
            time.sleep(delay)
    raise RuntimeError("unreachable") from last_err

Two details worth calling out. First, a truncated output (finish_reason == "length") is treated as a failure and retried — publishing a 900-word article that ends mid-sentence is worse than publishing nothing. Second, jitter on the backoff prevents the two language variants from retrying in lockstep and hammering the API at the same instant.

If you generate both languages concurrently, cap the concurrency (a ThreadPoolExecutor(max_workers=2) is fine for two). The rate limit is shared, and a burst of four retries across two languages is how you turn a transient 429 into a sustained one.

Validating the Draft

Requirements are only real if something checks them. A short validator catches the common failures before they reach the site.

import re

def validate(text: str) -> list[str]:
    problems = []
    if re.search(r"^# ", text, flags=re.MULTILINE):
        problems.append("contains H1 heading")
    words = len(re.findall(r"\b\w+\b", text))
    if not 1100 <= words <= 1900:
        problems.append(f"word count {words} out of range")
    if "```python" not in text:
        problems.append("no python code block")
    return problems

The word-count bounds are slightly wider than the prompt's (1100–1900 vs. 1200–1800) to absorb tokenization differences between your counter and the model's. If validation fails, retry once with the problems appended to the prompt; if it fails again, skip the article and log it. A missing article is a recoverable state; a malformed one on the homepage is not.

Deriving the Excerpt

You don't want to pay for a second API call to summarize each article, and you don't want raw Markdown in the meta description. Strip it.

def make_excerpt(markdown: str, limit: int = 160) -> str:
    text = re.sub(r"```.*?```", "", markdown, flags=re.DOTALL)  # drop code
    text = re.sub(r"^#{1,6}\s+.*$", "", text, flags=re.MULTILINE)  # drop headings
    text = re.sub(r"!?\[([^\]]*)\]\([^)]*\)", r"\1", text)  # keep link text
    text = re.sub(r"[*_`>]", "", text)
    text = re.sub(r"\s+", " ", text).strip()
    if len(text) <= limit:
        return text
    cut = text[:limit].rsplit(" ", 1)[0]
    return cut.rstrip(",.;:") + "…"

Dropping code blocks and headings first matters: otherwise the excerpt often starts with a function signature or a section title, which reads badly in a search result. Cutting on a word boundary and trimming trailing punctuation avoids the "…fixes the retry lo…" look.

The Manifest

With no human reviewing, you need a record of what was published, when, and from which prompt. A manifest.json keyed by slug gives you idempotency (the job can check whether today's article already exists and skip), reproducibility (you can see which prompt version produced a given post), and a cheap audit trail.

import json
from datetime import date
from pathlib import Path

MANIFEST = Path("manifest.json")

def load_manifest() -> dict:
    if MANIFEST.exists():
        return json.loads(MANIFEST.read_text(encoding="utf-8"))
    return {}

def record(entry: dict) -> None:
    data = load_manifest()
    data[entry["slug"]] = entry
    MANIFEST.write_text(
        json.dumps(data, indent=2, ensure_ascii=False), encoding="utf-8"
    )

def already_published(slug: str) -> bool:
    return slug in load_manifest()

Each entry should carry at least: slug, title, lang, published_at, word_count, prompt_hash, and model. The prompt_hash is a SHA-256 of the assembled prompt — when a batch of articles suddenly reads differently, you can tell whether the prompt changed or the model did.

import hashlib

def prompt_hash(prompt: str) -> str:
    return hashlib.sha256(prompt.encode("utf-8")).hexdigest()[:12]

Write the manifest after the article file is safely on disk, not before. If the process dies between the two writes, you'd rather re-generate than have a manifest entry pointing at nothing.

Putting the Pieces Together

The daily job is then a straight line: for each (title, language) pair, check the manifest, build the prompt, call with retry, validate, write the file, derive the excerpt, record the entry. The whole thing is maybe 120 lines, and the only part that requires judgment is the topic background — which is exactly where your attention should go, because it's the one input that determines whether the draft is specific or generic.

The pattern generalizes beyond blogging. Any unattended LLM pipeline that produces structured artifacts — reports, changelogs, documentation stubs — benefits from the same shape: fixed persona, numbered checkable requirements, evidence-based background, bounded retries, a validator, and a manifest. The model is the least predictable component, so everything around it should be the most.
