Surviving Corporate HTTPS Interception: Life Behind Sangfor aTrust

2026-10-06 Network & Security

Corporate laptops rarely talk to the internet directly anymore. If you work behind a zero-trust client like Sangfor aTrust, every TLS connection is terminated, inspected, and re-encrypted by a proxy. Your pip install works one day and fails the next. git clone hangs on "server certificate verification failed." Some CLI tools die instantly with CERTIFICATE_VERIFY_FAILED and no useful context.

This is a field guide to figuring out what's happening and getting your tooling back to a working state — without picking a fight with the security team.

What aTrust Actually Does to Your Traffic

aTrust is a zero-trust network access (ZTNA) client. Before it lets you reach anything, it installs a root CA into the OS trust store and routes traffic through a local proxy (often on 127.0.0.1 or a virtual adapter). The proxy performs TLS interception: it opens a connection to the real server, presents its own certificate to your client, and re-encrypts the response back to you.

From the client's point of view, the certificate chain now looks like:

your-client  →  aTrust proxy (presents Sangfor CA-signed cert)  →  real server

The OS-level trust store usually has the Sangfor root CA, so browsers and anything using the system store are fine. Everything else — Python's certifi bundle, Go binaries, Node's bundled CA store, git with its own config — is not.

Step 1: Confirm You're Being Intercepted

Don't guess. Run openssl s_client and look at the issuer:

openssl s_client -connect github.com:443 -servername github.com </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -subject

On a clean network you'd see something like issuer=C=US, O=DigiCert Inc, CN=DigiCert TLS .... Behind aTrust you'll see the Sangfor CA in the issuer field, or a corporate CN that has nothing to do with the site you're connecting to.

Compare against the browser. Open the same site in Chrome or Edge, click the padlock, and inspect the certificate chain. If the browser shows the corporate CA as an intermediate or root but openssl shows a different issuer, you're looking at two different interception layers — or the browser is trusting something the CLI isn't.

A quick Python check that prints both the leaf issuer and whether verification succeeds:

import socket
import ssl

def probe(host: str, port: int = 443) -> None:
    ctx = ssl.create_default_context()
    with socket.create_connection((host, port), timeout=5) as sock:
        with ctx.wrap_socket(sock, server_hostname=host) as tls:
            cert = tls.getpeercert()
            issuer = dict(x[0] for x in cert["issuer"])
            subject = dict(x[0] for x in cert["subject"])
            print(f"host={host}")
            print(f"  subject.CN = {subject.get('commonName')}")
            print(f"  issuer.CN  = {issuer.get('commonName')}")
            print(f"  issuer.O   = {issuer.get('organizationName')}")

probe("github.com")

If issuer.O is your employer or "Sangfor", interception is active. If this throws SSLCertVerificationError, your trust store doesn't have the corporate root — that's the root cause of most CLI failures.

Step 2: Find the Corporate Root CA

You need the actual PEM file, not a screenshot of the certificate. Common locations:

  • Windows: certlm.msc → Trusted Root Certification Authorities → export as Base-64 .cer.
  • macOS: Keychain Access → System Roots → export as PEM.
  • Linux: check /usr/local/share/ca-certificates/ and /etc/ssl/certs/.

On Windows with PowerShell:

Get-ChildItem Cert:\LocalMachine\Root |
  Where-Object { $_.Subject -match "Sangfor|YourCorp" } |
  ForEach-Object {
    $path = "C:\certs\$($_.Thumbprint).cer"
    Export-Certificate -Cert $_ -FilePath $path -Type CERT
    Write-Host "Exported $path"
  }

Convert DER .cer to PEM if needed:

openssl x509 -inform DER -in corp.cer -out corp-root.pem

Keep this file somewhere stable. Don't put it in a repo.

Step 3: Teach Each Tool About the CA

The pattern is always the same: append the corporate root to whatever bundle the tool uses. The tricky part is knowing which bundle that is.

Python requests

requests uses certifi's bundle by default. You have three options, in order of preference:

Option A — environment variable (least invasive):

export REQUESTS_CA_BUNDLE=/path/to/corp-root.pem
export SSL_CERT_FILE=/path/to/corp-root.pem

SSL_CERT_FILE also affects urllib, httpx, and OpenSSL-based tools.

Option B — build a combined bundle so you don't lose the public roots:

import certifi
from pathlib import Path

corp = Path("/path/to/corp-root.pem").read_text()
combined = Path.home() / ".config" / "ca-bundle.pem"
combined.write_text(Path(certifi.where()).read_text() + "\n" + corp)
print(combined)

Then point REQUESTS_CA_BUNDLE at combined. This is the safest approach because you keep both the corporate CA and the public roots.

Option C — per-session verify= when you only need it for one script:

import requests

r = requests.get(
    "https://internal.example.com/api/health",
    verify="/path/to/corp-root.pem",
    timeout=10,
)
print(r.status_code)

Never set verify=False in code that ships. It works, it's a bad habit, and it hides real problems.

git

Git has its own CA configuration and ignores SSL_CERT_FILE on most platforms.

git config --global http.sslCAInfo ~/.config/ca-bundle.pem

Verify with:

GIT_CURL_VERBOSE=1 git ls-remote https://github.com/git/git.git HEAD

If you see SSL certificate problem: unable to get local issuer certificate, the bundle path is wrong or the file isn't PEM. If you see self-signed certificate in certificate chain, you're hitting a proxy that isn't in the bundle at all — usually a second interception layer.

For per-host overrides (rare, but useful when one host uses a different CA):

git config --global http.https://internal.example.com/.sslCAInfo ~/.config/corp-only.pem

pip

pip uses requests under the hood, so REQUESTS_CA_BUNDLE and SSL_CERT_FILE cover it. You can also be explicit:

pip install --cert /path/to/ca-bundle.pem some-package

If you're behind a proxy too, set HTTPS_PROXY and HTTP_PROXY and make sure NO_PROXY includes localhost and any internal hosts.

Node.js

Node ships its own CA store. Set NODE_EXTRA_CA_CERTS:

export NODE_EXTRA_CA_CERTS=/path/to/corp-root.pem

Go

Go uses the system store on most platforms. On Linux it reads /etc/ssl/certs/ca-certificates.crt. Append the corporate root there and run update-ca-certificates. Binaries built with CGO_ENABLED=0 may use a bundled store instead — those need to be rebuilt or run with a custom RootCAs pool.

Step 4: Know What You Cannot Fix

Some tools do certificate pinning and will not accept a corporate CA, period. Examples:

  • Some mobile SDKs and desktop apps that pin to a specific public key.
  • Certain language package managers with hardcoded fingerprints.
  • Hardware tools, VPN clients, and anything with a "secure update" channel.

For these, the honest answer is: don't fight it. If the tool is required for work, escalate to the security team and ask for a documented exception or an internal mirror. If it's not required, find an alternative that respects the system trust store.

Step 5: Route Around Blocked Hosts Politely

Sometimes the problem isn't TLS — it's that a host is blocked outright. Before you do anything clever, check whether the block is policy or just a missing route.

curl with verbose output tells you a lot:

curl -v --max-time 10 https://blocked.example.com/ 2>&1 | head -30
  • Connection timed out → network-level block.
  • 403 from a proxy → policy block.
  • SSL certificate problem → interception, not blocking.

If it's a policy block, the polite move is to use an approved path: an internal mirror, a corporate artifact registry, or a documented proxy exception. Setting up a personal tunnel to bypass corporate controls is a fast way to lose your laptop and your job. Don't.

If it's a routing issue (e.g., an internal host isn't in the split-tunnel list), the fix belongs with the network team. File a ticket with the exact curl -v output and the destination IP. That gets resolved faster than any workaround.

A Small Diagnostic Script

Here's a script I keep around for the "is it just me?" moments:

import socket
import ssl
import sys

HOSTS = ["github.com", "pypi.org", "registry.npmjs.org"]

def check(host: str) -> str:
    try:
        ctx = ssl.create_default_context()
        with socket.create_connection((host, 443), timeout=5) as sock:
            with ctx.wrap_socket(sock, server_hostname=host) as tls:
                cert = tls.getpeercert()
                issuer = dict(x[0] for x in cert["issuer"])
                return f"OK   {host:30} issuer={issuer.get('commonName')}"
    except ssl.SSLCertVerificationError as e:
        return f"CERT {host:30} {e.verify_message}"
    except (socket.timeout, OSError) as e:
        return f"NET  {host:30} {e}"

for h in HOSTS:
    print(check(h))

Run it once on the corporate network and once on a hotspot. The diff tells you whether you're dealing with interception, a bad bundle, or a genuine outage.

The Mental Model

Three layers, in order:

  1. OS trust store — browsers and native apps use this. Usually fine.
  2. Per-tool CA bundles — certifi, Node, Go, Git. This is where things break.
  3. Certificate pinning — nothing you can do client-side. Escalate.

Fix layer 2 by appending the corporate root to the bundle each tool actually reads. Use environment variables where possible so you don't mutate installed packages. Keep a combined bundle so you don't lose public roots. And when a host is blocked by policy, go through the approved channel — the security team is not the enemy, and the workaround is rarely worth the fallout.
