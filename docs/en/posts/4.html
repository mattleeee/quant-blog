Staggering Nine Scheduled Tasks to Eliminate Resource Contention

2026-10-03 Windows Automation

Scheduled tasks are cheap to create and expensive to forget. A Windows box running a dozen Python jobs looks fine on paper until two of them wake up at the same minute, hit the same JSON state file, and one silently loses its write. That is exactly what happened here: a market-signal job and a data-refresh job both fired at the top of every hour. The signal job read a price snapshot while the refresh job was halfway through rewriting it. Neither crashed. The signal job just computed on stale data for a while, and nobody noticed until the numbers stopped matching the dashboard.

The fix was not more hardware or a rewrite. It was a timetable: a deliberate offset schedule where each job gets its own slot and nothing collides. This post covers how to inventory your existing triggers, how to space CPU-bound and I/O-bound jobs, how to avoid file-lock hazards, and how to keep the whole fleet visible on one page.

Step 1: Inventory every trigger before you touch anything

You cannot stagger what you cannot see. On Windows, scheduled tasks live in the Task Scheduler, but they can also be created by schtasks, by Python's schedule library inside a long-running process, or by a cron-like loop in a service. Start by dumping everything to a single table.

The most reliable inventory comes from the Task Scheduler's own XML, because it includes the exact repetition interval, not just the "next run time" the GUI shows.

import subprocess
import xml.etree.ElementTree as ET
from dataclasses import dataclass, field
from datetime import datetime

@dataclass
class TaskInfo:
    name: str
    triggers: list[str] = field(default_factory=list)
    action: str = ""
    enabled: bool = True

def list_tasks() -> list[TaskInfo]:
    raw = subprocess.run(
        ["schtasks", "/query", "/xml", "ONE"],
        capture_output=True, text=True, check=True,
    ).stdout

    tasks = []
    # schtasks emits multiple <Task> documents concatenated; wrap them.
    wrapped = f"<Root>{raw}</Root>"
    root = ET.fromstring(wrapped)

    ns = {"t": "http://schemas.microsoft.com/windows/2004/02/mit/task"}
    for task in root.findall("t:Task", ns):
        name_el = task.find(".//t:RegistrationInfo/t:URI", ns)
        name = name_el.text if name_el is not None else "unknown"

        triggers = []
        for trig in task.findall(".//t:Triggers/*", ns):
            # CalendarTrigger with a Repetition/Interval is the usual culprit
            interval = trig.find(".//t:Repetition/t:Interval", ns)
            start = trig.find(".//t:StartBoundary", ns)
            parts = [trig.tag.split("}")[-1]]
            if start is not None:
                parts.append(f"start={start.text}")
            if interval is not None:
                parts.append(f"every={interval.text}")
            triggers.append(" ".join(parts))

        exec_el = task.find(".//t:Actions/t:Exec/t:Command", ns)
        action = exec_el.text if exec_el is not None else ""

        enabled_el = task.find(".//t:Settings/t:Enabled", ns)
        enabled = enabled_el is None or enabled_el.text.lower() == "true"

        tasks.append(TaskInfo(name, triggers, action, enabled))

    return tasks

if __name__ == "__main__":
    for t in list_tasks():
        flag = "" if t.enabled else "  [DISABLED]"
        print(f"{t.name}{flag}")
        print(f"    action: {t.action}")
        for trig in t.triggers:
            print(f"    trigger: {trig}")

Run this once a week and diff the output. New tasks appear when you least expect them — an installer, a sync tool, a "temporary" script someone added six months ago. The diff is your early warning.

What you are looking for is the minute field. A task that repeats every hour at 00:00 and another that repeats every hour at 00:00 will always collide. A task that repeats every 15 minutes at 00:00 collides with both, four times an hour.

Step 2: Classify jobs as CPU-bound or I/O-bound

Spacing rules depend on what the job actually does, not on how long it usually takes. A job that pegs all cores for 40 seconds is a different problem from a job that waits on HTTP for 40 seconds.

The distinction matters because CPU-bound jobs contend for a shared resource that cannot be queued away — the cores. I/O-bound jobs contend for the file system, network sockets, and the GIL, but they spend most of their wall-clock time not running. Two I/O-bound jobs can overlap almost harmlessly. Two CPU-bound jobs cannot.

A quick way to classify a job is to measure its CPU time against its wall time. If the ratio is high, it is CPU-bound.

import subprocess
import time

def profile_job(command: list[str]) -> dict:
    start = time.perf_counter()
    proc = subprocess.run(command, capture_output=True, text=True)
    wall = time.perf_counter() - start

    # On Windows, use the process's own accounting via a wrapper if needed.
    # For a rough ratio, compare wall time against a known CPU baseline.
    return {
        "wall_seconds": round(wall, 2),
        "returncode": proc.returncode,
        "cpu_ratio_estimate": "high" if wall < 1.0 else "low",
    }

For a more accurate number, run the job under time on Linux or use Get-Process / Process.TotalProcessorTime on Windows. The point is not precision. The point is knowing which jobs will fight each other.

Rules of thumb that held up in practice:

  • CPU-bound jobs get at least 15 minutes of separation. A job that saturates the box for two minutes will still be flushing its caches and releasing file handles for a while after. Fifteen minutes is cheap insurance.
  • I/O-bound jobs can overlap, but not on the same files. Two jobs hitting different APIs at the same minute is fine. Two jobs reading and writing the same directory is not.
  • Jobs that touch the same state file must never overlap at all. This is not a spacing preference; it is a correctness requirement. More on this below.
  • Leave one slot per hour empty. If you have three hourly jobs, do not pack them at :00, :05, :10. Put them at :00, :20, :40 so a slow run has room to finish before the next one starts.

Step 3: The file-lock hazard

The original failure was not CPU contention. It was two processes writing the same JSON file. On Windows, open(path, "w") truncates the file immediately, before any data is written. If a reader opens the file in that window, it sees an empty file or a partial one. Python's json.load then raises JSONDecodeError, or worse, succeeds on a truncated-but-valid fragment.

There are three ways to handle this, in increasing order of robustness.

Option A: Atomic writes via a temp file and rename

Write to a temporary file in the same directory, then os.replace it over the target. os.replace is atomic on Windows and POSIX, so readers either see the old file or the new one, never a partial write.

import json
import os
import tempfile
from pathlib import Path

def atomic_write_json(path: Path, data: dict) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    fd, tmp_name = tempfile.mkstemp(
        dir=path.parent, prefix=path.name, suffix=".tmp"
    )
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as f:
            json.dump(data, f, indent=2)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp_name, path)
    except BaseException:
        os.unlink(tmp_name)
        raise

This eliminates the truncation window entirely. It does not eliminate the lost update problem: if two jobs read, modify, and write the same file, the second writer overwrites the first writer's changes. Atomicity is not isolation.

Option B: A lock file with a timeout

If two jobs genuinely need to mutate the same state, serialize them with a lock. On Windows, use msvcrt.locking or a simple O_CREAT | O_EXCL lock file with a stale-lock timeout.

import time
from pathlib import Path

class FileLock:
    def __init__(self, path: Path, timeout: float = 30.0):
        self.path = path
        self.timeout = timeout

    def __enter__(self):
        deadline = time.monotonic() + self.timeout
        while True:
            try:
                self.path.touch(exist_ok=False)
                return self
            except FileExistsError:
                if time.monotonic() > deadline:
                    raise TimeoutError(f"lock held: {self.path}")
                time.sleep(0.5)

    def __exit__(self, *exc):
        self.path.unlink(missing_ok=True)

The timeout matters. A crashed job that leaves a lock file behind will block every subsequent run until someone notices. Thirty seconds is usually enough for a job that finishes in two.

Option C: Do not share the file

The cleanest fix is architectural: give each job its own file and have a single consumer merge them. The signal job writes signals.json. The refresh job writes prices.json. A separate aggregation step reads both. No lock, no contention, no lost updates.

This is the option to reach for first. Locks are a symptom of two jobs that should not have been coupled.

Step 4: The one-page timetable

After inventorying and classifying, the schedule becomes a table. Here is the actual layout that resolved the collision, with the reasoning in the last column.

Time Job Type Why this slot
HH:00 Market signal computation CPU-bound Top of hour, isolated; nothing else runs here
HH:30 Data refresh (API pull) I/O-bound Offset from signals by 30 min; writes prices.json only
04:30 Heavy daily maintenance CPU-bound Night window, no market activity, full core budget
09:00 Blog publishing I/O-bound After maintenance, before the 10:30 slot
10:30 Second language site publish I/O-bound Offset from blog by 90 min; shares template cache

The market signal job still runs every hour at :00. The data refresh now runs at :30, so it never reads a snapshot that is being rewritten. The heavy maintenance job moved from midnight — where it collided with the first hourly signal — to 04:30. Blog publishing and the second language site are 90 minutes apart, which is more than the template cache needs to settle.

The timetable lives in a single Markdown file in the repo, and the actual task definitions are generated from it. That way the document and the scheduler cannot drift apart.

import subprocess
from dataclasses import dataclass

@dataclass
class ScheduleEntry:
    name: str
    time: str          # "HH:MM" or "HH:30" for repeating
    command: str
    repeat_minutes: int | None = None

SCHEDULE = [
    ScheduleEntry("MarketSignals", "00:00", "python -m jobs.signals", 60),
    ScheduleEntry("DataRefresh", "00:30", "python -m jobs.refresh", 60),
    ScheduleEntry("HeavyMaintenance", "04:30", "python -m jobs.maintenance"),
    ScheduleEntry("BlogPublish", "09:00", "python -m jobs.blog"),
    ScheduleEntry("SecondLangPublish", "10:30", "python -m jobs.blog_alt"),
]

def install(entry: ScheduleEntry) -> None:
    args = [
        "schtasks", "/Create", "/F",
        "/TN", f"CodeQuant\\{entry.name}",
        "/TR", entry.command,
        "/SC", "DAILY" if entry.repeat_minutes is None else "MINUTE",
        "/ST", entry.time,
    ]
    if entry.repeat_minutes:
        args += ["/MO", str(entry.repeat_minutes)]
    subprocess.run(args, check=True)

if __name__ == "__main__":
    for e in SCHEDULE:
        install(e)
        print(f"installed {e.name} at {e.time}")

Two things to note. First, schtasks /SC MINUTE /MO 60 with /ST 00:30 produces a job that runs at 00:30, 01:30, 02:30, and so on — the offset is preserved. Second, the /F flag overwrites an existing task, so re-running this script is idempotent. That makes the timetable the single source of truth.

What to check after you stagger

Staggering is not a one-time fix. Verify it holds:

  • Log the start and end time of every job. If a job's end time creeps into the next job's start time, the spacing is too tight.
  • Alert on lock timeouts. A TimeoutError from the lock means two jobs overlapped. That is a scheduling bug, not a runtime bug.
  • Re-run the inventory monthly. Tasks multiply. The diff catches the ones you forgot.
  • Keep the timetable in version control. If the schedule lives only in the Task Scheduler GUI, it is invisible and undocumented.

The original problem — two jobs at the top of every hour — took about twenty minutes to diagnose and ten minutes to fix. The expensive part was the weeks of subtly wrong numbers before anyone noticed. A one-page timetable and a thirty-minute offset would have prevented all of it.
