GB28181 Camera Cascading: When SIP INVITE Never Arrived

2026-10-07 Network & Security

A school's camera system cascades to a provincial education video platform through a Hikvision NCG (Network Camera Gateway). The platform dashboard showed the device as online — green light, heartbeat timestamps updating every few seconds. But when an operator clicked "Playback" in the provincial client, nothing happened. No video, no error, no timeout message. Just a spinner that eventually gave up.

This is one of the more frustrating failure modes in GB28181 deployments because the monitoring layer says everything is fine. The device is registered. The keepalive is flowing. The platform considers the camera healthy. Yet the actual media session never establishes.

The debugging path here is a good case study in how to isolate a network problem from an application problem, and how to produce evidence that a firewall engineer can act on without a three-hour conference call.

GB28181 Signaling: Two Very Different Flows

GB28181 runs SIP over UDP (usually port 5060) for signaling, and RTP over UDP for media. But the signaling itself splits into two distinct patterns that behave very differently on a firewall.

Heartbeat: REGISTER and Keepalive

The device periodically sends a SIP REGISTER message to the platform. The platform responds with 200 OK. Between registrations, the device sends keepalive packets — often a SIP MESSAGE or a custom heartbeat — at a shorter interval, typically every 5 to 60 seconds depending on configuration.

These packets are small. A typical REGISTER is 400–600 bytes. A keepalive MESSAGE is even smaller. They are also initiated by the device, which means they create a stateful entry in the firewall's connection tracking table. The firewall sees an outbound UDP packet from the school network to the platform IP, and it allows the return traffic.

This is why the platform sees the device as online. The heartbeat path works. The firewall has an open pinhole for that specific UDP flow.

INVITE: The Platform-Initiated Session

When the operator clicks Playback, the platform sends a SIP INVITE to the device. This is the critical difference: the INVITE is initiated by the platform, not the device. It travels from the platform IP to the school's public IP, and then must be forwarded to the NCG's internal address.

The INVITE is larger — often 800–1200 bytes because it carries SDP with media negotiation parameters. If the platform doesn't get a response, it retransmits. After a few retries, it gives up.

The problem in this case: the INVITE never arrived at the NCG. Not the first attempt, not the retries.

The tcpdump Evidence

The engineer ran tcpdump on the NCG server for 3.5 minutes while the operator repeatedly pressed Playback. The capture showed:

  • Heartbeat packets in both directions, every few seconds, exactly as expected.
  • Zero SIP INVITE packets. Not a single one.
  • On the platform side, the platform's own capture showed 16 retry bursts of roughly 950 bytes each — the INVITE retransmissions.

This is the key diagnostic split. The platform sent the INVITEs. The NCG never saw them. The packets died somewhere between the platform's egress and the NCG's ingress. That narrows the fault domain to the school firewall, an upstream router, or a NAT device in between.

Placing tcpdump Correctly

Where you run tcpdump determines what you can conclude. The mistake many people make is running it on the wrong interface or with a filter that misses the relevant traffic.

On the NCG

The NCG is the device that should receive the INVITE. Capture on the interface facing the upstream network (the WAN side), not the LAN side. If the NCG has a single NIC, capture on that.

# Capture SIP traffic on the WAN interface, write to file for analysis
tcpdump -i eth0 -n -s 0 -w /tmp/gb28181_capture.pcap 'udp port 5060'

The -s 0 ensures full packet capture. SIP messages can be large, and truncating them loses SDP details. The -n avoids DNS lookups that slow down capture. Writing to a file lets you analyze later with Wireshark.

On the Platform Side

If you have access to the platform server, capture there too. This gives you the other half of the conversation. You want to confirm the platform actually sent the INVITE and see the retry pattern.

# On the platform, capture traffic to/from the school's public IP
tcpdump -i any -n -s 0 -w /tmp/platform_capture.pcap \
  'udp port 5060 and host 203.0.113.45'

Replace 203.0.113.45 with the school's public IP. The -i any captures on all interfaces, which is useful when you're not sure which interface the traffic uses.

What to Look For

In the NCG capture, you want to see:

  • Heartbeat packets: source = NCG internal IP, destination = platform IP, port 5060.
  • Any inbound SIP from the platform IP. If this is empty, the INVITE never arrived.

In the platform capture, you want to see:

  • Outbound INVITE to the school's public IP.
  • Retransmissions at increasing intervals (typically 500ms, 1s, 2s, 4s...).
  • No response from the school side.

The combination proves the packets left the platform and never reached the NCG. The firewall or an upstream device is dropping them.

Why the Firewall Drops the INVITE

Several mechanisms can cause this. The heartbeat path works because it's outbound-initiated and the firewall's stateful tracking allows the return traffic. The INVITE is inbound-initiated, and the firewall has no existing state for it.

Missing Inbound Rule

The most common cause: the firewall has no rule allowing inbound UDP 5060 from the platform IP to the NCG. The heartbeat works because outbound traffic is allowed by default, and the return path is permitted by connection tracking. But a new inbound session from the platform is blocked.

NAT and Port Mapping

If the school is behind NAT, the platform sends the INVITE to the school's public IP on port 5060. The NAT device needs a port-forwarding rule to send that traffic to the NCG's internal IP. Without it, the packet arrives at the NAT device and is dropped because there's no mapping.

Asymmetric Routing

Sometimes the INVITE arrives at the firewall, but the firewall routes it out a different interface than the one the heartbeat uses. If the return path is asymmetric, the firewall may drop the packet as part of its stateful inspection.

SIP ALG Interference

Some firewalls have a SIP ALG (Application Layer Gateway) enabled. The ALG inspects SIP traffic and tries to rewrite headers. If it doesn't understand the GB28181 message format — which is common, since GB28181 uses SIP in non-standard ways — it may drop the packet or mangle it.

Building the Evidence Pack

The goal is to hand the firewall engineer a package that lets them find the rule or the drop without needing to reproduce the issue. Here's what to include:

1. Packet Captures from Both Sides

The NCG capture showing heartbeats but no INVITE. The platform capture showing INVITE retries with no response. Name the files clearly with timestamps.

2. A Timeline

A simple table showing when the operator pressed Playback, when the platform sent the INVITE, and what the NCG saw. This helps correlate the two captures.

3. The Exact 5-Tuple

The firewall engineer needs to know exactly what traffic to look for:

  • Source IP: platform IP
  • Source port: platform SIP port (often 5060, but can be ephemeral)
  • Destination IP: school public IP
  • Destination port: 5060
  • Protocol: UDP

4. A Python Script to Extract the Relevant Packets

If you want to make their life easier, provide a script that filters the capture and prints the relevant packets. Here's one using scapy:

from scapy.all import rdpcap, UDP, IP
from datetime import datetime

def analyze_gb28181_capture(pcap_file, platform_ip, ncg_ip):
    """
    Analyze a pcap for GB28181 signaling issues.
    Prints heartbeat traffic and flags missing INVITEs.
    """
    packets = rdpcap(pcap_file)

    heartbeats = []
    invites = []

    for pkt in packets:
        if IP not in pkt or UDP not in pkt:
            continue

        src = pkt[IP].src
        dst = pkt[IP].dst
        sport = pkt[UDP].sport
        dport = pkt[UDP].dport

        # SIP traffic on port 5060
        if sport != 5060 and dport != 5060:
            continue

        payload = bytes(pkt[UDP].payload)

        # Check for SIP method in payload
        if b'INVITE' in payload[:100]:
            invites.append({
                'time': datetime.fromtimestamp(float(pkt.time)),
                'src': src,
                'dst': dst,
                'size': len(pkt)
            })
        elif b'REGISTER' in payload[:100] or b'MESSAGE' in payload[:100]:
            heartbeats.append({
                'time': datetime.fromtimestamp(float(pkt.time)),
                'src': src,
                'dst': dst,
                'size': len(pkt)
            })

    print(f"Total packets: {len(packets)}")
    print(f"Heartbeat/REGISTER packets: {len(heartbeats)}")
    print(f"INVITE packets: {len(invites)}")
    print()

    if heartbeats:
        print("First heartbeat:", heartbeats[0]['time'])
        print("Last heartbeat:", heartbeats[-1]['time'])
        print()

    if not invites:
        print("WARNING: No INVITE packets found in this capture.")
        print("If the platform sent INVITEs, they are being dropped")
        print("before reaching this capture point.")
    else:
        for inv in invites:
            print(f"INVITE at {inv['time']} from {inv['src']} "
                  f"to {inv['dst']} ({inv['size']} bytes)")

    return {
        'heartbeats': heartbeats,
        'invites': invites
    }

# Usage
result = analyze_gb28181_capture(
    '/tmp/gb28181_capture.pcap',
    platform_ip='198.51.100.10',
    ncg_ip='192.168.1.100'
)

This script gives the firewall engineer a quick summary without needing to open Wireshark. It confirms the heartbeat is present and the INVITE is absent, which is the core evidence.

5. A Request for Specific Logs

Ask the firewall engineer to check:

  • Drop logs for UDP 5060 from the platform IP to the school public IP.
  • NAT session table for any existing mapping to the NCG.
  • SIP ALG status and whether it's enabled for this traffic.

Fixing the Firewall

Once the evidence is in hand, the fix is usually straightforward:

  1. Add an inbound rule allowing UDP 5060 from the platform IP to the NCG's internal IP.
  2. Add a NAT port-forward if the school is behind NAT, mapping the public IP:5060 to the NCG's internal IP:5060.
  3. Disable SIP ALG if it's enabled, since GB28181's SIP usage often confuses ALG implementations.
  4. Verify the return path is symmetric — the NCG's response to the INVITE should go out the same interface the INVITE arrived on.

After the fix, re-run the capture on both sides. You should see the INVITE arrive at the NCG, the NCG respond with 200 OK, and the media session establish.

The Broader Lesson

GB28181 cascading failures often masquerade as application problems because the heartbeat creates a false sense of connectivity. The heartbeat proves the device can reach the platform, but it says nothing about whether the platform can reach the device. Those are two different firewall paths, and only one of them is exercised by the heartbeat.

When you see "online but no video," the first question is always: did the INVITE arrive? If you can't answer that with a packet capture, you're guessing. And guessing at firewall rules without evidence wastes everyone's time.

The evidence pack approach — captures from both sides, a timeline, the exact 5-tuple, and a script to summarize it — turns a vague "video doesn't work" ticket into a specific, actionable request. The firewall engineer doesn't need to understand GB28181. They just need to know which packets to allow.
