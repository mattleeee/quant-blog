The Paper Trader That Stopped Trading: Debugging a Silent Filter Chain

2026-11-18 Quant Trading

A short-trading paper account sat idle for four months. Zero trades. The first explanation everyone reaches for is "no setups" or "the conditions are too strict," and it's a comfortable explanation because it requires no work to accept. It was also wrong.

I replayed the scanner offline: 24 coins from the decline list, four months, 720 4h candles each. The hard entry conditions—EMA8 < EMA21 and price < EMA200—held on about 35% of evaluated bars. That works out to roughly one qualified short signal per day. The signal supply was healthy the entire time. The problem was downstream: the chain that consumes signals was dropping almost all of them before they could become orders.

This post is about how I found the two breakages, why both were invisible in production logs, and the instrumentation I added so the next silent failure announces itself.

The Funnel Model

A signal funnel is the sequence of stages a raw condition passes through before it becomes an order:

bar close -> hard conditions -> soft filters -> delayed confirmation -> risk sizing -> order

The useful property of a funnel is that you can measure each stage independently. If 100 signals enter a stage and 3 exit, either that stage is doing its job or it's broken—but you can't tell which until you count. My mistake was treating the funnel as a black box and reasoning about it from the outside ("the account isn't trading, so setups must be rare").

The replay harness made each stage countable. The core of it is deliberately boring:

from dataclasses import dataclass, field

@dataclass
class FunnelStats:
    evaluated: int = 0
    hard_pass: int = 0
    soft_pass: dict = field(default_factory=dict)
    confirm_pass: int = 0
    confirm_none: int = 0
    confirm_false: int = 0

    def report(self):
        print(f"bars evaluated:      {self.evaluated}")
        print(f"hard conditions:     {self.hard_pass} "
              f"({self.hard_pass / max(self.evaluated, 1):.1%})")
        for name, (passed, total) in self.soft_pass.items():
            print(f"  soft filter {name:<10} {passed}/{total} "
                  f"(removed {1 - passed / max(total, 1):.1%})")
        print(f"confirmation pass:   {self.confirm_pass}")
        print(f"confirmation None:   {self.confirm_none}")
        print(f"confirmation False:  {self.confirm_false}")

Run this over historical bars and the funnel stops being a story you tell yourself and becomes a column of numbers.

Culprit 1: The Timeframe Mismatch

The signal was generated on the 4h timeframe. The design then called for a "delayed confirmation" two hours later: before acting, re-check the trend condition. Sensible idea in principle—it guards against acting on a bar that immediately reverses.

But the confirmation helper re-checked the condition on 15m EMA8/EMA21, not 4h. On a 15-minute chart, a fast and slow EMA cross each other constantly. The 4h condition EMA8 < EMA21 might hold for days; the 15m version of the same condition flips every few hours. So signals that were valid on the timeframe that generated them were being re-validated on a timeframe with entirely different dynamics, and most failed.

The replay quantified it: of bars that passed the hard conditions, the overwhelming majority died at the confirmation stage. The confirmation wasn't confirming anything—it was a second, unrelated filter with a much higher rejection rate, masquerading as a safety check.

The fix is to make the confirmation timeframe explicit and tied to the signal's timeframe, not hardcoded somewhere in a helper:

def confirm_trend(signal, candles_by_tf, tf):
    """Re-check the trend condition on the SAME timeframe that produced the signal."""
    candles = candles_by_tf[tf]
    ema_fast = ema(candles["close"], 8)
    ema_slow = ema(candles["close"], 21)
    return bool(ema_fast[-1] < ema_slow[-1])

# The signal carries its own timeframe; confirmation must use it.
tf = signal.timeframe          # "4h"
result = confirm_trend(signal, candles_by_tf, tf)

If a confirmation genuinely needs a different timeframe, that's fine—but it should be a deliberate, documented decision with its own pass-rate measured, not an accident of which helper got called.

Culprit 2: None Treated as False

The second bug was worse because it was silent. The confirmation helper does I/O—it fetches candles. On a network error it returned None. The caller did this:

if not confirm_trend(...):
    stats.rejected += 1
    return  # discard signal

not None is True. So a failed fetch was indistinguishable from a failed confirmation. Every network hiccup quietly deleted a signal, and nothing was logged. In a paper environment with occasional flaky connectivity, this alone can account for a large share of the missing trades—and it's invisible, because from the outside "no signal" and "signal discarded after failed fetch" look identical.

The principle I settled on: only an explicit False blocks a signal. None means "couldn't verify," and the correct behavior for an unverifiable confirmation is to let the signal through (or, if you prefer, to queue it for retry)—never to treat it as a rejection. A filter that can't run is not a filter that said no.

def gate(signal, confirm_fn):
    result = confirm_fn(signal)
    if result is False:
        log.info("signal %s rejected: confirmation False", signal.id)
        return "rejected"
    if result is None:
        log.warning("signal %s: confirmation unavailable, passing through", signal.id)
        return "passed_unverified"
    return "passed"

Two changes matter here. First, the three-valued logic: True / False / None are distinct outcomes. Second, the log.warning on None—every unverified pass is recorded, so a spike in network errors shows up as a spike in warnings rather than as a mysterious absence of trades.

The Exonerated Filter

While instrumenting, I also measured the RSI filter, which everyone suspected. RSI < 35 as an oversold condition removed only 10.5% of otherwise-qualified signals. It was doing almost nothing—neither helping nor hurting. That number is worth having: it means the RSI filter was never the reason for the drought, and I could stop tuning it. Without per-stage counts, it would have stayed a prime suspect and absorbed hours of pointless parameter tweaking.

This is the general lesson: when a funnel produces nothing, measure every stage before changing any of them. The stage you're most tempted to loosen is often not the one that's blocking.

Rules for Filter Chains

From this episode I now apply four rules to any signal pipeline:

  1. Every filter branch logs. A branch that discards a signal without a log line is a bug waiting to be discovered by an empty trade log. No silent return.
  2. Distinguish "no" from "don't know." Use three-valued results (True/False/None) and handle None explicitly. Never let a falsy default absorb an error.
  3. Match timeframes deliberately. A confirmation must run on the signal's timeframe unless a different one is chosen on purpose, with its pass rate measured.
  4. Count at every stage. Persist per-stage counts (evaluated, passed, rejected-by-reason, errored) and alert when a stage's pass rate moves outside its historical band. A stage that suddenly passes 0% is as alarming as one that passes 100%.

The instrumentation itself is small—a counter dict and a few log lines—but it converts the funnel from an opaque "it just doesn't trade" into a sequence of measurable gates. When the account went quiet, the counters would have shown the drop at the confirmation stage within a day, and the None warnings would have pointed straight at the network handling.

What Changed in Practice

After unifying the confirmation timeframe to 4h and treating None as pass-through-with-warning, the funnel began consuming the signals it was always receiving. The hard-condition supply never changed—roughly one qualified signal per day across the decline list—but the signals now reached the order stage instead of dying in a helper function.

The broader point isn't about this particular strategy. It's that a trading system's failure mode is usually not "the market stopped offering setups." It's a filter chain that broke somewhere in the middle and told no one. Build the funnel so that every gate reports what it did, and the next silent failure will be loud.
