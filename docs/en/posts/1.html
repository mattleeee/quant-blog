Why I Replaced Daemon Processes with Windows Task Scheduler

2026-10-02 Windows Automation

The first sign was a silent one. A Python process that polled a data source every minute and wrote to a local SQLite file simply stopped. No traceback in the log file, no crash dump, no entry in the Windows Event Log beyond the usual noise. The process was gone, and nothing on the machine seemed to care.

This happened on a corporate Windows 10 box — the kind where you have local admin rights but not really, where antivirus and endpoint protection run at a kernel level, and where the security suite (Sangfor aTrust, in this case) watches process creation with more interest than you would like. The Python job was a straightforward daemon: a while True loop with a time.sleep(60), launched at logon via a shortcut in the Startup folder. It had run fine for weeks. Then it started dying every few hours, always when it spawned a child process.

This post is about what actually caused it, why the obvious fix (a watchdog) also failed, and how moving every recurring job to Windows Task Scheduler turned a fragile setup into something that survives reboots, retries on failure, and reports its own exit codes.

Symptoms of an intercepted child process

The daemon was not crashing on its own logic. The pattern was specific: it died whenever it called subprocess.run() to invoke a helper script. The helper would start, run for a fraction of a second, and then the parent would vanish. No exception was raised in the parent — the process was terminated externally.

If you have ever debugged this, you know the checklist:

  • pythonw.exe disappears from Task Manager with no error dialog.
  • The log file ends mid-operation, often right after a subprocess.Popen call.
  • Get-Process in PowerShell shows nothing.
  • Windows Event Viewer shows nothing under Application, but you may see entries under Microsoft-Windows-Security-Auditing if auditing is enabled.
  • Restarting the daemon works — for a while.

The aTrust client on these machines enforces a process-creation policy. It does not block python.exe itself, and it does not block the helper script when run manually. But when a long-running Python process spawns a child, the security suite sometimes flags the pattern as suspicious and terminates the entire process tree. The daemon's own keep-alive watchdog — a second Python process that checked every 30 seconds whether the first was alive and restarted it — was also a child process of the same shell, and it got killed too. Two daemons, one policy, zero survivors.

The lesson: in a locked-down enterprise environment, you cannot assume that a process you start will stay started. You need something outside your process tree that the security suite trusts.

Why Task Scheduler survives where daemons do not

Windows Task Scheduler is a first-class OS component. It runs as a service (Schedule), it is signed by Microsoft, and it is used by the operating system itself for maintenance tasks. Endpoint protection products are configured to allow it. When Task Scheduler launches your Python script, the process is a child of svchost.exe hosting the Schedule service, not a child of your interactive shell. That parent-child relationship is what the security suite evaluates — and it is a trusted one.

This is not a hack. It is the intended way to run recurring work on Windows. The daemon pattern — a long-lived process with an internal loop — is a Unix idiom that maps poorly onto Windows security models. Task Scheduler gives you:

  • Trigger-based execution. Run at logon, at startup, every N minutes, on idle, on event. No while True loop needed.
  • Process isolation. Each run is a fresh process. A crash does not take down the scheduler.
  • A working directory you control. Set it explicitly; do not rely on the shell's cwd.
  • Execution time limits. If a run hangs, Task Scheduler kills it and records the result.
  • Retry semantics. StartWhenAvailable runs a missed task as soon as the machine is available.
  • Result codes. Every run records Last Run Result, which you can query from Python or PowerShell.

The tradeoff is that you lose in-memory state between runs. For most recurring jobs — polling, scraping, file sync, report generation — that is fine. For jobs that genuinely need a persistent connection, you keep a daemon but run it under a service wrapper (NSSM, sc.exe) rather than as a child of your shell. Task Scheduler is for the recurring, stateless work.

Mapping a daemon to a task

Take the original daemon: poll an endpoint every 60 seconds, write results to SQLite, log to a file. As a daemon it looked like this:

import time, sqlite3, logging

logging.basicConfig(filename="poll.log", level=logging.INFO)

def poll_once():
    # fetch, parse, insert
    ...

if __name__ == "__main__":
    while True:
        try:
            poll_once()
        except Exception:
            logging.exception("poll failed")
        time.sleep(60)

As a scheduled task, the loop disappears. The script becomes a single-shot job:

import sys, sqlite3, logging
from datetime import datetime, timezone

LOG = r"C:\jobs\poll\poll.log"
DB = r"C:\jobs\poll\data.sqlite"

logging.basicConfig(
    filename=LOG,
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)

def poll_once():
    # fetch, parse, insert
    ...

def main() -> int:
    try:
        poll_once()
        logging.info("ok")
        return 0
    except Exception:
        logging.exception("poll failed")
        return 1

if __name__ == "__main__":
    sys.exit(main())

Two things matter here. First, the script returns an exit code: 0 on success, 1 on failure. Task Scheduler records this as Last Run Result. Second, all paths are absolute. Do not assume the working directory.

Register the task with schtasks (or the Task Scheduler GUI, or the pywin32 COM API). The schtasks command is the most portable:

schtasks /Create /TN "CodeQuant\Poll" /TR "C:\Python311\python.exe C:\jobs\poll\poll.py" /SC MINUTE /MO 1 /RL LIMITED /F

That is the minimum. In practice you want a few more flags:

schtasks /Create ^
  /TN "CodeQuant\Poll" ^
  /TR "C:\Python311\python.exe C:\jobs\poll\poll.py" ^
  /SC MINUTE /MO 1 ^
  /RL LIMITED ^
  /F

/RL LIMITED runs the task with the least privilege the account has. Do not use /RL HIGHEST unless the job genuinely needs elevation; it makes the security suite pay more attention.

For a job that should survive reboots and catch up on missed runs, set StartWhenAvailable and a time limit. schtasks does not expose every setting, so drop into PowerShell for the full set:

$action = New-ScheduledTaskAction `
    -Execute "C:\Python311\python.exe" `
    -Argument "C:\jobs\poll\poll.py" `
    -WorkingDirectory "C:\jobs\poll"

$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date) `
    -RepetitionInterval (New-TimeSpan -Minutes 1)

$settings = New-ScheduledTaskSettingsSet `
    -StartWhenAvailable `
    -ExecutionTimeLimit (New-TimeSpan -Minutes 5) `
    -RestartCount 3 `
    -RestartInterval (New-TimeSpan -Minutes 1) `
    -MultipleInstances IgnoreNew

Register-ScheduledTask `
    -TaskName "CodeQuant\Poll" `
    -Action $action `
    -Trigger $trigger `
    -Settings $settings `
    -User "DOMAIN\youruser" `
    -RunLevel Limited

The key settings:

  • -WorkingDirectory sets the cwd for the process. Without it, the script runs in C:\Windows\System32 and any relative path breaks.
  • -StartWhenAvailable runs the task as soon as the machine is on, even if the scheduled time was missed. This is what replaces the daemon's "always running" property.
  • -ExecutionTimeLimit kills a hung run. A daemon that hangs holds a connection forever; a scheduled task that hangs gets cleaned up.
  • -RestartCount and -RestartInterval give you retry-on-failure without a watchdog process.
  • -MultipleInstances IgnoreNew prevents overlap if a run takes longer than the interval. This is the equivalent of the daemon's single-threaded loop.

Reading last-run result codes

The operational win that surprised me most: Task Scheduler records the exit code of every run. You get failure visibility for free.

Query it from PowerShell:

Get-ScheduledTaskInfo -TaskName "CodeQuant\Poll" |
    Select-Object LastRunTime, LastTaskResult, NextRunTime, NumberOfMissedRuns

LastTaskResult is the exit code your script returned. 0 means success. Anything else is a failure you can alert on. NumberOfMissedRuns tells you if the machine was off or the task was disabled.

From Python, wrap the same query:

import subprocess, json

def task_status(task_name: str) -> dict:
    ps = (
        f"Get-ScheduledTaskInfo -TaskName '{task_name}' | "
        "Select-Object LastRunTime, LastTaskResult, NextRunTime, NumberOfMissedRuns | "
        "ConvertTo-Json"
    )
    out = subprocess.run(
        ["powershell", "-NoProfile", "-Command", ps],
        capture_output=True, text=True, check=True,
    ).stdout
    return json.loads(out)

if __name__ == "__main__":
    info = task_status(r"CodeQuant\Poll")
    if info["LastTaskResult"] != 0:
        # send alert
        ...

This is the part that a daemon cannot give you without building it yourself. The daemon's failure mode was silence. The scheduled task's failure mode is a non-zero integer sitting in the Windows task store, queryable from any script.

What this changes operationally

Moving from daemons to Task Scheduler changed three things for me:

Reboot survival. A daemon launched from the Startup folder dies when the user logs off, and it does not come back until the next logon. A scheduled task with a trigger at startup or logon runs regardless, and StartWhenAvailable catches up on anything missed while the machine was off.

No watchdog to maintain. The keep-alive process is gone. Retry is a setting, not a script. If a run fails, Task Scheduler retries it on the interval you configured. If it hangs, the execution time limit kills it. You delete an entire class of code.

Failure is observable. Every run leaves a result code. You can build a single dashboard that queries all your tasks and alerts on non-zero results. No more discovering at 3 a.m. that a daemon died six hours ago.

The one thing you give up is in-memory state. For polling, syncing, and report jobs, that is not a real loss. For anything that needs a persistent socket or a long-lived cache, keep the daemon but run it as a Windows service under sc.exe or NSSM — not as a child of your shell, where the security suite can see it.

The migration checklist

If you are moving a daemon to Task Scheduler, here is the sequence that worked:

  1. Refactor the loop body into a single-shot function with an explicit exit code.
  2. Make every path absolute. No relative imports, no cwd assumptions.
  3. Register the task with an explicit working directory and a repetition trigger.
  4. Set StartWhenAvailable, an execution time limit, and a restart policy.
  5. Set MultipleInstances to IgnoreNew to prevent overlap.
  6. Query LastTaskResult after the first few runs to confirm the exit code is what you expect.
  7. Delete the old daemon and its watchdog. Do not leave both running.

The security suite will not block any of this, because none of it looks like a daemon spawning children. It looks like Windows doing what Windows does.
