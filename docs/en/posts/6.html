Migrating a Python Automation Stack to a New Windows Server

2026-10-04 Windows Automation

A stack that runs unattended for months accumulates assumptions. Most of them are invisible until you move it to another machine. Ours was nine scheduled tasks: a blog pipeline that renders Markdown to a static site, a trading system that polls data feeds and writes state, and a pile of maintenance scripts that rotate logs and clean temp files. It lived on a Windows 11 dev box for two years. Then we had to put it on a fresh Windows Server 2016 instance, and almost everything that could differ between two Windows installs did.

This is the migration as it actually happened: what broke, what the package looked like, and the encoding bug that cost the most time.

Why a package, not a copy

The naive move is to zip the project folder and drop it on the server. That fails for one reason: the dev box folder contains both code and runtime state, and they have opposite requirements.

Code should be copied exactly. Runtime state should mostly not be copied — logs are noise, built sites are regenerable, trade records are append-only history that the new machine will start writing to immediately, and cookies are machine-specific session tokens that will be invalid or, worse, silently confusing on a different host.

So we split the tree conceptually into two halves and used xcopy with an exclude list. The exclude file is the interesting part:

# migrate_exclude.txt
\logs\
\logs\*
\build\
\build\*
\dist\
\dist\*
\__pycache__\
\__pycache__\*
*.pyc
\cookies\
\cookies\*
\state\trades\
\state\trades\*
\state\tmp\
\state\tmp\*
\*.log
\.pytest_cache\
\.pytest_cache\*

Then the copy itself:

xcopy "D:\automation" "C:\automation" /E /I /H /K /Y /EXCLUDE:migrate_exclude.txt

/E copies empty directories too, which matters because several scripts assume their output directory exists and crash if it doesn't. /H includes hidden files. /K preserves attributes, since a couple of files were marked read-only by a previous cleanup pass and we wanted that to survive. /Y suppresses the overwrite prompt — this runs unattended.

The exclude list protects the destination as much as it trims the source. If the server already has a state\trades directory with real records, xcopy without exclusions would happily overwrite it with the dev box's stale copies. Excluding runtime paths makes the copy idempotent: you can run it twice and the second run changes nothing that matters.

Paths that survive a move

Hardcoded paths are the first thing to break. The dev box had D:\automation; the server had C:\automation and a different user profile name. Rather than parameterize every script, we made the installer infer everything.

The one-click installer is a batch file that resolves its own location and derives the rest:

@echo off
setlocal enabledelayedexpansion

REM ROOT is the directory this bat lives in.
set "ROOT=%~dp0"
if "%ROOT:~-1%"=="\" set "ROOT=%ROOT:~0,-1%"

REM Everything else hangs off it or off the user profile.
set "PY=%ROOT%\venv\Scripts\python.exe"
set "LOGS=%ROOT%\logs"
set "STATE=%ROOT%\state"

if not exist "%LOGS%" mkdir "%LOGS%"
if not exist "%STATE%" mkdir "%STATE%"

if not exist "%PY%" (
    echo [install] creating virtualenv
    py -3 -m venv "%ROOT%\venv" || goto :fail
    "%PY%" -m pip install --upgrade pip || goto :fail
    "%PY%" -m pip install -r "%ROOT%\requirements.txt" || goto :fail
)

echo [install] root = %ROOT%
echo [install] python = %PY%
exit /b 0

:fail
echo [install] FAILED
exit /b 1

The %~dp0 trick is the important line. It means the package can be unzipped anywhere — C:\automation, D:\projects\automation, a user's Desktop — and the installer configures itself accordingly. No config file to edit, no environment variable to set by hand.

Python-side, we stopped hardcoding paths too. Every script resolves its root relative to __file__:

from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
STATE_DIR = ROOT / "state"
LOG_DIR = ROOT / "logs"

def ensure_dirs() -> None:
    for d in (STATE_DIR, LOG_DIR):
        d.mkdir(parents=True, exist_ok=True)

resolve() matters here. Without it, a script invoked through a symlink or a relative path can end up computing a root that points somewhere unexpected. With it, the path is absolute and canonical before anything else touches it.

Re-registering the scheduled tasks

The nine tasks were the real work. They had been created on the dev box with schtasks and had absolute paths baked into their actions. Copying task definitions between machines is not a supported operation, so we re-registered them from scratch on the server.

The PowerShell approach is cleaner than schtasks because you can build the action and trigger as objects:

$Root = "C:\automation"
$Py   = Join-Path $Root "venv\Scripts\python.exe"

$Tasks = @(
    @{ Name = "AutoBlog_Build";   Script = "blog\build.py";        Time = "06:00" },
    @{ Name = "AutoBlog_Deploy";  Script = "blog\deploy.py";       Time = "06:30" },
    @{ Name = "Trade_Poll";       Script = "trade\poll.py";        Time = "07:00" },
    @{ Name = "Trade_Settle";     Script = "trade\settle.py";      Time = "21:00" },
    @{ Name = "Maint_RotateLogs"; Script = "maint\rotate_logs.py"; Time = "23:00" }
)

foreach ($t in $Tasks) {
    $scriptPath = Join-Path $Root $t.Script
    $action = New-ScheduledTaskAction `
        -Execute $Py `
        -Argument "`"$scriptPath`"" `
        -WorkingDirectory $Root

    $trigger = New-ScheduledTaskTrigger -Daily -At $t.Time

    $settings = New-ScheduledTaskSettingsSet `
        -StartWhenAvailable `
        -DontStopOnIdleEnd `
        -ExecutionTimeLimit (New-TimeSpan -Hours 2)

    Register-ScheduledTask `
        -TaskName $t.Name `
        -Action $action `
        -Trigger $trigger `
        -Settings $settings `
        -User "SYSTEM" `
        -RunLevel Highest `
        -Force
}

Three details in there are load-bearing.

-WorkingDirectory $Root — without it, the task runs from C:\Windows\System32, and any script that uses a relative path for output writes into the system directory. We hit this on the first attempt.

-StartWhenAvailable — the server reboots for patching, and a task whose trigger time passed during the reboot should still run. The default silently skips it.

-ExecutionTimeLimit — the default is three days, which is effectively no limit. A hung polling script would sit there forever. Two hours is generous for our longest task.

The verification bat

After registering, we needed to prove the tasks were actually correct — not just present. A task can exist with a broken action and you won't notice until it fails at 3 a.m.

The verification script pulls each task's action and last run result and compares them against expectations:

@echo off
setlocal

set "ROOT=%~dp0"
if "%ROOT:~-1%"=="\" set "ROOT=%ROOT:~0,-1%"
set "PY=%ROOT%\venv\Scripts\python.exe"

echo [verify] python: %PY%
if not exist "%PY%" (
    echo [verify] FAIL: interpreter missing
    exit /b 1
)

powershell -NoProfile -ExecutionPolicy Bypass -Command ^
  "$root = '%ROOT%';" ^
  "$py = Join-Path $root 'venv\Scripts\python.exe';" ^
  "$names = @('AutoBlog_Build','AutoBlog_Deploy','Trade_Poll','Trade_Settle','Maint_RotateLogs');" ^
  "$bad = 0;" ^
  "foreach ($n in $names) {" ^
  "  $t = Get-ScheduledTask -TaskName $n -ErrorAction SilentlyContinue;" ^
  "  if (-not $t) { Write-Host \"MISSING $n\"; $bad++; continue }" ^
  "  $exe = $t.Actions[0].Execute;" ^
  "  $arg = $t.Actions[0].Arguments;" ^
  "  $info = Get-ScheduledTaskInfo -TaskName $n;" ^
  "  $code = $info.LastTaskResult;" ^
  "  Write-Host \"$n exec=$exe arg=$arg last=$code\";" ^
  "  if ($exe -ne $py) { Write-Host \"  WARN: unexpected interpreter\"; $bad++ }" ^
  "  if ($code -ne 0 -and $code -ne 267009) { Write-Host \"  WARN: last result $code\" }" ^
  "}" ^
  "if ($bad -gt 0) { exit 1 } else { exit 0 }"

if errorlevel 1 (
    echo [verify] one or more tasks need attention
    exit /b 1
)

echo [verify] all tasks look correct
exit /b 0

267009 is SCHED_S_TASK_RUNNING — a task that's currently executing reports that as its last result, and it isn't an error. Filtering it out avoids false alarms when you run the verifier while a long task is mid-flight.

The verifier is the thing you run after every deploy, not just the first one. Task definitions drift: someone edits one by hand, a patch changes a default, a script gets renamed. A thirty-second check catches all of it.

The encoding trap

This is the part that cost us a full day, and it's the reason this article exists.

The dev box ran Windows 11 with UTF-8 as the system code page. The server ran Windows Server 2016 with GBK. Same Python version, same scripts, same data — different behavior.

The symptom was subtle. A blog post with a non-ASCII character would render correctly on the dev box and come out as mojibake on the server. A trade log would parse fine in one place and throw UnicodeDecodeError in the other. Nothing in the code looked wrong, because nothing in the code specified an encoding.

Python's default encoding for open() is not UTF-8. It's whatever locale.getpreferredencoding() returns, which on Windows follows the system code page. On the dev box that was UTF-8. On the server it was GBK. Every open() call without an explicit encoding was a latent bug that only surfaced after the move.

The fix is mechanical but has to be complete. Every read and write pins its encoding:

from pathlib import Path
import json

def read_text(path: Path) -> str:
    return path.read_text(encoding="utf-8")

def write_text(path: Path, text: str) -> None:
    path.write_text(text, encoding="utf-8", newline="\n")

def load_json(path: Path):
    with path.open("r", encoding="utf-8") as f:
        return json.load(f)

def save_json(path: Path, obj) -> None:
    tmp = path.with_suffix(path.suffix + ".tmp")
    with tmp.open("w", encoding="utf-8", newline="\n") as f:
        json.dump(obj, f, ensure_ascii=False, indent=2)
    tmp.replace(path)

Two things beyond the encoding argument. newline="\n" forces LF line endings regardless of platform, so files written on the server are byte-identical to files written on the dev box. And the atomic write — write to a temp file, then replace — means a crash mid-write can't leave a half-written state file that the next run will choke on.

We also audited for the places encoding hides. Subprocess calls are a common one:

import subprocess

def run(cmd: list[str]) -> str:
    result = subprocess.run(
        cmd,
        capture_output=True,
        text=True,
        encoding="utf-8",
        errors="replace",
        check=True,
    )
    return result.stdout

Without encoding="utf-8", text=True decodes the child process's output using the system code page. On the server that meant a GBK decode of UTF-8 bytes, which produced garbage or raised depending on the byte sequence.

The other hiding place is environment variables and file paths read from config. Anything that crosses the process boundary needs to be treated as bytes until you explicitly decode it.

Once every read and write pinned its encoding, the two machines behaved identically. The migration didn't fix a bug so much as expose one that had been there the whole time — the dev box's UTF-8 default had been silently covering for it.

What the package looks like now

The final structure is a self-contained directory with four entry points:

  • install.bat — creates the venv, installs dependencies, makes directories
  • register_tasks.ps1 — re-registers all scheduled tasks with correct paths
  • verify.bat — checks every task's action and last result
  • migrate_exclude.txt — the exclude list for xcopy

The whole migration is three commands on a fresh server: copy with exclusions, run the installer, register the tasks. Then verify. The encoding audit is a one-time fix that lives in the code, not the package, which means it travels with every future copy.

The lesson generalizes beyond this stack. A migration is an opportunity to find the assumptions you didn't know you'd made — hardcoded paths, implicit encodings, tasks that only work when run from a particular directory. Each one you pin down is a failure mode that can't surprise you next time.
