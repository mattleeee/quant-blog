Migrating from xcopy to robocopy: Copy Reliability on Chinese Paths

2026-11-13 Windows Automation

The failure mode is nasty because nothing looks broken. A scheduled task runs, xcopy exits with code 0 or 1, the redirected log file is empty or contains a single line of mojibake, and the destination directory is untouched. You find out days later when a downstream job reads stale files.

The root cause is /EXCLUDE. xcopy reads that file with the current console code page (typically 936 on Chinese Windows, or 437 on an English system), not with the system's Unicode APIs. The moment the exclusion file contains a path like D:\数据\临时\, the bytes get mangled, the pattern matches nothing sensible, and depending on the xcopy build and the surrounding quoting, the whole copy can degenerate into "zero files copied, exit code 0."

Here is a minimal reproduction. Two source trees, one exclusion file with a Chinese directory:

import subprocess
from pathlib import Path

src = Path(r"D:\数据\源")
dst = Path(r"E:\备份\目标")
src.mkdir(parents=True, exist_ok=True)
dst.mkdir(parents=True, exist_ok=True)

(src / "a.txt").write_text("keep me", encoding="utf-8")
(src / "临时").mkdir(exist_ok=True)
(src / "临时" / "b.txt").write_text("skip me", encoding="utf-8")

exclude = Path(r"D:\exclude.txt")
exclude.write_text("临时\\\n", encoding="gbk")  # what a human would write

cmd = [
    "xcopy", str(src), str(dst),
    "/E", "/I", "/Y", "/R", "/K",
    f"/EXCLUDE:{exclude}",
]
proc = subprocess.run(
    cmd, capture_output=True, text=True, encoding="gbk", errors="replace"
)
print("exit:", proc.returncode)
print("stdout:", proc.stdout)
print("files copied:", [p.name for p in dst.rglob("*") if p.is_file()])

On a Chinese-locale machine this often prints exit: 0 and files copied: []. On an English-locale machine it prints exit: 4 ("Initialization error occurred. There is not enough memory or disk space...") — a misleading message for what is actually an encoding problem. Either way, the exclusion file is the culprit, and there is no way to tell xcopy which code page to use.

You can sometimes work around it by writing the exclusion file in the OEM code page and avoiding trailing backslashes, but the behavior is undocumented and varies between Windows versions. That is not a foundation for a backup job.

Why robocopy Is the Right Replacement

robocopy was built for the same job but takes a different approach to exclusions: they are command-line arguments, not a file. /XD takes directory paths, /XF takes file patterns, and both are parsed by the same Unicode-aware argument handling that robocopy uses for its source and destination paths. There is no intermediate text file to encode, so there is no code page to get wrong.

Three properties make the migration worthwhile:

  1. Unicode paths work natively. A path like D:\数据\临时 passes through the command line intact, assuming the process is not doing something silly with subprocess and ANSI code pages.
  2. Exit codes have clear semantics. 0–7 are success variants (files copied, extras present, mismatches, etc.), 8 and above are failures. You can branch on < 8 with confidence.
  3. It is resumable and idempotent. robocopy compares timestamps and sizes and skips unchanged files, which is exactly what you want for a scheduled sync.

The trade-off: robocopy's argument surface is large, and the defaults are not what you want for a backup job. You have to design the parameter set deliberately.

Designing the Parameter Set

Here is the invocation I use for a one-way mirror of a data tree, with exclusions passed as arguments:

import subprocess
from pathlib import Path

SRC = r"D:\数据\源"
DST = r"E:\备份\目标"

EXCLUDE_DIRS = [
    r"D:\数据\源\临时",
    r"D:\数据\源\缓存",
]
EXCLUDE_FILES = [
    "*.tmp",
    "*.lock",
    "~$*",
]

def build_robocopy_cmd(src: str, dst: str) -> list[str]:
    cmd = [
        "robocopy", src, dst,
        "/E",          # recurse, including empty dirs
        "/COPY:DAT",   # data, attributes, timestamps
        "/DCOPY:T",    # preserve directory timestamps
        "/R:3",        # retry 3 times on locked files
        "/W:5",        # wait 5 seconds between retries
        "/MT:8",       # 8 threads; tune to disk, not CPU
        "/NP",         # no per-file progress percentage
        "/NFL",        # no file list (keep log small)
        "/NDL",        # no directory list
        "/IS",         # include same files (force overwrite)
        "/IT",         # include tweaked files (force overwrite)
        "/XD", *EXCLUDE_DIRS,
        "/XF", *EXCLUDE_FILES,
    ]
    return cmd

proc = subprocess.run(
    build_robocopy_cmd(SRC, DST),
    capture_output=True,
    text=True,
    encoding="utf-8",
    errors="replace",
)
print("exit:", proc.returncode)

A few choices deserve explanation.

/E versus /MIR

/MIR mirrors the destination, which means it deletes files at the destination that no longer exist at the source. For a backup target that is fine; for a shared destination that other processes write to, it is dangerous. I default to /E and only use /MIR when the destination is dedicated and I have a retention policy elsewhere. If you do use /MIR, add /XD entries for anything the destination needs to keep.

/COPY:DAT and /DCOPY:T

The default /COPY:DAT copies data, attributes, and timestamps, which is what you want. Add /DCOPY:T so directory timestamps survive; without it, every sync resets directory mtimes and downstream tools that watch directories will fire spuriously.

/R and /W

The defaults are /R:1000000 /W:30, which means a single locked file can stall the job for weeks. Set these explicitly. Three retries with five-second waits is enough for transient locks from antivirus scanners or an open Excel file.

/MT

Multi-threaded copying is a large win on many small files. /MT:8 is a reasonable default; going much higher mostly increases contention on spinning disks. Note that /MT implies /NP behavior in some builds, so setting /NP explicitly keeps the log format consistent.

Forcing Overwrite with /IS and /IT

This is the part that catches people migrating from xcopy, and it is worth its own section.

robocopy's default comparison is timestamp-based: a file is copied if the source is newer than the destination. That sounds correct, but it fails in two real situations:

  • Clock skew. If the source machine's clock drifted forward, or the file was touched by a process with a bad clock, the source timestamp can be older than the destination even though the content is newer. robocopy skips the file. xcopy with /D has the same problem; xcopy without /D copies everything, which is why some people never noticed.
  • Timestamp-only changes. Some tooling rewrites a file with identical content but a new mtime. robocopy sees "same size, same time" and skips it — usually fine — but if the destination was modified by something else, you want the source to win.

/IS ("include same files") and /IT ("include tweaked files") tell robocopy to copy files that are classified as identical or as having only a timestamp difference. Combined, they make the copy effectively "source always wins" for anything that isn't excluded.

The cost is bandwidth and I/O: every file is re-read and re-written on every run. For a few hundred gigabytes of mostly-static data on a local disk, that is acceptable. For a nightly job over a WAN, it is not. The middle ground is to use /IS /IT for the initial migration and for jobs where correctness matters more than throughput, and to drop them for large incremental jobs where the clock is trustworthy.

If you want content-based comparison rather than timestamp-based, robocopy has no built-in hash mode. The practical approach is a two-stage job: run robocopy normally, then run a Python pass that hashes mismatched sizes or suspicious timestamps and copies the outliers. That is more code than most people need, but it is the honest answer.

Auditing the Log

robocopy writes a summary table at the end of its output. The exit code is derived from that table, but the table is what you read when something goes wrong. Parse both.

import re
import subprocess
from dataclasses import dataclass

@dataclass
class RobocopyResult:
    exit_code: int
    dirs_copied: int
    files_copied: int
    files_skipped: int
    files_failed: int
    bytes_copied: int
    failed_paths: list[str]

SUMMARY_RE = re.compile(
    r"^\s*(Dirs|Files|Bytes)\s*:\s*"
    r"(\d+)\s+(\d+)\s+(\d+)\s+(\d+)\s+(\d+)\s+(\d+)",
    re.MULTILINE,
)
FAILED_RE = re.compile(r"^\s*ERROR\s+\d+\s+\(0x[0-9A-Fa-f]+\)\s+(.+)$", re.MULTILINE)

def run_robocopy(cmd: list[str]) -> RobocopyResult:
    proc = subprocess.run(
        cmd, capture_output=True, text=True,
        encoding="utf-8", errors="replace",
    )
    out = proc.stdout

    dirs_copied = files_copied = files_skipped = files_failed = 0
    bytes_copied = 0
    for m in SUMMARY_RE.finditer(out):
        kind = m.group(1)
        # columns: total, copied, skipped, mismatch, failed, extras
        copied = int(m.group(3))
        skipped = int(m.group(4)) + int(m.group(5))
        failed = int(m.group(6))
        if kind == "Dirs":
            dirs_copied = copied
        elif kind == "Files":
            files_copied = copied
            files_skipped = skipped
            files_failed = failed
        elif kind == "Bytes":
            bytes_copied = copied

    failed_paths = [m.group(1).strip() for m in FAILED_RE.finditer(out)]

    return RobocopyResult(
        exit_code=proc.returncode,
        dirs_copied=dirs_copied,
        files_copied=files_copied,
        files_skipped=files_skipped,
        files_failed=files_failed,
        bytes_copied=bytes_copied,
        failed_paths=failed_paths,
    )

Two details matter here. First, the summary table's column order is fixed (Total, Copied, Skipped, Mismatch, FAILED, Extras), but the numbers are right-aligned and the spacing varies, so a regex anchored on the label is more robust than splitting on whitespace. Second, ERROR lines in the output are the only place robocopy names the file it could not copy; the summary only gives counts. Extract them or you will be re-running the job with /L (list-only) to find out what failed.

Wrap the whole thing in a check that distinguishes the exit-code classes:

def classify(result: RobocopyResult) -> str:
    if result.exit_code >= 8:
        return "FAILED"
    if result.exit_code & 0b100:  # 4: mismatched files present
        return "MISMATCH"
    if result.exit_code & 0b010:  # 2: extra files at destination
        return "EXTRAS"
    if result.exit_code & 0b001:  # 1: files copied
        return "COPIED"
    return "NO_CHANGE"  # 0: nothing to do

Exit code 0 is not an error — it means the trees already match. That is the single most important semantic difference from xcopy, where 0 and 1 both mean "something may or may not have happened." Treat < 8 as success, log the class, and alert on >= 8 or on a nonzero files_failed.

Migration Checklist

If you are moving a production job, do it in this order:

  1. Run the old and new commands with /L. robocopy's list-only mode prints what it would copy without touching disk. Diff the file lists against what xcopy actually produced. This is where you discover that your exclusion patterns meant something different than you thought.
  2. Convert every /EXCLUDE entry. Directory entries go to /XD, file patterns to /XF. xcopy's \-suffixed directory patterns map to /XD paths; bare names map to /XF names.
  3. Set /R and /W explicitly. Never rely on the defaults.
  4. Decide on /IS /IT. Use them for the first run and for jobs where clock skew is plausible; drop them for large incremental jobs after verifying timestamps are trustworthy.
  5. Replace exit-code checks. Anything that tested if exit_code == 0 against xcopy must become if exit_code < 8 against robocopy, or it will treat "files copied" as failure.
  6. Keep the log. Write the full robocopy output to a dated file and parse it. The summary table is your audit trail when a downstream consumer reports missing data.

The Chinese-path bug is what pushes people to migrate, but the exit-code semantics and the explicit exclusion arguments are the reasons the migration sticks. xcopy's silent failures are a property of its design, not a bug you can patch around; robocopy's failure modes are loud and classifiable, which is what a scheduled job needs.
