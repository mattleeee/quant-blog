Health Checks for a Fleet of Scheduled Tasks

2026-10-05 Windows Automation

Scheduled tasks are the duct tape of Windows automation. They run headless, survive reboots, and need no service wrapper. The failure mode is not that they break — it is that they break silently. A task that failed three days ago looks exactly like a task that succeeded three days ago if nobody is reading LastTaskResult.

Nine unattended tasks is past the point where manual checking works. At that count you need a health check: a script that enumerates the fleet, reads each task's state, compares it against an expected schedule, and pages you when something is off.

What the Task Scheduler COM API actually gives you

The Schedule.Service COM object exposes per-task fields that matter for monitoring. The ones worth wiring into an audit:

  • State — an enum: 0 Unknown, 1 Disabled, 2 Queued, 3 Ready, 4 Running. Ready is the healthy resting state. Disabled means someone turned it off (or a deployment did). Running means it is executing right now — useful context, but not a health signal by itself.
  • LastRunTime — a datetime in local time. Combined with the expected interval, this is what tells you a task is stale: it should have fired by now and did not.
  • LastTaskResult — the exit code of the last run. 0 is success. 0x41301 (267009) means "currently running". 0x41303 (267011) means "has not yet run". Everything else non-zero is a failure, and the exact code is often diagnostic (e.g. 1 for a generic script error, 0x80070002 for a missing file).
  • NextRunTime — derived from the trigger, not from history. A task can have a sane NextRunTime and still be stale because the last run never completed.

LastRunTime and LastTaskResult are only meaningful together. A task with LastTaskResult == 0 but LastRunTime from four days ago on an hourly schedule is not healthy — it is a task whose trigger stopped firing, or whose run never recorded a result.

The four states you actually care about

For an unattended fleet, collapse the raw fields into four verdicts:

  1. Disabled — State == 1. Nothing runs. This is either intentional (retired task) or an incident (someone disabled it while debugging and forgot).
  2. Running — State == 4 or LastTaskResult == 267009. Not a failure, but a task stuck in Running for hours is a different problem: a hung process holding the scheduler slot.
  3. Failed — LastTaskResult is non-zero and not one of the "no result yet" sentinels. This is the classic alert.
  4. Stale — LastRunTime is older than now - expected_interval - grace. The task may report success from its last run, but it has stopped firing on schedule.

A fifth implicit state, Ready with a recent successful run, is the only one that needs no action.

The expected-schedule table

You cannot compute "stale" without knowing the intended cadence. The scheduler knows the triggers, but parsing trigger XML for arbitrary task definitions is fragile. A small hand-maintained table is more honest and easier to review:

from datetime import timedelta

# task name -> (expected interval, grace period)
EXPECTED = {
    "Quant_Ingest":        (timedelta(minutes=15),  timedelta(minutes=5)),
    "Quant_Signal":        (timedelta(minutes=15),  timedelta(minutes=5)),
    "Quant_Risk":          (timedelta(minutes=30),  timedelta(minutes=10)),
    "Quant_Reconcile":     (timedelta(hours=1),     timedelta(minutes=15)),
    "Quant_Report":        (timedelta(days=1),      timedelta(hours=2)),
    "TeleAgent_Poll":      (timedelta(minutes=5),   timedelta(minutes=3)),
    "TeleAgent_Forward":   (timedelta(minutes=5),   timedelta(minutes=3)),
    "TeleAgent_Archive":   (timedelta(hours=6),     timedelta(minutes=30)),
    "TeleAgent_Heartbeat": (timedelta(minutes=10),  timedelta(minutes=5)),
}

The grace period absorbs normal jitter: clock skew, a task that takes a few minutes to finish, a machine that was asleep. Without it you will get false positives and start ignoring the alerts, which defeats the purpose.

Enumerating the fleet

The COM API is reachable through win32com.client. Enumerate the root folder, filter by name prefix, and read the fields:

import win32com.client
from datetime import datetime, timedelta

TASK_ENUM_HIDDEN = 1
TASK_STATE = {
    0: "Unknown", 1: "Disabled", 2: "Queued",
    3: "Ready", 4: "Running",
}

def _com_to_dt(value):
    """pywintypes datetime -> python datetime, or None."""
    if value is None:
        return None
    try:
        return datetime(value.year, value.month, value.day,
                        value.hour, value.minute, value.second)
    except AttributeError:
        return None

def enumerate_tasks(prefixes=("Quant_", "TeleAgent_")):
    service = win32com.client.Dispatch("Schedule.Service")
    service.Connect()
    root = service.GetFolder("\\")

    found = {}
    for task in root.GetTasks(TASK_ENUM_HIDDEN):
        if not task.Name.startswith(prefixes):
            continue
        found[task.Name] = {
            "state": TASK_STATE.get(task.State, f"Unknown({task.State})"),
            "state_code": task.State,
            "last_run": _com_to_dt(task.LastRunTime),
            "last_result": task.LastTaskResult,
            "next_run": _com_to_dt(task.NextRunTime),
            "enabled": bool(task.Enabled),
        }
    return found

Two things to watch. First, GetTasks(TASK_ENUM_HIDDEN) includes hidden tasks; if you do not pass the flag you will silently miss tasks that were created with the hidden bit set. Second, LastRunTime comes back as a pywintypes datetime — convert it explicitly so comparisons with datetime.now() are predictable.

Classifying each task

With the raw fields and the expected table, the classification is a small pure function. Keeping it separate from the COM access makes it testable without a Windows box:

SENTINEL_RUNNING = 267009      # 0x41301
SENTINEL_NOT_YET = 267011      # 0x41303

def classify(name, info, expected, now=None):
    now = now or datetime.now()
    interval, grace = expected.get(name, (None, None))

    if info["state_code"] == 1 or not info["enabled"]:
        return "disabled", "task is disabled"

    if info["last_result"] == SENTINEL_RUNNING:
        return "running", "currently executing"

    if info["last_result"] == SENTINEL_NOT_YET:
        return "stale", "has never run"

    if info["last_result"] != 0:
        return "failed", f"exit code {info['last_result']:#x}"

    if interval is None:
        return "unknown", "no expected schedule on file"

    last = info["last_run"]
    if last is None:
        return "stale", "no LastRunTime recorded"

    age = now - last
    if age > interval + grace:
        return "stale", f"last run {age} ago, expected every {interval}"

    return "ok", f"last run {age} ago"

The order matters. Check Disabled before Failed, because a disabled task often carries a stale non-zero result from before it was turned off. Check the running sentinel before the failure branch, because 267009 is technically non-zero. And treat "never run" as stale rather than failed — a freshly deployed task has no result yet, and you want the alert to say so.

Pushing the alert through PushPlus

PushPlus takes a simple HTTP POST with a token and a message body. The audit should send one consolidated message, not one per task — nine separate pushes train you to mute the channel.

import json
import urllib.request

PUSHPLUS_TOKEN = "your-token-here"
PUSHPLUS_URL = "http://www.pushplus.plus/send"

def push(title, body):
    payload = json.dumps({
        "token": PUSHPLUS_TOKEN,
        "title": title,
        "content": body,
        "template": "txt",
    }).encode("utf-8")
    req = urllib.request.Request(
        PUSHPLUS_URL, data=payload,
        headers={"Content-Type": "application/json"},
    )
    with urllib.request.urlopen(req, timeout=10) as resp:
        return json.loads(resp.read().decode("utf-8"))

Then assemble the report. Only alert when there is something to say:

def build_report(results):
    problems = {n: (v, r) for n, (v, r) in results.items() if v != "ok"}
    if not problems:
        return None

    lines = [f"{len(problems)} task(s) need attention:", ""]
    for name, (verdict, reason) in sorted(problems.items()):
        lines.append(f"[{verdict.upper()}] {name}: {reason}")
    return "\n".join(lines)

def run_audit():
    tasks = enumerate_tasks()
    now = datetime.now()
    results = {
        name: classify(name, info, EXPECTED, now)
        for name, info in tasks.items()
    }

    # Tasks in EXPECTED but missing from the scheduler are also a problem.
    for name in EXPECTED:
        if name not in tasks:
            results[name] = ("missing", "not found in Task Scheduler")

    report = build_report(results)
    if report:
        push("Task fleet health check", report)
    return results

The "missing" check matters more than it looks. If a task gets deleted during a cleanup, the scheduler simply stops listing it, and an enumeration-only audit reports a clean fleet.

Why the audit must itself be a scheduled task

The obvious failure mode of a monitoring script is that it is not running. If you launch the audit by hand, you have replaced nine tasks to babysit with one, and you will forget it on exactly the days something breaks.

Register the audit as a scheduled task, ideally on a different cadence from the tasks it watches, and with a trigger that catches missed runs:

def register_audit_task(script_path, python_exe):
    service = win32com.client.Dispatch("Schedule.Service")
    service.Connect()
    root = service.GetFolder("\\")

    definition = service.NewTask(0)
    definition.RegistrationInfo.Description = "Fleet health check"

    # Run every 10 minutes, indefinitely.
    trigger = definition.Triggers.Create(1)   # TASK_TRIGGER_TIME
    trigger.StartBoundary = datetime.now().isoformat()
    trigger.Repetition.Interval = "PT10M"
    trigger.Repetition.Duration = ""          # empty = forever

    # Catch up if the machine was off at trigger time.
    definition.Settings.StartWhenAvailable = True
    definition.Settings.ExecutionTimeLimit = "PT5M"

    action = definition.Actions.Create(0)     # TASK_ACTION_EXEC
    action.Path = python_exe
    action.Arguments = f'"{script_path}"'

    root.RegisterTaskDefinition(
        "Quant_FleetAudit", definition,
        6,        # TASK_CREATE_OR_UPDATE
        None, None, 3,   # TASK_LOGON_INTERACTIVE_TOKEN
    )

Two settings earn their keep. StartWhenAvailable makes the scheduler run a missed trigger as soon as the machine is back — without it, a laptop that was asleep at the scheduled minute silently skips the audit. And a short ExecutionTimeLimit prevents a wedged audit from holding the slot and blocking the next run.

Keep the audit out of the Quant_* / TeleAgent_* namespace so it does not audit itself. A task that checks its own LastRunTime will report itself stale the moment it is running, which is noise at best.

Operational notes

  • Log every run, not just failures. Append the full classification to a rotating log file. When a task fails at 03:00 and you get the push at 03:10, the log tells you whether it was the first failure or the fifth.
  • Alert on transitions, not states. If you push on every stale task every ten minutes, you will mute the channel within a day. Track the previous verdict per task and only push when it changes from ok to something else, or when a problem persists past a threshold.
  • Treat LastTaskResult codes as data. 0x80070002 is a missing executable, 0x80070005 is access denied, 1 is whatever the script returned. Put the hex code in the alert; it saves a trip to Event Viewer.
  • Beware the interactive-token trap. Tasks registered with TASK_LOGON_INTERACTIVE_TOKEN only run when the user is logged on. If your fleet must run headless, register with a stored password or a service account and verify that LastRunTime advances overnight.

The audit is small — a couple hundred lines including the report formatting. What it buys is the ability to stop thinking about nine tasks and start thinking about the one alert that says something is wrong.
