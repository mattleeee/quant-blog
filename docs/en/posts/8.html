Taming BLAS Threads in Scheduled Python Jobs

2026-10-05 Windows Automation

Scheduled Python jobs and BLAS threading are a bad combination by default. A single numpy.dot on a 4-core box will happily spin up four threads. Run three of those jobs at the same time via Task Scheduler, and you have twelve threads fighting over four cores. Context switches climb, cache lines bounce between cores, and total throughput drops — sometimes below the single-threaded case. The fix is usually boring: pin BLAS to one thread per process and let the scheduler handle parallelism across jobs.

What the environment variables actually control

NumPy itself doesn't do the math. It delegates to a BLAS/LAPACK backend — typically OpenBLAS (bundled with many wheels), MKL (Intel's, common in conda and mkl-enabled wheels), or the reference BLAS. Each backend runs its own thread pool, and each pool is configured independently.

  • OPENBLAS_NUM_THREADS — thread count for OpenBLAS. Historically OPENBLAS_NUM_THREADS replaced the older OMP_NUM_THREADS path; on modern OpenBLAS builds it's the authoritative knob.
  • MKL_NUM_THREADS — thread count for Intel MKL. MKL also reads MKL_DOMAIN_NUM_THREADS for per-domain tuning, but for a single job MKL_NUM_THREADS is enough.
  • OMP_NUM_THREADS — the OpenMP runtime thread count. Backends that use OpenMP internally (some MKL builds, some OpenBLAS builds) fall back to this. It also affects other OpenMP consumers in your process, e.g. scikit-learn's parallel loops or numba.

There's also NUMEXPR_NUM_THREADS for the numexpr engine used by pandas for some evaluation paths, and VECLIB_MAXIMUM_THREADS on macOS Accelerate. On Linux the equivalent is OPENBLAS_NUM_THREADS plus, for some builds, GOTO_NUM_THREADS. If you're on Windows and shipping wheels from PyPI, you almost always have OpenBLAS unless you installed via conda with MKL.

The key point: these are read at library initialization time. Set them after import numpy and you're too late — the pool is already sized.

Where to set them

There are two sane places, and one that quietly fails.

Option 1: the launcher (.bat / Task Scheduler action)

If your jobs are launched by a .bat file or directly from Task Scheduler, set the variables there. This is the cleanest option because it covers every process the job spawns, including subprocesses and any child Python interpreters.

@echo off
REM run_daily.bat
set OPENBLAS_NUM_THREADS=1
set MKL_NUM_THREADS=1
set OMP_NUM_THREADS=1
set NUMEXPR_NUM_THREADS=1

cd /d C:\jobs\daily
C:\Python311\python.exe -m daily.run >> C:\jobs\logs\daily.log 2>&1

If you're registering the task from the command line, pass the batch file as the action:

schtasks /Create /TN "daily-run" /TR "C:\jobs\run_daily.bat" ^
  /SC DAILY /ST 06:00 /RU SYSTEM

/RU SYSTEM runs without a logged-in user, which is what you want for a server. The environment block for the task is inherited from the system context, and your set lines override it.

Option 2: os.environ before importing numpy

When you can't control the launcher — say the job is invoked by a third-party scheduler or a service that calls python -c — set the variables at the very top of your entry module, before any numerical import.

# daily/run.py
import os

# Must run before numpy/pandas/numexpr are imported.
for var in (
    "OPENBLAS_NUM_THREADS",
    "MKL_NUM_THREADS",
    "OMP_NUM_THREADS",
    "NUMEXPR_NUM_THREADS",
):
    os.environ.setdefault(var, "1")

import numpy as np
import pandas as pd

setdefault is deliberate: it lets an operator override the value from the shell without editing code. If you want to force single-threading regardless of the environment, use os.environ[var] = "1" instead.

The trap here is import order. If any module in your package imports numpy at import time and you import that module before running the loop above, the pool is already initialized and the variables do nothing. Keep the env setup in a tiny module with no dependencies and import it first:

# daily/_threads.py
import os

def pin_blas_threads(n: int = 1) -> None:
    for var in (
        "OPENBLAS_NUM_THREADS",
        "MKL_NUM_THREADS",
        "OMP_NUM_THREADS",
        "NUMEXPR_NUM_THREADS",
    ):
        os.environ[var] = str(n)

# daily/run.py
from daily._threads import pin_blas_threads
pin_blas_threads(1)

import numpy as np  # safe now

The option that fails: setting them mid-run

import numpy as np
import os
os.environ["OPENBLAS_NUM_THREADS"] = "1"   # no effect on this process

This is the most common mistake. It looks right, it lints clean, and it does nothing for the current interpreter. It only affects subprocesses started afterward. If you see this pattern in a codebase, assume the thread-count problem is still present.

When single-threading wins, and when it loses

Single-threading is not universally faster. It's faster when aggregate throughput across concurrently scheduled jobs matters more than the latency of any single job. That's the typical server case: a handful of jobs overlap in the early morning, each doing moderate matrix work, and the box has 4–8 cores.

It's a loss when:

  • You have one long-running job on a large box and nothing else scheduled. A 16-core machine running a single big SVD will finish much sooner with 8–16 BLAS threads.
  • The workload is dominated by large dense matmuls where BLAS threading scales well. A 5000×5000 @ on 8 cores is roughly 5–7× faster than single-threaded.
  • The job is memory-bandwidth bound rather than compute-bound. More threads won't help, but they also won't hurt much — this is the ambiguous middle.

It's a clear win when:

  • Multiple jobs overlap. Three jobs × 8 threads on an 8-core box is worse than three jobs × 1 thread.
  • The matrices are small. BLAS thread-pool overhead (barriers, thread wakeups) dominates for anything under roughly 100×100. A loop of small matmuls single-threaded often beats the same loop with 8 threads.
  • Memory predictability matters. Each BLAS thread allocates workspace. With 8 threads per process and 4 processes, peak RSS can be several times the single-threaded figure. On a small VM, that's the difference between finishing and getting OOM-killed.

A reasonable default for a scheduled-job server: 1 thread per process, and control parallelism by scheduling. If a single job genuinely needs more, give it more and make sure it doesn't overlap with others.

A benchmark harness

Don't guess. Measure on your own hardware with your own shapes. The harness below runs the same workload at several thread counts and reports wall time and peak RSS.

# bench_blas.py
import os
import subprocess
import sys
import time

WORKLOAD = r"""
import numpy as np, time, resource
rng = np.random.default_rng(0)
A = rng.standard_normal((1200, 1200))
B = rng.standard_normal((1200, 1200))
# warm up
A @ B
t0 = time.perf_counter()
for _ in range(5):
    C = A @ B
elapsed = time.perf_counter() - t0
rss_kb = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
print(f"{elapsed:.3f} {rss_kb}")
"""

def run_once(threads: int) -> tuple[float, float]:
    env = os.environ.copy()
    for var in ("OPENBLAS_NUM_THREADS", "MKL_NUM_THREADS",
                "OMP_NUM_THREADS", "NUMEXPR_NUM_THREADS"):
        env[var] = str(threads)
    out = subprocess.check_output(
        [sys.executable, "-c", WORKLOAD], env=env, text=True
    ).strip()
    elapsed, rss_kb = out.split()
    return float(elapsed), float(rss_kb) / 1024.0

if __name__ == "__main__":
    for n in (1, 2, 4, 8):
        elapsed, rss_mb = run_once(n)
        print(f"threads={n:>2}  time={elapsed:6.3f}s  peak_rss={rss_mb:7.1f} MB")

Run it, then run it again with a second copy of the workload in parallel to simulate overlap:

# bench_overlap.py
import concurrent.futures as cf
from bench_blas import run_once

def pair(threads: int):
    with cf.ThreadPoolExecutor(max_workers=2) as ex:
        f1 = ex.submit(run_once, threads)
        f2 = ex.submit(run_once, threads)
        (t1, m1), (t2, m2) = f1.result(), f2.result()
    # wall time of the pair is roughly the max, but measure it properly
    return max(t1, t2), m1 + m2

if __name__ == "__main__":
    for n in (1, 2, 4):
        t, m = pair(n)
        print(f"2 jobs x {n} threads  slowest={t:6.3f}s  combined_rss={m:7.1f} MB")

On a 4-core box the pattern is usually: single job fastest at 4 threads, two overlapping jobs fastest at 1–2 threads each. The crossover point is your scheduling policy.

Two notes on the harness. First, resource.getrusage is POSIX; on Windows use psutil.Process().memory_info().rss instead. Second, subprocess isolation is essential — you cannot change BLAS thread counts within a running process, so each configuration needs a fresh interpreter.

A practical default

For a Windows server running a handful of scheduled Python jobs:

  1. Set OPENBLAS_NUM_THREADS=1, MKL_NUM_THREADS=1, OMP_NUM_THREADS=1, NUMEXPR_NUM_THREADS=1 in the .bat launcher for every job.
  2. Stagger job start times in Task Scheduler so heavy jobs don't overlap where you can avoid it.
  3. Benchmark your actual workload at 1, 2, and 4 threads. If a single job is the only thing running and it's compute-bound, give it more — but only if it doesn't overlap.
  4. Log peak RSS per job. If it swings by a factor of 3 between runs, thread count is the likely cause.

The change is a few lines in a launcher and a setdefault block in your entry module. It's the cheapest performance work you'll do this quarter.
